## 🔴 P0 — 执行时会炸

### 1. P0.3 父类继承校验与 `parse_frontmatter()` 不兼容

**位置**：§P0 新增校验 vs `validate_disease.py:36-50`

P2 父类模板定义了**嵌套 YAML**：

```yaml
功能域定性方向:
  防御域: null
  奖赏域: ↓
  ...
```

但 `validate_disease.py` 的 `parse_frontmatter()` 只做**扁平行解析**（`key.partition(":")`），碰到缩进子键会丢数据。P0.3 描述的校验逻辑（"加载父类文件，解析其 `功能域定性方向:` YAML"）在当前解析器下无法工作。

**建议**：在 P0 中增加一项 `P0.0 — 升级 parse_frontmatter()`

> P0.0: 将 `parse_frontmatter()` 从简单行解析升级为 YAML 解析（`import yaml` 或手写嵌套字典解析），使其能正确读取父类文件的 `功能域定性方向:` 嵌套键和子类文件的 `父类:` 声明。P0.3 依赖此项。

或：简化父类 frontmatter 为扁平格式（所有域方向写在同一行：`功能域定性方向: 防御域=null, 奖赏域=↓, ...`），避免升级解析器。**推荐前者**（YAML 标准解析，长期可维护）。

### 2. 228→364 清扫未完成，P4.3 的乐观假设是错的

**位置**：§P4.3 vs 实际 grep 结果

P4.3 写的是"确认 228→364 链路数清扫已完成"并期望 grep 无残留后标记 ✅。但实测 grep（排除 `link_228` ID 和坐标值 `0.2285` 后）有 **8+ 处残留**：

| 文件 | 行 | 内容 |
|------|:--:|------|
| `呈现/战斗界面布局.md` | 31 | `\| 228 \| 展开底部面板` |
| `管线/预烘焙管线脚本设计.md` | 29, 58, 207, 253 | "228 条链路" ×4 |
| `参考/文献/疾病-脑区链路映射-文献数据源.md` | 252, 265 | "228链路层" ×2 |
| `data/connectivity/subcortical_links_AUDIT.md` | 29 | "228 链路层" |

P4.3 的 grep 命令会找到这些，所以不会出现"假阴性"——但计划文本说"无残留 → 标记 ✅"是错误的预期。实际执行时会是"有残留 → 清理"，这是一个**额外工作量**（估计 6 个文件需要编辑），P4.3 应把它列为明确任务而非假设已完成。

**建议**：将 P4.3 第 1 步改为：

> 1. 执行 228→364 清扫（**已知有残留，不是确认性检查**）：
>    - `呈现/战斗界面布局.md:31`
>    - `管线/预烘焙管线脚本设计.md` ×4
>    - `参考/文献/疾病-脑区链路映射-文献数据源.md` ×2
>    - `data/connectivity/subcortical_links_AUDIT.md:29`
>    - 决策树中的 228 是历史记录（如 `:1060` 已有 `📝 回溯审计修正` 注释），保留不清理

### 4. P2 父类/子类 frontmatter 键名体系不一致

**位置**：§P2.0 迁移模板、§P2 父类模板、§P2 子类模板

三个地方用了三套不同的键名：

| 来源 | 键名 | 值示例 |
|------|------|------|
| P2.0 迁移（偏执型精分） | `父类:` | `奖赏系统障碍` |
| P2 父类模板 | `父类ID:` `父类名:` | `reward-system` / `奖赏系统障碍` |
| P2 子类模板 | `父类:` | `奖赏系统障碍` |

P0.3 的校验函数需要 loaded `父类: 奖赏系统障碍` → 找到父类文件 → 读取 `功能域定性方向`。但解析器怎么知道用 `父类:` 的值去匹配父类文件的 `父类名:` 还是文件名 `_奖赏系统障碍.md`？

**建议**：统一规范——

> **查找规则**：子类 `父类:` 的值 = 父类的 `父类名:` 值 = 父类文件名去掉 `_` 前缀和 `.md` 后缀。P0.3 校验时用 `_<父类值>.md` 路径加载父类文件。父类 YAML 中的 `父类ID:` 仅用于程序化索引（英文 slug），不参与文件名匹配。

并在 P2 中显式写出这条查找规则。

## 🟡 P1 — 设计间隙 / 歧义

### 6. P0 各项的代码集成位置不明确

**位置**：§P0 vs `validate_disease.py` 结构

P0.1/P0.2/P0.3 描述了校验逻辑，但没说它们与 `validate_file()` 的集成方式：

- P0.1（病理类型校验）→ 新函数 `validate_pathology_types()`，在 `validate_file()` 中 ERROR 级调用
- P0.2（权重校验）→ 扩展现有 `validate_drop_pool()`，增加权重列解析
- P0.3（父类继承）→ 新函数 `validate_parent_inheritance()`，需要加载外部父类文件，ERROR 级调用

**建议**：在 P0 末尾加一个"集成规格"小节，明确每个校验项的：函数名 / ERROR 还是 WARNING / 在 `validate_file()` 中的调用位置。

### 7. P4.1 父类交叉验证与 P0.3 的边界模糊

**位置**：§P4.1 末条 vs §P0.3

P4.1 说"父类归属交叉验证：grep 所有疾病文件 `父类:` 声明 → 汇总每个父类的子类列表 → 与父类文件目录对比"。但这是 P0.3 校验的自然延伸——P0.3 需要加载父类文件，加载过程本身就会验证父类文件是否存在。

**建议**：将 P4.1 的交叉验证合并到 P0.3 的 `validate_parent_inheritance()` 中：

> `validate_parent_inheritance()` 做两件事：
> 1. 对每个子类：加载父类 → 校验域方向（P0.3 核心逻辑）
> 2. 汇总所有子类的 `父类:` 声明 → 与 `_*.md` 目录对比 → 有父类无子类或有子类无父类 → WARNING

P4.1 不再单独做交叉验证，改为"P4.1 = 跑 P0 全部校验 + 全量 19 文件无 ERROR"。

### 8. P4.2 的 grep 验证命令假设了不存在的文件格式

**位置**：§P4.2 角色→疾病引用改造

`grep -oP '(?<=疾病: \[).*?(?=\])'` 假设角色文件中已有 `疾病: [重度抑郁症](../../实体/疾病目录/重度抑郁症.md)` 格式。但当前 `实体/角色与面具.md` 的角色定义中没有这种结构化疾病字段——疾病概念以 prose 形式散落在角色描述中（如 `:474` "玩家开局自带初始面具和初始疾病"）。

**建议**：P4.2 分两步：

> 1. 先确认 `实体/角色与面具.md` 中角色疾病信息的当前格式（markdown 表格？段落 prose？）
> 2. 再决定引用改造的具体方案——可能不只是 grep 替换，而是需要为每个角色新增一个"疾病"字段行

### 9. P3 缺少各疾病的预估链路数

**位置**：§P3 全部疾病表

19 个疾病文件，偏执型精分有 15 条链路 / 8 个域。其他疾病如果平均 10-15 条链路，总工作量 = 180-270 行链路数据需要填写（含 m 偏移、病理类型、文献标注/推导标注）。

没有预估链路数 → 无法判断 P3-A/B/C 各档的实际工作量差异 → 分档的依据只是"文献充分度"，而不是"填充工作量"。

**建议**：在 P3 表格中加一列"预估链路数"（可以粗估），并在分档定义中注明"链路数多 + 文献充分 = 优先 A 档"或反之。

### 11. 父类 `_进食障碍.md` 的默认病理类型语法

**位置**：§P2 父类表格

`_进食障碍.md` 的默认病理类型写的是 `解耦沉默 + 过度耦合混合`，其他父类用的是 `或`（如 `_认知控制障碍.md`：`过度耦合 或 解耦沉默`）。

"混合"和"或"语义不同：混合 = 同一链路可能同时有两种类型；或 = 不同链路分属不同类型。应该统一用词或在父类模板中定义这两个词的区别。

**建议**：统一用 ` + ` 表示混合（同一条链路可能有复合类型），用 `或` 表示择一（不同链路取不同类型）。在 P2 父类模板的 §默认病理类型 中加一行说明。

### 12. P0.2 权重范围上限 N 的定义

**位置**：§P0.2

"权重列每个值必须是合法整数且在 `[1, N]` 范围内（N=3，即核心/关联/边缘的上限）"。但 P3 模板中掉落池的权重列格式是 `权重 (tier标签)` 如 `3 (核心)`。如果某疾病只有 2 个 tier 的掉落（核心+关联，无边缘），权重范围应该是 `[1, 2]` 还是仍为 `[1, 3]`？

**建议**：N 定义为"该疾病 CGI-S 域扩展表中实际出现的 tier 数"，而非全局常量 3。或者明确 N=3 是全局上限（所有疾病共用），但允许某些 tier 不出现在特定疾病中（此时权重值最大为该疾病实际 tier 数）。

### 13. P4.3 清扫命令的 `grep -rn "228"` 噪音大

**位置**：§P4.3

当前命令会产生大量噪音（link_228 ID、坐标值 -0.2285、hash b22871cc 等），需要手动筛查。虽然用 `grep -v` 可以排除但这些排除词在计划中没有列出。

**建议**：在计划中给出**精确的清扫命令**（已验证的排除模式）：

```bash
grep -rn "\b228\b" --include="*.md" --include="*.py" --include="*.json" . \
  | grep -v ".git/" | grep -v "\.scratch/" \
  | grep -v "link_228" | grep -v '"id": "link_228"' \
  | grep -v "link_id.*228" | grep -v "0\.2285" \
  | grep -v "b22871cc"
```
