## 🔴 P0 — 执行时会炸

### 1. 父类文件路径双重约定矛盾

**位置**：P0.3 step 2 vs step 11 vs frontmatter 键名规范

PLAN 中出现了两种互相冲突的父类文件路径约定：

| 位置 | 路径格式 |
|------|---------|
| P0.3 step 2 (:69) | `实体/疾病目录/_<父类值>.md` |
| P0.3 step 11 (:93) | `实体/疾病目录/_父类/` 目录 |
| frontmatter 键名规范 (:114) | `实体/疾病目录/_<父类值>.md` |
| P2 父类文件表格 (:232-239) | `_奖赏系统障碍.md` 等（不指定子目录） |

当前 `实体/疾病目录/_父类/` **不存在**，`实体/疾病目录/` 下只有 `偏执型精神分裂症.md`。

**影响**：P0.3 实现者不知道该去哪里找父类文件。如果按 step 2 实现在疾病目录根下找，但 P2 创建者按 step 11 放入了 `_父类/` 子目录，校验会全部 FAIL。

**建议**：统一为以下方案之一：

**方案 A（推荐）**：父类文件放 `实体/疾病目录/_父类/<父类名>.md`。文件名不带 `_` 前缀——目录名 `_父类/` 已标识身份。P0.3 step 2 改为 `实体/疾病目录/_父类/<父类值>.md`。扫描父类文件时遍历 `实体/疾病目录/_父类/*.md`。子类扫描仍为 `实体/疾病目录/*.md`（不进入 `_父类/` 子目录）。

**方案 B**：父类文件放 `实体/疾病目录/_<父类名>.md`（`_` 前缀在文件名上区分）。删除 step 11 中的 `_父类/` 子目录引用，改为在 `实体/疾病目录/` 下扫描 `_` 前缀文件。子类扫描排除 `_` 前缀文件。

方案 A 更清晰——目录结构直接表达语义，且不需要 `_` 前缀做双重编码。

### 2. P0.3-A "净 m 方向"的计算方法未定义

**位置**：P0.3-A step 4-6 (:68-72)

PLAN 说"遍历子类每条链路的 m 偏移方向，与该域的父类定性方向比对"，但**从未定义如何从多条链路的多级 m 值计算一个域的"净 m 方向"**。

设"奖赏域"有两条链路：

| 链路 | m偏移(轻/中/重) |
|------|:---:|
| VTA→NAcc | -0.2/-0.4/-0.6 |
| 黑质致密部→壳核 | 0/-0.2/-0.4 |

净方向显然是负。但如果是：

| 链路 | m偏移(轻/中/重) |
|------|:---:|
| 链路 A | +0.3/-0.1/+0.2 |
| 链路 B | -0.2/-0.3/-0.4 |

净方向取决于算法：
1. 求和所有链路 × 所有严重度的 m 值，取符号 → (-0.5) → 负
2. 取 m 绝对值最大值的符号 → |-0.4| > |+0.3| → 负
3. 多数决：非零 m 值中正负比例 → 6 正 5 负 → 正

不同算法可能给出不同结果。对于 `异常` 约束（至少有一条非零 m），歧义不致命；但对于 `↓`/`↑` 约束，可能造成 false positive/negative。

**建议**：在 P0.3-A 中明确指定算法。推荐**简单求和**：

> **净 m 方向** = sign(Σ 该域所有链路 Σ(轻 m + 中 m + 重 m))。零向量 → 不满足任何方向约束。`异常` → |总和| > 0 即满足，符号不限。`↓` → 总和 < 0。`↑` → 总和 > 0。

选择求和的理由：它在数学上等价于"该域整体是增强还是减弱"，且实现最简单（无分支逻辑）。

### 3. P4.3 228 残留 grep 命令会命中审核追溯文档

**位置**：P4.3 精确清扫命令 (:434-439)

PLAN 正确地将 `docs/决策树.md` 排除在清理范围外（因为它是历史记录——决策时的链路数是 228，保留是正确的）。但 grep 命令**没有排除其他审核追溯文档**：

```
docs/grilling-质量保障体系-v2-审查意见.md:182
docs/grilling-质量保障体系-v2-批改意见.md:108,110,112,264
```

这些和决策树一样，记录的是审核时的历史事实。修改它们会破坏审核追溯的完整性。

**建议**：在 grep 命令中追加排除项：

```bash
grep -rn "\b228\b" --include="*.md" --include="*.py" --include="*.json" . \
  | grep -v ".git/" | grep -v "\.scratch/" \
  | grep -v "link_228" | grep -v '"id": "link_228"' \
  | grep -v "link_id.*228" | grep -v "0\.2285" \
  | grep -v "b22871cc" \
  | grep -v "docs/grilling-" \
  | grep -v "docs/决策树"
```

同时在 P4.3 表格中新增一行：

| 文件 | 操作 |
|------|------|
| `docs/grilling-质量保障体系-v2-*.md` | **保留**（审核追溯，同决策树） |

### 4. P0.3 与 P2 的执行顺序依赖未标注

**位置**：执行检查清单 (:453-468)

P0.3 `validate_parent_inheritance()` 的交叉验证（step 10-13）需要父类文件已存在才能产生有意义的输出。但现在的清单是 P0.0→P0.1→P0.2→P0.3→P1→P2.0→P2——即 P0.3 排在 P2 之前。

可执行的工作流是：

当前清单暗示 P0.3 可以独立完成并给出有意义的校验结果，但事实上在 P2 完成前它只能做空跑。

**建议**：在清单中给 P0.3 加注：

```
- [ ] P0.3: 新增 `validate_parent_inheritance()`（代码实现在 P0 阶段完成；全量校验延迟至 P2 父类文件创建后执行）
```

### 5. P1 文献搜索缺少执行者定义和验收标准

**位置**：P1 (:118-207)

P1 列出了 11 条搜索任务，但有两项关键信息缺失：

- **执行者**：是 AI 用 WebSearch/WebFetch？还是人类去 PubMed/Google Scholar 搜？PLAN 说"搜索前先 `Read`"暗示 AI 参与，但学术文献搜索对 AI 工具可靠性有限（付费墙、DOI 解析不稳定、摘要页结构差异大）。
- **验收标准**：什么算"搜索完成"？找到至少一篇？找到有 Cohen's d 的？搜了但找不到怎么办——标记推导还是阻塞？

**建议**：在 P1 开头加一段执行说明：

> **执行方式**：AI 执行 WebSearch + WebFetch 做首轮搜索，人类复核文献质量和效应量数据。每个疾病搜索预算 ~15 分钟。若某疾病未找到足够文献，标记 `[推导: 文献不足]` 并在该疾病文件中标注推导依据（父类方向 × 相近疾病类比）。
>
> **验收标准**：每个新增疾病至少 1 篇相关文献被找到、摘要已读确认、数据已按模板格式追加到文献数据源文件 §七。

### 6. CGI-S "域数合计"列缺少自动校验

**位置**：P0 校验项列表 + P3 模板

P3 要求每个疾病文件的 CGI-S 域扩展表包含"域数合计"列。但 P0 的校验函数列表中**没有校验"域数合计"是否与实际域数一致**的检查。当前 `validate_cgi_consistency()` 和 `validate_domain_count_constraints()` 都不检查域数合计列。

如果某文件轻度行宣称"域数合计 = 5"，但核心域列只写了 3 个域 → 静默通过。

**建议**：在 P0 中加一项小检查（可放在 `validate_cgi_consistency()` 内或独立函数）：

> **域数合计校验**：对 CGI-S 表的每一行，解析核心域/关联域/边缘域的实际域数量，与"域数合计"列的数值比对。不一致 → WARNING。

实现很简单——`_parse_domains()` 已有，只需对每行计数后比对。

## 🪞 后记：为什么问题反复出现

v1→v2→v3→v4→v5，五轮审查每轮都能发现新问题，这不是某一个人的疏忽，而是**审查方法本身的模式缺陷**：

### 根因一：审查做的是 pattern matching，不是 dry run

每轮审查的方法是"读文本→找不一致"，在语义层做模式匹配。v4 发现"异常方向没定义"→补了 `↑/↓/异常/null` 四种语义的定义（解决了表面问题），但没有往下追问："好，现在我有四条链路各有三级 m 值，你具体怎么算净方向？"

这种追问需要的是**假装自己在写 `validate_parent_inheritance()` 函数**——只有进入实现者的视角，才会撞上"净 m 方向怎么算"这个语义断层。

### 根因二：修复是点状的，不做半径扩大复查

v4 #5 发现"异常方向未定义"→ 补了方向语义表。但没有以这个修复点为锚做周边复查：
- 方向语义表补完了 → 计算方法呢？（#2）
- 矛盾矩阵补完了 → 非矛盾类型呢？（#8）
- P0.3 的 step 2 路径写了对不对？（#1）

修复只管当前问题点，不回溯检查同类问题。

### 对下一轮审查的建议

如果还要再做一轮，**换方法**：

1. **Dry run 执行检查清单**：按 :453-468 的清单逐项模拟执行——P0.0 做什么、输入输出是什么、P0.3 调用它时拿到什么类型、取哪个 key 访问嵌套 dict、文件从哪里读……
2. **以 P0.3 为中心做一次完整数据流追踪**：子类 frontmatter → `parse_frontmatter()` → `validate_parent_inheritance()` → 父类 frontmatter → 方向比对 → 病理类型比对 → 交叉验证。画一张数据流图，逐边检查类型和路径。
3. **修复后做半径扩大复查**：每修一处，以其为锚点检查周边相关定义是否一致。
