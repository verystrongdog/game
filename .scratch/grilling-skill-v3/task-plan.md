## 一、问题诊断

### 1.1 事件还原

2026-08-03，月光物理模型 grilling (#19)。AI 连续两次在同一模式上出错：

| 轮次 | 术语 | AI 脑内默认模型（旧） | 项目定义（M1-M5） | AI 实际使用的 |
|------|------|---------------------|-------------------|-------------|
| 第 1 题 | 月光 | 天体反射太阳光 | 场在视觉中的坍缩表观 | 旧 |
| 第 1 题 | 月相 | 月球绕地球轨道周期 | 集体生物节律拍频 | 旧 |
| 第 2 题 v1 | 场源 | 单一发射体 | 所有感染者的相位同步 | 旧 |
| 第 2 题 v1 | 场传播 | 距离平方反比衰减 | 相干场，无处不在 | 旧 |

**每次错误的共同模式**：AI 已 Read 源文件中的新定义，但生成新内容时，术语的旧现实世界模型劫持了输出。新定义被读到了但**没有被激活为认知基础**。

### 1.2 根因：术语复用认知陷阱

这不是注意力不集中或"没认真读"。这是**认知替换失败**：

- "月光""月相""场源"这些词在 AI 的预训练数据中指向完整的、自洽的现实世界物理模型
- 项目设计文档给这些术语赋予了新含义
- **读一遍新定义不足以卸载一生训练建立的旧模型**
- 当 AI 进入"生成"模式——提出公式、构建推导链——旧模型比新定义更快激活

这比 #16 诊断的"凭记忆引用"更深一层。#16 的问题是"没读到就引用"——修复方法是先 Read。这个问题的根因是**读到了但旧模型劫持了生成**——修复需要新的机制。

### 1.3 普遍性

这个陷阱不限于"月光"。任何使用了**现实世界已有概念的词汇**的设计术语都携带同样的风险：

| 项目术语 | 现实世界默认模型 | 项目实际含义 | 陷阱风险 |
|----------|----------------|-------------|---------|
| 链路 | 计算机网络连接 / 简单连线 | 两个脑区间的有向功能连接 | 中 |
| 感染 | 病原体传播 | 月光场中的耦合状态 | 高 |
| 场 | 电磁场 / 引力场 | 多源相位同步的相干观察场 | 高 |
| 技能 | 游戏角色可学习的动作 | 链路上下文的链路组封装 | 中 |
| 态度 | 一个人的评价倾向 | ⚠️ 已废弃（认知+情绪+行为=态度，结果非实体） | 高 |
| 防御 | 物理格挡/闪避 | 跨行动窗口持续状态（物理伤害-50%） | 低 |
| 装备 | 角色穿戴的物品 | 面具组件 = 链路激活/抑制 | 中 |

**每次 grilling 涉及这些术语时，都存在旧模型劫持 AI 生成的风险。**

### 1.4 为什么现有机制（v2）无法防御

| v2 机制 | 防护目标 | 为什么对此类漏洞无效 |
|----------|---------|-------------------|
| 事实锚定 (3.2) | 确保引用有源文件支撑 | 引用对了源文件 (§x)，但生成的内容仍然用了旧模型——引用是正确的，理解是错误的 |
| 决策深度自检 (3.3) | 防止浅层共识 | 自检不包含"我的默认模型是否正确"这一维度 |
| 一致性清扫 (Step 4) | 清理残留引用 | 清扫检查的是文件间的引用一致性，不是"写下的数值是否与术语定义兼容" |
| 引用即读取铁律 | 防止记忆引用 | 已读到了——但读到 ≠ 理解对了 |

**v2 的脆弱假设**：读取源文件 → 信息正确进入认知 → 基于正确信息生成。但术语复用打破了第二步：新信息确实进入了认知，但在生成时被旧模型的更强路径覆盖。

## 二、解决方案

### 2.0 数据基础：术语注册表 `term_registry.json`

在讨论 3.0 机制之前，必须先建立**术语注册表**——一个结构化的、可被脚本校验的术语定义文件。

**为什么需要**：review-plan 暴露的 G1-G5 有一个共同根因——当前方案让 AI 同时承担四个角色：术语识别者、定义查找者、旧模型回忆者、兼容性判定者。这四个角色全部依赖 AI 认知，而 AI 认知已被证明在术语复用场景下不可靠。**术语注册表将前三个角色的数据从 AI 脑中移入结构化文件**，AI 只承担"查询+声明新假设"的角色。

#### 2.0.1 文件位置与结构

`data/term_registry.json` —— 与 `brain_regions.json`、`link_registry.json` 同级，属于管线层数据资产。

```json
{
  "terms": {
    "月光": {
      "definition": "场在视觉感知中的坍缩表观。不是来自天体——来自零号病人激发的相干场，经场相变和生物节律拍频调制后在视觉通道的呈现。",
      "source": "决策树.md M1-M5（2026-08-02 Boss 设计 Grilling）",
      "old_model": "天体反射太阳光——月球绕地球轨道的天文周期",
      "deviation_reason": "项目世界观中不存在独立于场的'月亮'。月光是观察者效应下场的表观，强度由场相态×源密度×耦合度决定，不由天体位置决定。",
      "status": "active",
      "numerical_locations": [
        "规则/核心机制.md §6.3（月光调制 1.0-2.0×）",
        "实体/敌人与事件.md §8.2（月相表：新月 0.5-0.7× / 弦月 0.8-1.0× / 满月 1.3-2.0×）",
        "事件/游戏循环.md §2.1（三段：上午弱/下午中/夜晚强）"
      ],
      "added": "2026-08-03",
      "updated": "2026-08-03"
    }
  }
}
```

#### 2.0.2 字段语义

| 字段 | 类型 | 说明 |
|------|------|------|
| `definition` | 文本 | 项目中的现行定义。如术语含义发生过变更，此为最新版本。定义变更时**必须同步更新** |
| `source` | 文本 | 定义的来源——决策树节点或设计文档§。可追溯 |
| `old_model` | 文本 | 该术语在现实世界中的默认模型。如果现实模型与项目定义一致（如"髓鞘化"在神经科学中也是 use-driven），填 `—（与项目定义一致，无偏离）` |
| `deviation_reason` | 文本 | 项目为何偏离旧模型。如果无偏离（old_model 无冲突），填 `—` |
| `status` | `枚举<active\|deprecated\|under_revision>` | `active`=现行有效；`deprecated`=已废弃（保留为参考）；`under_revision`=当前 grilling 中正在修改 |
| `numerical_locations` | `List<引用<文档§>>` | **关键字段**——所有引用该术语并包含数值/公式的活跃文档位置。Step 4.7c 的兼容性检查依赖此字段。术语定义变更时，这些位置必须逐一复查 |
| `added` | 日期（ISO 8601 YYYY-MM-DD） | 首次加入注册表的日期 |
| `updated` | 日期（ISO 8601 YYYY-MM-DD） | 最后一次修改定义的日期 |

#### 2.0.3 准入标准

什么术语需要进入注册表？**三个条件满足其一即可**：

1. **术语在现实世界中有常用含义，且项目偏离了该含义**（如月光/感染/场/防御/装备）——这是陷阱风险最高的类别，必须注册
2. **术语出现在 CLAUDE.md §核心术语表中**——已有机密级术语定义，应集中管理
3. **术语是项目独创但承载核心机制语义**（如髓鞘化/可塑性巩固/聚焦容量）——虽无旧模型冲突，但需明确数据来源
4. **术语在 ≥2 个活跃设计文档中被引用，且具有机制语义（含数值/公式/规则）**——即使不在前三个条件中，高频使用的机制术语也应注册以启用 numerical_locations 追踪。例："激活点"已更名为聚焦容量，但旧词在文档中仍有残留引用——注册旧词并标记 status=deprecated，numerical_locations 列出需迁移的位置

初始注册表从 CLAUDE.md 核心术语表 + §1.3 风险表中的术语作为第一批填充。后续 grilling 中每遇到新术语 → 追加到注册表。Step 4.7c 清扫发现未注册的高频术语 → 追加。

### 2.1 核心机制：定义基线声明（3.0）——注册表驱动

在 Step 3 的每个问题之前，AI 执行定义基线声明。**与初版的关键区别：术语定义不再由 AI 从文档中临时搜索+回忆——而是从 `term_registry.json` 中查询。**

```
AI 的工作流变为:
  1. 扫描当前问题涉及的关键概念
  2. 查询 term_registry.json → 匹配到的术语直接填入基线
  3. 未匹配到的术语 → 标记为"本次新假设"（可能是候选注册术语）
  4. 旧模型列已由注册表提供 → AI 不需要自己回忆
```

**格式模板**：

```markdown
### 第 N 题 — [问题]

#### 定义基线（从 term_registry.json 查询）

| 术语 | 项目定义 | 来源 | 旧模型（已否决的默认模型） |
|------|---------|------|---------------------------|
| [术语A] | [来自 term_registry.json 的 definition 字段] | `term_registry.json` + `源文件.md` §N | [来自 old_model 字段] |
| [术语B] | [同上] | ... | — （与项目定义一致，无偏离） |

#### 检查

- 术语A → 注册表命中 ✅
- 术语B → 注册表命中 ✅
- 术语C → ⚠️ 不在注册表中 → **本次新假设。建议 grilling 结束后评估是否追加到注册表。**
```

### 2.2 关键设计决策

**D1 — 注册表是基线声明的唯一数据源。** AI 不再在 3.0 阶段做临时的定义搜索。如果术语不在注册表中，它就是"新假设"。这消除了 AI 搜索质量不稳定和旧模型回忆不可靠两个变量。

**D2 — "旧模型"列由注册表维护，不由 AI 即兴填充。** 注册表的 `old_model` 和 `deviation_reason` 字段由设计者在术语入库时填写一次，此后所有 grilling 会话复用。这解决了 review-plan G2（AI 声称的"现实默认含义"用户无法验证）——用户只用审查一次，写入注册表后不再争议。

**D3 — 新假设显式声明 + 注册候选。** 不在注册表中的术语 → 声明为"本次新假设"。grilling 结束后评估：如果该术语 (a) 在现实中有常用含义且项目偏离，或 (b) 成为核心机制术语 → 追加到注册表。如果是一次性的临时概念 → 不进注册表。

**D4 — "无偏离"术语的豁免。** 如果注册表中的术语 `old_model` = `—（与项目定义一致，无偏离）`，基线表中该行可省略旧模型列内容，标注 `—` 即可。但**不能整个术语跳过**——仍需确认"这个术语在本问题中是否被正确使用"。

**D5 — 每轮仍要输出基线表，但可引用前轮。** 注册表消除了"AI 每次临时回忆旧模型"的变量，但如果 20 个问题涉及完全相同的一组术语，输出 20 次完整表格仍是浪费。允许去重引用：

```markdown
#### 定义基线
术语集与第 N 题相同，无新增术语。约束集复用第 N 题的基线声明。
新增术语: [X] — ⚠️ 不在注册表中，本次新假设。
```

**去重引用的时效前提条件**（必须全部满足才能复用）：
1. 被引用的第 N 题属于**同一次 grilling 会话**（跨会话不使用——不同会话的文档状态可能已变更）
2. 中间轮次**未修改**该术语集中任一术语的定义（grilling 中的临时共识不影响注册表本身，但可能影响对术语的"理解"——保守策略：如果中间任何一轮用户否定了涉及某术语的假设，该术语的基线不得复用，必须重新查询注册表）
3. 中间轮次**未新增**与已有术语冲突的新假设

AI 在去重引用前自检这三条。任一不满足 → 输出完整基线表。

**D6 — 编号与位置。** §3.0 插入在 §3.1（基本规则）之前。完整编号：3.0 定义基线声明 → 3.1 基本规则 → 3.2 事实锚定 → 3.3 决策深度自检。先建立约束集，再在约束集内做事实锚定。

**D7 — 注册表入库触发时机。** 以下任一发生时，术语必须加入注册表：
- Grilling 中创建了新的核心机制术语（如本次"场的相态"）
- 已有术语的定义被 grilling 修改（定义变更 → 注册表 `updated` 字段同步更新 + `numerical_locations` 重新验证）
- 发现现有术语在项目中被使用但不在注册表中（Step 4.7c 清扫时发现）

**入库执行者**：AI 在 Step 5（关 issue）之前，列出本次 grilling 中产生的"注册候选清单"（新术语 + 定义变更的术语），用户确认后写入 `term_registry.json`。此步骤整合进 Step 4 写入流程——注册表更新与设计文档写入在同一批次完成。如有术语的 numerical_locations 需要填充 → 运行 `build_term_registry.py`（增量模式）生成初稿 → 人类确认。

### 2.3 自检规则（配合 3.0）

在 3.3 决策深度自检的"何时不能停"清单中新增：

- **基线表中出现不在注册表中的术语，且该术语在现实中有常用含义 → 追问用户：是否将此术语加入注册表？其旧模型是什么？项目为何偏离？**

### 2.4 与 Step 4 一致性清扫的集成

**Step 4.7c 从 AI 判断改为注册表驱动的结构检查。**

原来的问题（review-plan G5）：AI 判断"已有数值是否与新定义兼容"——这正是 AI 不可靠的环节。改为两层：

**Layer 1 — 脚本层（可自动化）**：
```
1. 读取 term_registry.json 中本次修改的术语
2. 对每个术语，遍历其 numerical_locations
3. 检查: 该引用的文档是否存在？段落是否存在？→ 结构性检查（确定性强）
4. 检查: 注册表 updated 日期是否晚于源文件的最后 git 修改日期？
   → 如果注册表 updated < 源文件修改日期 → WARN: "源文件已更新，注册表定义可能过期"
   → 不逐字比较内容——避免假阳性。用文件修改时间作为"可能不一致"的代理信号
5. 输出差异报告（结构断裂 + 可能过期）
```

**Layer 2 — 人类/AI 辅助层（参考脚本输出）**：
```
对 Layer 1 报告的每个差异:
  - AI 列出: 旧数值 | 新定义 | 可能的冲突
  - 标注: 兼容 / 需修订 / 不确定
  - "不确定"必须标记 ⚠️ 需人类复查
```

**关键**：Layer 1 的脚本检查是确定性的（结构层——数值位置的引用是否断裂、定义是否同步），Layer 2 的语义判断在 AI 辅助下做但默认为"不确定"。这避免了 Step 4.7c 的自举悖论——AI 不单独做兼容性判断，只做"列出差异 + 建议"。

**numerical_locations 的维护规则**：
- 术语注册时 → 首次填充
- 每次 grilling 在文档中新增了引用该术语的数值/公式 → Step 4 追加到注册表的 `numerical_locations`
- 每次 grilling 修改了术语定义 → 遍历 `numerical_locations` 逐一复查兼容性
- **脚本定期校验**：grep 全项目找术语出现位置 → 对比 `numerical_locations` 列表 → 发现未注册的数值使用 → WARNING

### 2.5 与 review-plan 的交叉效果

review-plan SKILL.md 的 H1 拉入被引用文件时，直接读取 `term_registry.json` 做术语语义基准。如果引用方对术语的使用方式与注册表中的 `definition` 暗示的类型/边界不一致 → 标记 `⚠️ 语义偏移（对照 term_registry.json）`。

**numerical_locations 初始填充方法**：

分两步：

1. **脚本自动生成初稿**（`tools/build_term_registry.py`，本次实施时编写）：
   - 对每个术语，`grep -rn` 全项目 `*.md` 和 `*.json` 文件

   - 输出：`{术语: [文件路径:行号]}` 映射
   - AI 辅助将行号转换为段引用（`§N`）——优先段引用，因为段引用比行号稳健

2. **人类确认**：
   - 逐术语审查初稿列表
   - 删除误报（纯叙述性的数字提及，非机制性数值）
   - 补充遗漏（脚本 grep 关键词匹配可能漏掉变体/同义词）
   - 确认后写入 term_registry.json 的 numerical_locations 字段

3. **后续维护**（§2.4 D11）：每次 grilling Step 4 时更新。

> **⚠️ 首批填充是本次实施的阻塞前提**——没有 numerical_locations，Layer 1 脚本和 Step 4.7c 无法运作。`build_term_registry.py` 的编写是本计划的第一步。
