## 一、问题诊断

### 1.1 退化表现（5 类）

| # | 类型 | 描述 | 严重度 | 最近案例 |
|---|------|------|--------|----------|
| 1 | **事实引用错误** | AI 引用参数/公式/决策时凭记忆（训练数据概率分布），而非实际读取源文件确认 | 🔴 致命 | 本文档 v1 即犯此错——SAN 阈值行号写为 205，实际在 314-318（见批改意见 B1） |
| 2 | **遗漏已有约束** | 新决策与已有设计冲突，AI 未发现——因为相关文档未被读取到上下文中 | 🔴 致命 | `subcortical_links.json` 对抗性审核修正 (commit `a1e4cd1`) — 3 处事实性错误需事后补修 |
| 3 | **决策深度不足** | 未追问到足够深度就草率达成共识，遗漏关键分支 | 🟡 严重 | `[待回溯填充]` 触发：回溯最近 3 轮 grilling，标记是否有"单字确认"导致的浅层共识 |
| 4 | **写入不完整/错位** | 决策写入设计文档时遗漏细节、参数、或写错文件位置 | 🟡 严重 | `[待回溯填充]` 触发：回溯最近 3 轮 grilling 的 Step 4 写入验证，检查决策→文档的转录完整性 |
| 5 | **跨文件矛盾** | 同一轮 grilling 改动的多个文件之间产生不一致 | 🔴 致命 | `[待回溯填充]` 触发：对六维状态中"已完成"项逐项交叉验证（两个文档引用同一参数但值不同） |

### 1.2 根因

**信息基础不可靠。** Grilling 过程中 AI 的知识来源有两个：

| 来源 | 可靠性 | 当前利用情况 |
|------|--------|-------------|
| **项目文件**（设计文档、数据 JSON、决策树、参数表） | ✅ 可靠（ground truth） | ❌ 依赖 AI "记忆"而非强制读取 |
| **AI 训练数据**（神经科学知识、游戏设计常识） | ⚠️ 半可靠（可能有幻觉） | ✅ 被过度依赖 |

**核心矛盾**：AI 的上下文窗口有限，面对复杂话题时，无法一次性将所有相关文件装入上下文。结果就是"凭记忆引用"——而记忆不可靠。

### 1.3 为什么事后审核不够

事后审核（提交前检查/定期扫描）只能抓到已产生的错误，不能阻止错误产生。需要的是**过程内质量保障**——在 grilling 的每一步强制信息验证。

## 二、核心原则：引用即读取

### 2.1 铁律定义

> **任何事实性引用，必须先 `Read` 源文件确认。不得凭记忆引用项目内的参数、公式、设计决策、文件路径。**

### 2.2 适用范围

以下内容属于"事实性引用"，触发铁律：

| 引用类型 | 示例 | 必须 Read 的文件 |
|----------|------|-----------------|
| 数值参数 | "SAN 基线是 80" | `规则/核心机制.md` 或对应 grilling memory |
| 公式 | "Δm = base(L) × (1-sigmoid(m,0.45,10)) × g(n)" | `规则/核心机制.md` §八 |
| 已有决策 | "我们之前决定过 NPC 用预烘焙查表" | `docs/决策树.md` + 对应的 grilling memory |
| 文件路径 | "在 `规则/技能树系统/操作层/` 下" | `ls` 或 Glob 确认路径存在 |
| 数据结构 | "link_legitimacy_matrix.json 约有 360+ 条链路" | `data/connectivity/link_legitimacy_matrix.json`（快照：364 条 @2026-08-01，实际以 `_stats.legal_links` 为准） |
| 交叉引用 | "详见 §五" | Read 目标文件确认小节存在 |

以下内容**不触发铁律**（可以凭常识回答）：

- 通用神经科学知识（如"前额叶参与执行功能"）
- 游戏设计常识（如"回合制需要速度排序"）
- 对用户问题的理解性复述

### 2.3 自检触发信号

出现以下短语时，AI 应触发自检——这些短语是凭记忆引用的常见模式。自检通过（有 `Read` 记录支撑 + 标注来源文件/段落）则引用合法；无 `Read` 记录支撑则判定为违规：

- "根据我们之前的讨论..."
- "项目中使用的是..."
- "按照 CLAUDE.md 的规定..."
- 任何不带文件路径和段落号的参数/公式引用

正确的引用格式（优先使用段引用，因为行号随编辑漂移）：

> `规则/核心机制.md` §5.1 — SAN ≥ 60 稳定（行 314），< 30 恐慌（行 316），= 0 随机行为（行 318）

**行号 vs 段引用的选择原则**：段引用（`§5.1`）更稳健但粒度粗；行号精确但易过时。**优先使用段引用，仅在需要精确定位某句话时附加行号。**

### 3.3 决策深度自检规则

#### 何时不能停（以下任一条件触发，必须继续追问）

## 四、项目级引用规范

> **路径约定**：本文及项目所有文档中 `memory/` 是 `~/.claude/projects/-home-dog-game/memory/` 的简写。
> 此简写在 CLAUDE.md 上下文中自动解析（通过 tool 的 memory 系统注入），但发给外部窗口的文档中应在首次出现时附完整路径。
> 详见 [附录 B：路径约定](#附录-b路径约定)。

### 4.1 文件路径引用格式

```
# 段引用（推荐，最稳健——不受行号漂移影响）
`规则/核心机制.md` §八             →  文件 §节号
`规则/核心机制.md` §5.1            →  文件 §子节

# 精确引用（需要精确到行时使用，注意行号随编辑漂移）
`规则/核心机制.md:314`             →  文件:行号
`data/connectivity/link_legitimacy_matrix.json`  → 完整相对路径（数据文件不需要行号）

# Memory 引用（路径约定见附录 B）
`memory/grill-brain-skill-tree-2026-07-27.md` §11.5  →  memory 文件 + 段落
```

**选择原则**：优先段引用。仅在需要精确定位某句话（如引用某个特定数值）时附加行号。行号是易碎品——每次编辑都可能导致漂移。

### 4.2 参数定义规范

所有数值参数在文档中定义时，使用统一格式：

```markdown
| 参数 | 符号 | 默认值 | 范围 | 来源 |
|------|------|--------|------|------|
| SAN 基线 | SAN₀ | 80 | 70-90 | `memory/numerical-calibration-grilling-2026-07-31.md` |
| 激活点起始 | AP₀ | 4 | 固定 | Cowan 2001, `规则/核心机制.md` §2.1 |
```

**🆕 新增参数必须标注 `[NEW]` 和所属 grilling issue 编号**：

```markdown
| 审核超时阈值 | T_review | 300s | 60-600 | [NEW] [#16] |
```

**`[NEW]` 标记生命周期**：在所属 grilling issue 关闭后，**下一次涉及该文件**的 grilling 或文档编辑中摘除，最迟不超过两轮 grilling。超过两轮仍未摘除视为过期标记，应改为 `[NEW-since-#xx]` 或移除。目的是防止标记长期残留（"下一轮 grilling"可能与参数所在文件完全无关，导致无人看到该标记）。

### 4.3 决策引用格式

```
# 决策树节点引用
决策树: [Grilling] 数值校准 §第7题  →  HP基线=50±10

# Memory 引用
memory: numerical-calibration-grilling-2026-07-31.md §N

# Issue 引用
[#16] → https://github.com/verystrongdog/game/issues/16
```

### 4.4 交叉引用规范

文档间的交叉引用统一格式：

```markdown
# 正确 ✅
详见 [核心机制 §八 可塑性巩固](../规则/核心机制.md) —— §八 可塑性巩固 小节

# 错误 ❌
详见 核心机制.md 的可塑性巩固部分
```

引用时确保：
1. 使用相对路径（相对于当前文件所在目录）
2. 展示文本清晰描述目标内容（不只是裸文件名）
3. 包含小节锚点（如适用）

**⚠️ 锚点兼容性说明**：Markdown 锚点生成规则因渲染器而异。GitHub 将 `## 八、可塑性巩固` 转为 `#八可塑性巩固`（去掉标点符号），但 VS Code 预览、Pandoc、或其他渲染器可能生成不同锚点。**如不确定目标渲染器，优先使用段引用格式（`§八`）而非 URL 锚点**——段引用是给人读的，不依赖渲染器行为。

| `tools/validate_grilling_quality.py` | 检查最近一轮 grilling 的产物完整性（决策树追加/六维更新/memory 写入/文档修改） | P0 | grilling Step 5 |
| `tools/validate_json_schema.py` | 检查 `data/` 下 JSON 文件与 schema 一致 | P1 | 提交前 |

> **命名规范**：所有校验脚本统一使用 `validate_` 前缀。原计划中的 `check_grilling_quality.py` 更名为 `validate_grilling_quality.py`。

### 5.2 `validate_cross_refs.py` 规格

```python
"""
扫描 docs/ 和 规则/ 下所有 .md 文件，提取其中的交叉引用（格式: [text](path)），
检查目标文件是否存在。
CLI: --format json|text, --output <file>, --base-dir <项目根目录>
输出: 统一 JSON 格式（见 §5.4），列出死链列表 + 源文件位置。
"""
```

### 5.3 `validate_grilling_quality.py` 规格

```python
"""
输入: grilling issue 编号
检查项:
1. docs/决策树.md 中是否有对应记录（grep issue编号）
2. docs/设计框架-六维状态.md 对应维度是否有更新
3. memory/ 下是否有新/改 memory 文件
4. 是否有 md 文件在本轮中被修改（git diff --name-only）
5. (未来) 写入验证表是否每一项都标记为"已验证"
CLI: --issue <N>, --format json|text, --output <file>
输出: 统一 JSON 格式（见 §5.4），通过/不通过 + 缺失项列表
"""
```

### 5.4 校验脚本的统一输出格式

所有校验脚本输出统一 JSON：

```json
{
  "script": "validate_cross_refs",
  "timestamp": "2026-08-01T12:00:00Z",
  "summary": {
    "total": 156,
    "passed": 150,
    "blocker": 2,
    "warn": 3,
    "info": 1
  },
  "blocker": [
    {
      "source_file": "规则/核心机制.md",
      "source_line": 489,
      "target": "../参考/废弃/态度系统/态度结算.md",
      "reason": "文件不存在（已删除或路径错误）"
    }
  ],
  "warn": [],
  "info": []
}
```

**退出码约定**：`0` = 全部通过（无 blocker）；`1` = 有 blocker（CI 应失败）；`2` = 脚本自身错误（如文件不可读）。warn 和 info 不影响退出码。

## 附录 A：校验脚本开发规范

### CLI 接口

所有 `tools/validate_*.py` 脚本须支持以下标准参数：

```
usage: validate_xxx.py [--format {json,text}] [--output FILE] [--base-dir DIR] [options]

Standard options (all scripts):
  --format {json,text}   输出格式（默认 text）
  --output FILE          输出文件路径（默认 stdout）
  --base-dir DIR         项目根目录（默认脚本所在目录的父目录，即 repo root）
  --help                 显示帮助

Script-specific options:
  --issue N              (validate_grilling_quality.py) grilling issue 编号
  --strict               将 warn 升级为 blocker
```

### 退出码

| 退出码 | 含义 |
|--------|------|
| 0 | 全部通过（summary.blocker = 0） |
| 1 | 存在 blocker（CI/pre-commit hook 应拒绝） |
| 2 | 脚本自身运行错误（如输入文件不存在、JSON 解析失败） |

### Python 环境

- Python ≥ 3.10
- 标准库优先（`json`, `argparse`, `pathlib`, `re`）
- 仅在必要时引入第三方库（如 `jsonschema` 用于 JSON Schema 校验），并在 `tools/requirements.txt` 中声明

### 输出约定

- `--format json`：输出 §5.4 定义的统一 JSON 格式到 stdout 或 `--output` 文件
- `--format text`（默认）：人类可读的分组列表输出
- blocker/warn/info 三级分类，定义见 §1.1
