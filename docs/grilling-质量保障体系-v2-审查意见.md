## 🟡 重要级

### R1. 行 507 — 文档尾部交叉引用自违反 §4.4 规范

> 原文：`*关联: [设计框架-六维状态](设计框架-六维状态.md), [CLAUDE.md](../CLAUDE.md), [批改意见](grilling-质量保障体系-v2-批改意见.md)...*`

**问题**：§4.4 明确规定交叉引用的展示文本必须"清晰描述目标内容（不只是裸文件名）"。`[CLAUDE.md](../CLAUDE.md)` 的展示文本正是裸文件名——质量保障文档自身的尾部违反自身规范。这是一个 ironic 的自我矛盾。

此外，三个链接的展示文本风格不统一：
- `设计框架-六维状态` — 描述性名称
- `CLAUDE.md` — 裸文件名
- `批改意见` — 部分描述

**建议修正**：
```markdown
*关联: [设计框架-六维状态](设计框架-六维状态.md), [项目配置文件](../CLAUDE.md), [v2 批改意见](grilling-质量保障体系-v2-批改意见.md), [Grilling Issue #16](https://github.com/verystrongdog/game/issues/16)*
```

### R2. 行 65 — 硬编码数据快照 "364 条" 与文档自身逻辑矛盾

> 原文：`"link_legitimacy_matrix.json 约有 360+ 条链路"` → `数据/connectivity/link_legitimacy_matrix.json`（当前实际 364 条，2026-08-01）

**核查**：`_stats.legal_links` = 364，数据正确。

**问题**：文档自身的核心论点之一就是"行号随编辑漂移，数字会过时"。§2.2 表格中 `link_legitimacy_matrix.json` 条目被用作"引用格式示例"——而示例值 `364` 是一个**硬编码快照**。虽然加了日期标注，但：

1. 日期标注（`2026-08-01`）容易被后续编辑者忽略更新
2. 这正是文档 §1.1 诊断的类型 1 问题（"事实引用错误"）的潜在来源——下次有人读这个示例，可能不验证就直接引用 "364"

**建议**：将表格中的示例改为不依赖具体数字的表述，或显式标注为快照：
```markdown
| 数据结构 | "link_legitimacy_matrix.json 约有 360+ 条链路" | `data/connectivity/link_legitimacy_matrix.json`（快照：364 条 @2026-08-01，实际以 `_stats.legal_links` 为准） |
```

### R3. 行 415-421 — 阶段 1 实施存在自指循环

> 原文：`阶段 1：铁律入法（立即，本次 grilling 完成后）`

**问题**：本文档**自身就是一次 grilling 的产物**。阶段 1 说"本次 grilling 完成后"执行——但文档里写的规则（如"引用即读取"、Step 0 资料包声明）在**本次 grilling 过程中尚未生效**。这形成了一个自指循环：

```
文档说："grilling 时必须先 Read 源文件"
但这条规则要等本文档写入 CLAUDE.md 后才生效
而本文档的写入动作自身并未经过它所要求的质量检查
```

**这不是文档错误**（自指是这类元层次文档的固有属性），但**应该显式承认这个 bootstrapping 问题**，避免给外部执行者造成"一切已就绪"的错觉。

**建议**：在阶段 1 开头加一句：
```markdown
> **Bootstrapping 说明**：本文档自身的撰写过程尚未受益于其所定义的强化流程。
> 阶段 1 完成后，后续所有 grilling 将受新规则约束。
```

### R4. 行 136 — CLAUDE.md 现有 grilling 规则与新增强化流程的合并策略未讨论

> 阶段 1 计划："将 §三 'Grilling 流程强化' 的新增步骤写入 Grilling skill 指令"

**事实核查**：CLAUDE.md 中已有详细的 grilling 规则（行 134-199），包含 Step 0-5 的逐步骤清单。v2 的 §三 强化流程是在**此基础之上**增加检查点（如 0.3 资料包、3 事实锚定、4.5 写入验证表、5.2 校验脚本）。

**问题**：阶段 1 只说"写入 CLAUDE.md"和"写入 skill 指令"，但没有明确：
1. 强化后的检查点是**追加**到现有 CLAUDE.md grilling 规则中，还是**替换**？
2. 如果追加——CLAUDE.md 已有 12 个 grilling 步骤项（Step 0: 3 项 + Step 1-5: 各 1-4 项），新增后可能达到 20+ 项。CLAUDE.md 的 `只增不删` 铁律（行 75）意味着旧步骤不能被删除，只能追加——grilling 规则会越来越长。
3. CLAUDE.md 和 skill 指令的分工边界在哪里？（CLAUDE.md = 触发规则 + 步骤骨架，skill = 详细执行指令？）

**建议**：在阶段 1 中增加一行：
```markdown
- [ ] 确认 CLAUDE.md vs skill 的分工边界：CLAUDE.md 保留触发规则 + Step 编号骨架，
      skill 承载详细检查清单（方案 B 的 agent definition 路径）
```

## 🔵 建议级

### r1. 行 303 — 锚点示例使用 GitHub 特定格式，与自身警告不完全一致

> 原文（§4.4 示例）：
> ```markdown
> # 正确 ✅
> 详见 [核心机制 §八 可塑性巩固](../规则/核心机制.md#八可塑性巩固)
> ```

**核查**：`规则/核心机制.md` 行 404 = `## 八、可塑性巩固`。GitHub 将 `、` 去掉生成锚点 `#八可塑性巩固`，此链接在 GitHub 上有效。

**问题**：§4.4 末尾（行 316）已经加了锚点兼容性警告，说"如不确定目标渲染器，优先使用段引用格式（`§八`）而非 URL 锚点"。但 §4.4 的**主示例**仍使用了 URL 锚点（`#八可塑性巩固`）。警告和示例之间存在轻微矛盾——读者会困惑："既然你推荐段引用，为什么正确示例里用的是锚点？"

**建议**：将"正确 ✅"示例改为纯段引用格式（与警告一致）：
```markdown
# 正确 ✅
详见 [核心机制 §八 可塑性巩固](../规则/核心机制.md) —— §八 可塑性巩固 小节
```

### r2. 行 208 — Step 3 产物模板中 memory 路径未附带解析说明

> 原文：
> ```markdown
> - `memory/numerical-calibration-grilling-2026-07-31.md` (→ 路径见附录 B) — 玩家 HP 基线 50
> ```

**问题**：`(→ 路径见附录 B)` 是一个合理的指针——但 Step 3 产物模板是给**每轮追问的回答**用的。如果每轮回答的"事实依据"里都出现 `memory/` 路径，读者需要反复跳转到附录 B 才能理解。更友好的做法是在模板中首次出现时内联简短说明。

另外，这个模板中的 `memory/` 引用本身是在**示意**——实际 grilling 中 AI 会替换为真实的 memory 文件引用。但模板没有说明 `memory/` 前缀在输出时应如何处理（是保留简写还是展开为完整路径）。

**建议**：在模板的 `memory/` 行下加一行注释：
```markdown
- `memory/numerical-calibration-grilling-2026-07-31.md` — 玩家 HP 基线 50
  <!-- memory/ = ~/.claude/projects/-home-dog-game/memory/，在发给外部窗口时替换为完整路径 -->
```

### r3. 行 246 — "首次出现时附完整路径"的首次出现时机不明确

> 附录 B 说明：`此简写在 CLAUDE.md 上下文中自动解析...但发给外部窗口的文档中应在首次出现时附完整路径。`

**问题**：`memory/` 在本文档中的**首次出现**是行 61 的 §2.2 表格（`数值参数 → memory/numerical-calibration-grilling-2026-07-31.md`），而非行 246 的 §四 显式定义处。行 61 处没有任何路径说明——读者在读到 §四（约 200 行之后）之前，已经遇到了 3 次 `memory/` 引用（行 61, 208, 215）。

**这不是严重问题**（因为文档有目录，读者可以跳转），但严格来说违反了附录 B 自身的约定。

**建议**：在 §二 或文档更靠前的位置（如首次目录之后）加一行路径约定提示：
```markdown
> **路径约定**：本文中 `memory/` 是 `~/.claude/projects/-home-dog-game/memory/` 的简写。详见 [附录 B](#附录-b路径约定)。
```

以下方面在 v2 中处理得很好，值得肯定：

1. **批改意见 17 条全部修正到位**：B1-B5（5 条阻塞）、S1-S7（7 条重要）、C1-C5（5 条建议）逐条落实，无遗漏。详见下方[追溯验证](#批改意见追溯验证)。

2. **§2.3 违规信号 + 正确引用格式**（行 76-86）：新增的"段引用优先"原则和行号漂移警告是 v2 最有价值的增量——直接解决了 v1 的行号错误根因（不只是修一个数字，而是建立了防止同类错误的机制）。

3. **§4.4 锚点兼容性说明**（行 316）：⚠️ 警告框准确指出了 Markdown 锚点的渲染器依赖性问题。这是 S2 批改意见的优雅解决方案——不是禁止锚点，而是告知风险并给替代方案。

4. **§3.1 纯缩进版流程图**（行 139-169）：C1 批改意见的解决方案。双版本（box-drawing + 纯缩进）确保在任何终端/字体下可读。

5. **§3.3 双清单设计**（行 226-240）："何时不能停"+"何时可以停"形成完整的决策门控。C4 批改意见的解决方案到位。

6. **附录 A 校验脚本开发规范**（行 446-484）：CLI 接口、退出码、Python 环境、输出约定——S6 批改意见要求的全部内容。规范具体、可执行。

7. **§5.4 统一 JSON 输出格式**（行 379-408）：`blocker/warn/info` 三级分类 + `source_file/source_line/target` 字段设计 + 退出码约定（0/1/2）——是一个完整的、可直接实现的 spec。
