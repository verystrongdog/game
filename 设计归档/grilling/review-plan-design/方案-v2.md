## 一、问题诊断

### 1.1 v1→v5 退化模式

五轮审查，每轮发现更深层问题，但审查方法始终是"读文本→找不一致"的 pattern matching：

| 轮次 | 典型发现 | 审查方法 |
|------|---------|---------|
| v1 | 计数错误、表格缺行 | 表面一致性 |
| v2 | 残留引用、措辞修正 | 交叉文件比对 |
| v3 | YAML 解析升级 | 代码级语义 |
| v4 | "异常"方向未定义 | 校验语义 |
| v5 | "净 m 方向"计算方法未定义 | 实现级语义 |

### 1.2 两个根因

1. **审查不做实现预演**。读到"比对净 m 方向与父类定性方向"，补上了 ↑/↓/异常/null 值域定义就过了——没有继续追"具体怎么算净方向"。
2. **修复是点状的，不做半径复查**。"异常"补了，但没问"计算方法呢？矛盾矩阵补完了非矛盾类型呢？"

## 二、核心模型

### 2.1 符号执行（Symbolic Execution）

审查 = 对规格文本做符号执行。核心动作是**写下每一步的输入类型和输出类型**。

**可操作定义**：读完一段规则后，不问"对不对"，问三个问题：
> 1. 这段话定义了什么数据？
> 2. 这个数据的类型是什么？
> 3. 谁消费它？

三个答不上来 → 不是"写得不好"，是"有缺口"。审查只报告缺口，不做设计决策。

### 2.2 限界验证（Bounded Verification）

借鉴 Alloy (Jackson 2012)：不验证无限情况。对当前步骤涉及的实体（3-4 个文件 × 值域枚举 × 分支条件）做叉乘完备性检查。

### 2.3 概念完整性

借鉴 Brooks《人月神话》：审查流程以"符号执行"为单一核心模型。所有检查规则都是这个模型的推论，不是散装清单。

## 三、启发式规则 H1-H6

从 md 自然语言中识别"含数据流动、值得 trace"的规则段落：

| # | 触发信号 | md 中的形态 | 抓取内容 |
|---|---------|------------|---------|
| **H1** | 跨文件引用 | YAML `父类: xxx`、`[显示名](路径)`、`参考 xxx.md §N` | 消费方文件路径、被引用字段 |
| **H2** | 枚举/类型定义 | 列表 `↑/↓/异常/null`、表格中值域列、YAML 字段的可选值 | 完整值域枚举、是否有 null/其他兜底 |
| **H3** | 数据变换 | 含"计算/求和/取最大值/比对/转换/映射/归一化"的段落 | 变换的输入→输出类型、中间步骤 |
| **H4** | 分支/条件 | "如果…则…"、"当…时…"、表格中不同行有不同处理逻辑 | 分支条件、所有分支是否覆盖完备 |
| **H5** | 管道衔接 | 编号步骤（Step 1→2→3）、"上述结果传入…"、"基于上一步的…" | 步骤间数据类型传递 |
| **H6** | 表格数据列 | ≥3 列的表格，列中含数值/类型字段/文件路径 | 每列类型、值域范围、null 处理 |

### 不触发

- 纯叙述/解释段落（"X 系统负责 Y 功能"——无数据流动）
- 纯设计意图/动机（"为什么选择 A 而不是 B"——无可 trace 结构）
- 已标记 `⚠️ 已废弃` 的段落
- 纯索引/目录列表

## 四、从标注到 Trace：H→9列的映射方法

每个 H 触发后，按以下策略填充 9 列 trace table：

| 触发 | 核心动作 | 填列顺序 |
|------|---------|---------|
| **H1** 跨文件引用 | 生成"引用连接行"——从被引用方到引用方 | 先填"输入·来源"（被引用文件+字段）→"变换"=引用解析 →"输出·类型"=引用方可用的数据形态 →"输出·消费者"=引用方中消费该数据的所有段落 |
| **H2** 枚举/类型定义 | 生成"类型定义行" | 先填"输出·类型"（完整值域枚举）→"变换"=定义值域 →"输入·来源"=该值域被定义的上下文 →"输出·消费者"=所有引用该值域的地方 |
| **H3** 数据变换 | 生成"变换行"——核心行类型 | 先填"变换"（原文中的变换描述）→ 从变换的上文推导"输入·类型" → 从变换的下文推导"输出·类型" → 两个类型都填上后再填"边界" |
| **H4** 分支/条件 | 有前置 H3 → 扩展 H3 的行，在"变换"列中追加分支枚举，在"边界"列中做分支×值域叉乘。无前置 H3 → 独立生成 trace 行，变换="条件分支"，输入·类型=分支变量类型，输出·类型=各分支结果类型的枚举。前置范围 = 同一 `###` 小节内 | 分支条件从原文提取 → 分支数 × 输入值域 → 逐组合检查覆盖 |
| **H5** 管道衔接 | 合并多步为一个 trace 行序列。管道步骤内同时触发 H4 → 先在 H3 行内展开分支（H4 扩展），再检查步骤间类型一致性（H5 衔接）。处理顺序：H3 → H4 → H5 | 严格检查每行的"输出·类型" = 下一行的"输入·类型" |
| **H6** 表格数据列 | 每列生成一个"类型定义行"（类似 H2）+ 行间关系生成"变换行"（类似 H3） | 同 H2 + H3 |

### 推导策略

- **"输入·类型"**：从原文找"从 X 中取"/"基于 X"/"X 包含"——X 就是输入。如 X 已在之前的 trace 行中定义过，复用其"输出·类型"。如 X 未定义过 → ❌ 缺口。
- **"输出·消费者"**：全文搜索引用该输出的段落（按字段名/变量名/步骤编号）。搜不到 → ⚠️ 输出未被消费。搜到多个 → 全部列出。
- **"边界"**：枚举所有异常输入（null/空/越界/类型不匹配），逐条检查是否有处理逻辑。

### 排序规则

解析阶段完毕后，按数据流依赖对文件排序：

| 优先级 | 依赖方向 | 判定依据 |
|--------|---------|---------|
| 1 | 父类 → 子类 | frontmatter `父类: X` → X.md 在子文件之前 |
| 2 | 被引用 → 引用方 | `[显示名](path)` → path 在引用方之前 |
| 3 | 数据文件 → 消费方 | `.json`/`.yaml` 被 md 引用 → 数据文件在前 |
| 4 | 方案 → 实现 | 方案.md 被审查建议.md 引用 → 方案在前 |

循环引用 → 保留原始输入顺序，标注"⚠️ 循环依赖"。无法判定 → 保留原始顺序，标注"依赖未解析，按输入顺序"。

### Trace 粒度

以"语义上独立的数据变换"为一行：

| 触发 | 拆成几行 |
|------|---------|
| H2 枚举/类型定义 | 1 行（变换 = "定义值域"） |
| H3 数据变换 | 每个独立的"计算/求和/比对/映射/转换" = 1 行 |
| H4 分支/条件 | 跟在所属的 H3 行内，不单独成行（在"变换"和"边界"列中展开分支） |
| H1 跨文件引用 | 每个引用目标 = 1 行（变换 = "引用解析"） |
| H6 表格 | 每列 = 1 行（类型定义），跨列计算 = 1 行 |

### 叉乘上限

N 种输入 × M 种分支 > 50 组合 → 抽样模式：
- 全边界组合（必查）：数值型取 min + max + null；枚举型取全部枚举值 + null；混合型取笛卡尔积。枚举无自然序时以声明顺序为首尾
- 随机抽样：剩余组合中取 10-15 组
- 总计 ≤ 30 组
- 标注：`⚠️ 抽样检查: N×M=X 种组合, 检查了 Y 组（含全边界）`

## 五、Trace Table 格式

9 列结构化表格：

| 列 | 追问的问题 | 空格的后果 |
|---|---|---|
| **#** | 步骤序号 | — |
| **规则** | 在追踪哪条规则？（格式: `文件名 §段落`） | 无法追溯 |
| **输入·来源** | 数据从哪个文件/字段/上一步来的？ | 不知道数据有没有定义 |
| **输入·类型** | 确切类型签名？值域枚举完整吗？（使用 §六 类型标签） | 值域漏洞 |
| **变换** | 这一步对数据做什么？ | 方法未定义 |
| **输出·类型** | 产出的确切类型？所有可能返回值列出 | 返回值不全 |
| **输出·消费者** | 谁在下一步消费这个输出？列出所有调用方 | 修了这里不知道影响谁 |
| **边界** | 空输入/极端值/类型不匹配时怎么处理？ | null 穿透 |
| **判定** | ✅完整 / ⚠️有疑点 / ❌有缺口。AI 代劳无脚本时标注覆盖深度：`✅(浅)` = 浅层检查通过，`⚠️(AI)` = 覆盖不完整 | 未验证 = 留空 |

## 六、md 简化类型系统

### 基础类型

| 标签 | 含义 | "已定义"标准 | md 典型形态 |
|------|------|------------|-----------|
| `枚举<T>` | 有限值域 | 列出所有合法值 + 是否有 null | `↑/↓/异常/null` |
| `数值` | 连续值 | 有下界 + 上界 + 单位（如有） | `m ∈ [0, 1.4]` |
| `引用<T>` | 指向其他文件/段落 | 目标存在 + 目标类型已知 | `父类: 奖赏系统障碍` |
| `文本` | 无约束字符串 | 有格式约束则注明，否则"无约束" | YAML 描述字段 |

### 复合类型

`List<枚举<T>>` `List<数值>` `Dict<枚举<K>, 数值>` `Optional<引用<T>>`

`枚举<是|否>` 等价于布尔类型，不单独建 `布尔` 标签，避免与枚举的判定规则重复。

### 判定规则

- `枚举<T>` 值域没列全 → ❌
- `数值` 缺上界或下界 → ⚠️
- `引用<T>` 目标不存在 → ❌。含段/锚点引用（`§N`）→ 段不存在即 ❌。含字段引用（YAML frontmatter）→ 字段不存在即 ❌
- `文本` 一般不做缺口判定（除非有显式格式约束）

## 七、停止条件

### 正常停止

1. **项目边界停**：数据源是项目外不可变的东西（YAML 规范、Python 标准库）。项目内非标准工具（自写的 parse 函数）要追进去。
2. **类型闭合停**：输入类型已定义 + 输出类型已定义 + 值域叉乘已覆盖 + 边界条件有处理。
3. **重复模式停**：与之前 trace 过的步骤同构，引用之前的 trace 结论。

### 不能停的信号

- 某步的输入/输出类型没写全
- 变换逻辑有"计算/求和/映射/比对"但没有具体方法
- 某步的输出没有列出所有消费者
- 某步的边界条件有空白

## 八、半径扩张机制

### v1 实现：强制列出消费者（不等状态变更）

任何 trace 行判定为 ❌ 或 ⚠️ 时，该行的"输出·消费者"列**必须**填写。消费者非空 → 自动进入"待复查清单"。

设计者修复缺口后，重新运行 `/review-plan`。对比两次输出的"缺口汇总"——消失的缺口 = 已修复，新出现的缺口 = 修复引入的新问题。

### 待复查清单

| 修复点 | 修复内容 | 受影响消费者 | 复查状态 |
|--------|---------|-------------|---------|
| Step N 输出类型新增 X | 值域从 {A,B} 扩为 {A,B,X} | Step M（`文件名`） | 待复查 / ✅已复查 |

### 变更追踪

```markdown
## 变更追踪（与上次 trace 对比）

| 上次缺口 | 本次状态 | 备注 |
|---------|---------|------|
| #3 净方向计算方法未定义 | ✅ 已修复 | 新增 _compute_net_direction 规格 |
```

第一次 trace 为空。后续由审查者手动对比或让 AI 读取上次 trace 输出做自动对比。

上次 trace 文件发现：glob `.scratch/review-trace-*-<文件名>.md`，按文件名时间戳排序取最新非本次文件。`--diff-against <file>` 可手动覆盖。

## 九、执行流程

```
/review-plan <file.md> [file2.md ...] [--pre-check <script_output>]
  │
  ├── 1. 解析阶段
  │   ├── 读取所有目标 md 文件
  │   ├── 如有 --pre-check → 解析为已验证基础层
  │   ├── 对跨文件引用（H1）→ 自动拉入被引用文件（深度 1 级, 上限 5 文件）
  │   └── 用 H1-H6 标注所有规则候选段落
  │
  ├── 2. 排序阶段
  │   └── 按数据流依赖排序（§四 排序规则）
  │
  ├── 3. Trace 阶段
  │   ├── 逐条填 9 列 trace table（§四 H→9列映射方法）
  │   ├── 每步做值域叉乘（上限 N×M>50 → 抽样）
  │   ├── 空白格 = 缺口 → 标记 ❌ 或 ⚠️
  │   └── 缺口产生时 → 填写"输出·消费者"→ 写入待复查清单
  │
  ├── 3.5. 交叉比对（如使用了 --pre-check）
  │   ├── Layer 2 trace 出的 ❌/⚠️ 与 Layer 1 覆盖声明取交集
  │   ├── 缺口落在 Layer 1 声称覆盖的区域内 → 追加标记 "⚠️ Layer 1 可能漏检（非抽查发现）"
  │   └── 缺口落在 Layer 1 覆盖范围外 → 正常标记，非 Layer 1 职责
  │
  ├── 4. Layer 1.5 抽查（如使用了 --pre-check）
  │   ├── 覆盖声明 = --pre-check 输入的"检查范围"段（见 §十 推荐格式）
  │   ├── 从覆盖声明中随机抽 3 项做独立验证
  │   ├── 不一致 → 追加 "⚠️ 前置脚本可能漏检"
  │   └── 退化路径：输入无检查范围段 → 标注 "⚠️ 无法确定覆盖范围，跳过抽查"
  │
  └── 5. 输出阶段
      ├── 写入 .scratch/review-trace-YYYY-MM-DD-HHMM-<文件名>.md
      └── 终端打印摘要（总行数 / ✅ / ⚠️ / ❌ / 待复查数）
```

### H1 自动拉入边界

- 深度: 1 级（只拉入直接引用，不递归）
- 上限: 5 个额外文件
- 循环引用: visited set 去重
- 超限: 标注 `⚠️ 引用文件超过拉入上限(5)，N 个文件未自动拉入: [...]`

## 十、前置输入与分层架构

### 分层模型

```
Layer 1: 确定性脚本
  检查: 格式/引用存在性/参数范围/结构一致性
  特性: 确定性（同输入→同输出）

Layer 1.5: AI 抽查
  从 Layer 1 的"通过"结论中随机独立验证
  不一致 → 标记 "⚠️ 前置脚本可能漏检"

Layer 2: AI 符号执行
  检查: 类型闭合/分支完备/数据流贯通
  前提: Layer 1 存在且完整。没有 Layer 1 → AI 从头 trace → 退化风险高
```

### --pre-check 参数

```
/review-plan <file> [--pre-check <text_or_file>]
```

通用机制，不绑定特定领域（不是只能传 `validate_disease.py` 输出）。调用方自行决定跑什么脚本、传什么输出。审查引擎将其标记为"已验证基础层"，trace 时跳过已验证项。不传则 AI 从头 trace（包括格式/引用/参数层），退化风险较高。

### --pre-check 推荐格式

脚本输出建议遵循以下结构，便于引擎可靠解析：

```
# <脚本名> — <一句话描述>
## 检查范围
- <检查类别1>：<覆盖说明>
- <检查类别2>：<覆盖说明>

## 结果
PASS  <check_id>  <描述>  [位置]
FAIL  <check_id>  <描述>  [位置]
WARN  <check_id>  <描述>  [位置]

## 汇总
N checks: X passed, Y failed, Z warnings
```

脚本不遵循此格式时 → AI 语义解析原始输出，标注 `⚠️ 前置输入格式非标准，解析可能不完整`。

## 十一、输出格式

写入 `.scratch/review-trace-YYYY-MM-DD-HHMM-<文件名>.md`（时间戳到分钟避免覆盖）：

```markdown
# Review Trace: <文件名>

> 审查日期: YYYY-MM-DD HH:MM
> 审查范围: <文件列表>
> 方法: 符号执行 + 限界验证（Alloy 方法论）
> 前置检查: <脚本名 + 摘要, 或 "无">

## 前置输入

- [x] {pre_check_label} — {pre_check_summary}（如适用）
- [x] Layer 1.5 抽查: K/N 项一致（如适用）
- [x] 被引用文件自动拉入: [file1](path), [file2](path)

## Trace Table

| # | 规则 | 输入·来源 | 输入·类型 | 变换 | 输出·类型 | 输出·消费者 | 边界 | 判定 |
|----|------|----------|----------|------|----------|------------|------|------|

## 缺口汇总
```

## 十二、与其他工具的分工

### 已有工具（可直接用作 --pre-check 前置输入）

### 计划中工具（不存在时 AI 代劳，退化风险：中-高）

| 工具 | 计划阶段 | AI 代劳时的覆盖深度 | 退化风险 |
|------|---------|-------------------|---------|
| `validate_cross_refs.py` | Grilling #16 阶段 2 | 仅检查显式 `[xxx](path)` 和 frontmatter `父类:` | 中 |

AI 代劳时在 trace table 中标注覆盖深度，不在结论中声称"全面检查"。

### 与 grilling 的关系

- `/review-plan` = 发现断层，产出缺口列表（批处理，不中断提问）
- `/grilling` = 对缺口做设计决策（交互式追问）
- trace table 中标注"建议 grilling"的缺口 → 创建 grilling issue

## 十三、审查范围策略

| 文件数 | 策略 |
|--------|------|
| 1-2 | 全 trace：每个 H3 触发都走完整 9 列 |
| 3-5 | 聚焦跨文件数据流：H1 + H5 优先，单文件内部快速扫描 |
| 6+ | 仅 H1 跨文件引用链：保证引用完整性，标注"未做单文件深度 trace" |

策略选择打印在输出摘要中，用户可在命令行覆盖。

文件数 = 用户显式传入的文件数。H1 自动拉入文件不参与策略判定，仅做引用完整性检查（H1 行）。

传入文件总行数 > 5000 → 自动降级为聚焦跨文件策略（H1+H5），输出中标注 `⚠️ 文件较大（N行），降级审查范围`。`--full` 可覆盖。

## 附录 A: Skill 自检信号

Skill 运行中应监控以下信号，触发时提示用户介入：

| 信号 | 触发条件 | 提示内容 |
|------|---------|---------|
| 类型分类退化 | 连续 ≥5 行"输入·类型"或"输出·类型"被标记为 ⚠️ 无法判定，且 AI 确认"文档写清楚了但我无法归类"（v1 AI 元认知判断；v2+ 考虑替换为客观启发式） | "类型标签体系可能覆盖不足，建议创建补充 Worked Example" |
| 叉乘频繁抽样 | 连续 ≥3 次叉乘触发抽样上限 | "该文件分支复杂度较高，建议拆分规则段落降低单行输入维度" |
| Layer 1.5 不一致 | 抽查发现 Layer 1 的"通过"结论与独立验证不符 | "前置脚本可能漏检，建议审查脚本逻辑或扩大抽查比例" |
| 拉入超限 | H1 拉入被引用文件连续超限（>5） | "该文档跨文件依赖较多，建议缩小审查范围或分批次审查" |
