具体语义我建议锁成：

```text
游戏日 D
│
├─ 上午（时段 1）
│    └─ 休息 → 下午
│
├─ 下午（时段 2）
│    └─ 休息 → 夜晚
│
└─ 夜晚（时段 3）
     └─ 休息 → D+1 日 · 上午
```

这里有一个细节需要**明确写进契约**：

### 「一天从醒来开始」与「第 3 次休息完成」其实是同一个边界

不要把“第 3 次休息”算成新一天的第一个时段。

更准确地说：

- `D / 上午`：当天开始；
- 上午休息 → `D / 下午`；
- 下午休息 → `D / 夜晚`；
- 夜晚休息完成 → `D+1 / 上午`，**同时触发一次游戏日推进**。

因此：

\[
D \rightarrow D+1
\]

发生在**夜晚结束、进入下一天上午的瞬间**。

### 两个重要的隔离也应该锁死

**1. 时段不是模拟动力学时间步。**

时段只服务于design/events/呈现层：

- NPC 调度
- 可访问性
- 风险表现
- 月光基线的弱/中/强呈现

不能因为“上午/下午/夜晚”而人为给动力学系统增加三个时间步。

**2. 月相推进只绑定游戏日，不绑定时段。**

即：

```text
游戏日推进一次
      ↓
λ 推进一步
      ↓
模拟时间接口映射
      ↓
E_c / E_th 等月相相关参数更新
```

而不是：

```text
上午 → λ 更新
下午 → λ 更新
夜晚 → λ 更新
```

后者会把现有三时段事件粒度错误地升级成动力学时间粒度。
