## 一、经典运动图与对齐-混合（motion graphs / registration curves）

> 问题：把一批互不相干的 clip 拼成一条连续长动作，靠什么机制？两条 clip 的接缝如何「对齐 + 混合」？——本条是「离散 clip 之间做过渡」的**原始范式**，也是本项目处境（2–3 条 clip、接缝有静态失配）在文献上的直系祖先。

### 1.1 运动图：把 clip 切成帧、按姿势相似度建图

- **模型**：运动图（motion graph）——把动作数据切成帧节点，节点间以「姿势相似度」连边，把动画合成问题化为**在有向图上搜索路径**；跨 clip 的过渡在图的边上生成（而非为每对 clip 手工制作过渡动画）。
- **来源**：Kovar L, Gleicher M, Pighin F. *Motion graphs*. ACM Transactions on Graphics, 21(3), 473–482, 2002. DOI 10.1145/566654.566605（Crossref 已核验：题名/作者/期刊/年份一致）。会议版 DOI 10.1145/566570.566605。URL：https://doi.org/10.1145/566654.566605
  - **状态**：📋 仅核验元数据。全文未直读（ACM 付费墙；作者站点镜像 `graphics.cs.wisc.edu/Papers/2002/KGP02/motiongraphs.pdf` 实测返回 404 HTML）。本综述**不**转述该文的具体算法细节。

### 1.2 注册曲线：把「对齐」这件事自动化（这是本项目真正在做的事的正式名称）

- **模型**：motion blending（运动混合）是把多条 clip 按**时变权重**合成新动作的通用操作；过渡（transitioning）与多目标插值都是它的实例。**注册曲线（registration curve）** 是一个自动构造的数据结构，它**自动确定输入动作之间关于「时间（timing）、局部坐标系（local coordinate frame）、约束状态（constraint states）」的关系**，从而扩大「不需要人工干预就能混合成功」的动作范围。
- **原文（✅ 已读开放全文 PDF）**：
  - 运动定义：`M(f) = (p_R(f), q_1...n(f))`——`p_R` = 根的全局位置，`q_i` = 第 i 个关节在其父坐标系中的朝向，每个参数向量 `M(f)` 称为一**帧（frame）**；`f` 为帧索引。混合 `B(t)` 由 N 条输入运动 `M_1…M_N` 与一个 **N 维权重函数 `w(t)`** 构造；`w_i = 1 @ t0` 且其余为 0 时退化为单条输入。
  - 摘要原文：「We introduce a novel data structure called a registration curve that expands the class of motions that can be successfully blended without manual input. Registration curves achieve this by automatically determining relationships involving the timing, local coordinate frame, and constraints of the input motions.」
  - 引言原文：「blending can be used to create seamless transitions between motions, allowing one to build lengthy, complicated motions out of simpler actions.」
  - 关键限制（引言原文，**对本项目最重要的一句**）：「While blending is a powerful tool, it will not produce realistic results unless the input motions are chosen with some care. The range of motions that can be successfully blended depends heavily on how much information about the motions is given to the algorithm. If nothing is known about the input other than the raw motion parameters (e.g., the root position and joint angles at each frame), then existing blending algorithms are reliable only if the motions are quite similar.」
- **来源**：Kovar L, Gleicher M. *Flexible Automatic Motion Blending with Registration Curves*. SCA 2003（Eurographics/SIGGRAPH Symposium on Computer Animation），The Eurographics Association, pp. 214–224. 开放全文条目页：https://diglib.eg.org/items/3e8f3a0d-0631-4913-8259-999774a54e49 （PDF 直链：https://diglib.eg.org/bitstreams/2f9fca81-a459-4385-a26b-d9e7c849386b/download ）
  - ⚠️ 该文 BibTeX 键为 `10.2312:SCA03/214-224`，但形如 `10.2312/SCA.SCA03.214-224` 的 DOI **在 doi.org 未能解析**（实测 404），ACM 侧也无对应 DOI（试查 DOI 均 404）→ 引用请用上面的 Eurographics DL 条目页/PDF 直链，**不要**写成 DOI 链接。

## 二、运动形变与约束对齐（motion warping / spacetime constraints）

> 问题：不改动画源数据，如何把一条已有动作「掰」到新的目标（位置/朝向/轨迹/接触点）？——这一条回答的是**「对齐」的一半**：给一条 clip 施加形变使其端点满足外部约束。任务书中的两位作者（Witkin / Popović）归属经核验正确。

- **Motion warping**：Witkin A, Popović Z. *Motion warping*. SIGGRAPH '95（Proceedings of the 22nd annual conference on Computer graphics and interactive techniques）. DOI **10.1145/218380.218422**（Crossref 已核验：题名、作者、会议、年份一致）。URL：https://doi.org/10.1145/218380.218422 —— 📋 元数据核验。
  - ⚠️ 常见误传的 DOI `10.1145/218380.218446` 经核验实为 Heeger & Bergen 的 *Pyramid-based texture analysis/synthesis*（同届会议），**不要用**。
- **Spacetime constraints（原始）**：Witkin A, Kass M. *Spacetime constraints*. SIGGRAPH '88. DOI 10.1145/54852.378507（Crossref 已核验）。URL：https://doi.org/10.1145/54852.378507 —— 📋 元数据核验。
- **Spacetime constraints（运动编辑形式）**：Gleicher M. *Motion editing with spacetime constraints*. I3D 1997. DOI 10.1145/253284.253321（Crossref 已核验）。URL：https://doi.org/10.1145/253284.253321 —— 📋 元数据核验。
- **Physically based motion transformation**：Popović Z, Witkin A. SIGGRAPH '99. DOI 10.1145/311535.311536（Crossref 已核验）。URL：https://doi.org/10.1145/311535.311536 —— 📋 元数据核验。
- **共性代价（工程含义，非引文）**：这一脉的产出是**离线求解**一条新动作曲线（或手工指定一段形变函数），代价是求解/调参，收益是「端点精确对齐」。它不解决「两条 clip 的静态姿势构型本来就不同」这件事，只把姿势搬到目标约束上。

## 三、运行时低开销过渡：inertialization / dead blending

> 问题：传统交叉淡化（crossfade）在过渡期间必须**同时求值**源状态与目标状态（动画开销翻倍）。有没有「不双重求值」的过渡法？——有，就是 inertialization（惯性化）；其出处经核实为 **GDC 2018**，且**已在商业引擎里产品化**（Unreal 内置；团结引擎官方 AnimGraph 内置）。

### 3.1 出处核实（任务书问「我记得来源是 GDC 演讲，请核实并给准确出处」）

- **GDC 2018 ✅**：Session「Inertialization: High-Performance Animation Transitions in 'Gears of War'」，Speaker：**David Bollo（Microsoft）**，Track/Format：**Programming / Lecture**，会议 **GDC 2018**（页面元数据 `'conferenceName': 'GDC 2018'`，session 1025331）。URL：https://gdcvault.com/play/1025331/
  - 官方摘要原文（✅ 页面直读）：「The traditional approach to animation transitions involves blending between the old source animation state and the new target animation state; however this can have a significant performance cost, because one must evaluate both the source and target animation states during a transition, effectively doubling the animation evaluation cost. For 'Gears of War 4', Microsoft eliminated these blended transitions altogether and chose to instead handle motion transitions as a post-process with a technique called "inertialization". … In this talk, David Bollo presents the mathematics behind Microsoft's inertialization technique, for both vector and quaternion values, and show how it can be easily introduced into an existing game engine.」
  - → 你的记忆**正确**：出处是 GDC 演讲，准确坐标为 **GDC 2018 / Programming 场 / David Bollo（Microsoft）**。
- **同源一手技术材料（含数学）✅**：Bollo D. *High Performance Animation in Gears of War 4*（Supplemental Material）. ACM SIGGRAPH '17 Talks, 2017. DOI 10.1145/3084363.3085069（Crossref 已核验：题名 *High performance animation in Gears of War 4*、会议 *ACM SIGGRAPH 2017 Talks*、2017）。PDF 直链（第一方 CDN，实测 200 / 441 KB）：https://cdn.gearsofwar.com/thecoalition/publications/SIGGRAPH%202017%20-%20High%20Performance%20Animation%20in%20Gears%20ofWar%204%20-%20Supplemental.pdf
  - PDF 原文（✅ 已读）：「Our Gears of War 4 motion transition method constructs a quintic polynomial … and velocity at the beginning of the transition and converges to zero by the end of the transition.」；「We choose to use a quintic polynomial both because it fits well with the experimentally observed motion of humans [Flash and Hogan 1985], but also because it gives us the ability to freely control the initial acceleration at the start of the transition. We choose an initial acceleration of zero except in situations with a large negative initial velocity, in which case we adjust the initial acceleration in order to ensure that the curve does not overshoot (i.e.: to ensure that x ≥ 0 for all t between 0 and t₁).」
  - ⚠️ 诚实标注：该补充材料全文中**未出现 "inertialization" 一词**（`grep -c inertial` = 0）。**命名出自 GDC 2018 演讲**；SIGGRAPH 2017 材料给的是同一技术族的过渡曲线数学（五次多项式 / 初始加速度为零 / 防过冲）。同一作者（David Bollo, Microsoft），但不要写成「SIGGRAPH 2017 那篇叫 inertialization」。

### 3.2 生产级落地（一）：Unreal Engine 的两种惯性混合节点

- **✅ 已核实（Epic 官方文档原文 HTML 直读）**：Unreal Engine 官方「Animation Blueprint Blend Nodes」页给出两个节点，原文写明两者是**两种不同的惯性混合（inertial blending）**做法：
  - 原文：「Inertialization — Inertial blending is a high-performance alternative to traditional animation crossfading that produces natural transitions as a post-process. **Once an inertial blend is activated, the source pose is no longer evaluated at all.**」
  - 原文：「To use inertial blending, you can add an **Inertialization** or **Dead Blending** node to the AnimGraph after the source animation blend you want inertially blended. Each node approaches inertial blending using different methods.」
  - URL：https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine （API 侧同类节点：`FAnimNode_Inertialization` / `FAnimNode_DeadBlending`）
  - → **「inertialization / dead blending」这一对术语在 Unreal 中已是引擎内置节点**，属「今天就能在生产里用」的一档。

### 3.3 生产级落地（二）：团结引擎（Unity 中国版）官方 AnimGraph 也有这两个节点

- **✅ 已核实（官方中文手册原文直读）**：**团结引擎 1.10 手册**的 AnimGraph（动画节点编辑器）「过渡混合节点」分类下**同时提供 Inertialization 与 Dead Blending 两个节点**：
  - **Inertialization 节点**原文：「该节点记录动画切换前后的姿态差异，在混合期间使用**多项式衰减函数**逐渐消除差异…」「惯性化混合仅需记录姿态差异并衰减，**无需同时评估两个动画片段**，因此过渡期间性能开销更低。」「节点使用**五次多项式函数**衰减姿态差异」——特性表列出「平滑性 / **防过冲** / **速度感知**」。性能数据原文：「在 **100 个同屏角色**频繁切换动画状态的场景中，过渡阶段性能平均提升约 **4.5%**，非过渡阶段性能损耗约 **0.4%**。」触发方式原文：在状态机过渡的 Inspector 里把 **Blend Mode 设为 Inertialization**，并在输出前接一个 Inertialization 节点接收图内所有惯性化过渡请求。另有「逐骨骼持续时间遮罩（Per-Bone Duration Mask）」与 `AnimationClipPlayable` 接口。
  - **Dead Blending 节点**原文：「该节点在动画切换时捕获源姿态与速度，使用**隐式指数衰减（Implicit Exponential Decay）**对每个骨骼通道进行速度感知的外推，并通过**交叉混合（Cross-fade）**平滑过渡到目标姿态…**与 Inertialization 使用多项式衰减不同**，Dead Blending 使用基于速度的指数衰减外推，能更自然地延续源动画的运动趋势」。含**启发式半衰期**（Half Life Base / Min / Max，按通道运动速度自动调整）、**速度钳制**（Max Translation Velocity m/s、Max Rotation Angular Velocity deg/s）、逐骨骼遮罩、缩放插值模式。
  - URL：https://docs.unity.cn/cn/tuanjiemanual/Manual/AnimGraphAnimationNodeInertialization.html ・ https://docs.unity.cn/cn/tuanjiemanual/Manual/AnimGraphAnimationNodeDeadBlending.html
  - → **重要结论**：**主线 Unity（6000.x）文档中检索不到** inertialization / dead blending 的官方节点（见 §7.10 与缺口清单 11）；但 **Unity 中国版引擎的官方 AnimGraph 已经有正式实现与文档**。这说明该技术已「产品化到能进引擎官方体系」，同时也说明**主线 Unity 至今没有把它做进 `Animator`**——本项目若要用，只能引第三方（§3.4）或自写（Playables）。

## 四、Motion Matching：GDC 演讲 + 开源实现核验

> 问题：能否不要过渡动画、不要状态机，直接「每帧在 mocap 数据库里找最匹配当前姿势与未来意图的帧」？——能，但它的前提是**一个足够大的数据库**。

### 4.1 源头演讲（✅ 出处与元数据已核实）

- **GDC 2016**：Session「Motion Matching and The Road to Next-Gen Animation」，Speaker：**Simon Clavet（Ubisoft Montreal）**，Track/Format：**Programming / Lecture**，会议 **GDC 2016**（页面元数据 `'conferenceName': 'GDC 2016'`）。URL：https://www.gdcvault.com/play/1023280/Motion-Matching-and-The-Road
  - 官方摘要原文（✅ 页面直读，本综述最有用的一个数据点）：「For navigation, they don't have to manually organize transition animations like starts, stops, and turns. **They just capture 5 or 10 minutes of a person running around and import it directly into the engine.** At runtime, they continuously find the frame in the mocap database that simultaneously matches the current pose and the desired future plan, and transition with a small blend time to this other place in the data.」
  - → 数据量口径：**5–10 分钟连续 mocap**（且只是 locomotion 的导航需求）；过渡做法是「**small blend time**」——motion matching 自己也要混合，只是混合窗很短。

## 七、Unity 引擎自身能力（逐条官方原文核验）

> 本节按任务要求**优先用官方文档原文**核实，全部为 ✅ 已读原文（6000.0 与 6000.5 双版本直读；文本一致者合并标注；关键默认值另与 Unity C# 参考源码交叉核对）。

### 7.1 `Animator.CrossFade` — 精确语义（官方原文）

- **签名与默认值（6000.5 官方页原文）**：
  - `public void CrossFade(string stateName, float normalizedTransitionDuration, int layer = -1, float normalizedTimeOffset = float.NegativeInfinity, float normalizedTransitionTime = 0.0f);`
  - `public void CrossFade(int stateHashName, float normalizedTransitionDuration, int layer = -1, float normalizedTimeOffset = 0.0f, float normalizedTransitionTime = 0.0f);`
  - ✅ 已与 Unity C# 参考源码交叉核对（`UnityCsReference` → `Modules/Animation/ScriptBindings/Animator.bindings.cs`）：string 版特性为 `[DefaultValue("float.NegativeInfinity")] float normalizedTimeOffset`，int 版为 `[DefaultValue("0.0f")]` → **两个重载的默认 offset 确实不同，不是文档笔误。**
- **参数逐字**：
  - `normalizedTransitionDuration` — 「The duration of the transition (normalized).」
  - `normalizedTimeOffset` — 「**The time of the state (normalized).**」
  - `normalizedTransitionTime` — 「The time of the transition (normalized).」
- **描述逐字**：「Creates a crossfade from the current state to any other state using normalized times.」及「When you specify a state name, or the string used to generate a hash, it should include the name of the parent layer. For example, if you have a Run state in the Base Layer, the name is Base Layer.Run.」（另有「用 stateName 时内部会调 `Animator.StringToHash`」的性能提示）
- URL：https://docs.unity3d.com/6000.5/Documentation/ScriptReference/Animator.CrossFade.html （6000.0 文本逐字相同）
- ❌ **未能核实（对本项目最关键的一条）**：官方文档**没有**说明 `normalizedTimeOffset` 对**非循环 clip** 是否取模、超出 `[0,1]` 如何解释、以及 `float.NegativeInfinity` 这个默认值的语义。文档给的就是上面那句「The time of the state (normalized).」——**不要把「取模 / 钳制」当成文档结论**。

### 7.2 `Animator.CrossFadeInFixedTime`（秒制版本，可用于时长差一个数量级的 clip 对）

- 参数逐字：`fixedTransitionDuration` — 「The duration of the transition (**in seconds**).」；`fixedTimeOffset` — 「The time of the state (**in seconds**).」；`normalizedTransitionTime` — 「The time of the transition (normalized).」
- 描述逐字：「Creates a crossfade from the current state to any other state using times in seconds.」
- 注意：**此处两个重载的默认值一致**（`0.0f`）；`normalizedTransitionTime` 仍是归一化量（过渡曲线的时间分布，与时长单位无关）。
- 与手册的对应关系（Manual `class-Transition` 原文）：「Fixed Duration — If the Fixed Duration box is checked, the transition time is interpreted in seconds. If the Fixed Duration box is not checked, the transition time is interpreted as a fraction of the normalized time of the source state.」
- URL：https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animator.CrossFadeInFixedTime.html ・ https://docs.unity3d.com/6000.0/Documentation/Manual/class-Transition.html

### 7.3 `Animator.Play` — `normalizedTime` 的官方解释（任务书问的关键点）

- 参数逐字：`normalizedTime` — 「**The time offset between zero and one.**」；`stateNameHash` — 「The state hash name. **If stateNameHash is 0, it changes the current state time.**」
- 描述逐字（**逐句**）：「The normalizedTime parameter varies between 0 and 1. If this parameter is left at zero then Play will operate as expected. A different starting point can be given. An example could be normalizedTime set to 0.5, which means the animation starts halfway through. If the transition from one state switches to another, it may or may not be blended. If the transition starts at 0.75 it will be blended with the other state. **If no transition is set up then Play will continue to 1.0 with no changes.**」
- 默认值：`float normalizedTime = float.NegativeInfinity`（6000.0 / 6000.5 文档与 C# 源码一致）。
- → `Play` 的起始偏移**被官方限定在 `[0,1]`**（`1.0` = clip 末尾）——这是官方文档中**唯一**明确「从尾部进入」的手段；而「`stateNameHash` 为 0 时改变当前状态时间」是一条非显然的官方后门。
- URL：https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animator.Play.html （6000.5 逐字相同）

### 7.4 循环性从哪来：状态 / clip 导入设置 / `AnimatorStateInfo`

- `AnimatorStateInfo.loop` 逐字：「Is the state looping. **All animations in the state must be looping.**」
- `AnimatorStateInfo.normalizedTime` 逐字：「The normalized time is a progression ratio. **The integer part is the number of times the State has looped.** The fractional part is a percentage (0-1) that represents the progress of the current loop. For example, a normalized time of 2.5 means that the State has looped twice (2) and has progressed halfway (50% or .5) through its third loop.」
  - → **官方从未承诺 `normalizedTime` 被钳制在 `[0,1]`**——官方自己给的例子就是 2.5。**因此不能用它判断「非循环状态是否已播完」。**
- `AnimatorStateInfo.length` 逐字：「Current duration of the state. In seconds. Can vary when the State contains a Blend Tree.」
- `ModelImporterClipAnimation.loopTime` 逐字：「**Enable to make the clip loop.**」 → 循环性由 **clip 导入设置**决定（`.fbx` 的 Loop Time），状态只是继承它。
- **推论（明确标注为推论，非官方原文）**：既然「归一化时间的整数部分 = 状态已循环的次数」，而「状态只有在其中所有动画都循环时才标记为循环」，那么**非循环状态不存在「第 n 次循环」可计**；官方文档中**没有**任何关于非循环 clip 归一化时间取模的表述。
- URL：https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AnimatorStateInfo-loop.html ・ https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AnimatorStateInfo-normalizedTime.html ・ https://docs.unity3d.com/6000.0/Documentation/ScriptReference/ModelImporterClipAnimation-loopTime.html

### 7.5 负 `AnimatorState.speed` 的「进入行为」

- `Animations.AnimatorState.speed` 逐字（**全文**）：「The default speed of the motion. A speed of 1.0 plays the animation at its original speed. **A speed of -1.0 plays the animation backwards.** A speed between 0.0 and 1.0 plays the animation forwards and slower. A speed greater than 1.0 plays the animation forwards and faster. For example, a speed of 2.0 plays the animation twice its original speed while a speed of 0.5 plays the animation at half its original speed.」
  - 路径提示：`ScriptReference/AnimatorState-speed.html` 已 404，现路径带命名空间前缀 `Animations.`。
- 手册 `class-State` 的 `Speed` 行逐字：「The default speed of the motion for this state. Enable Parameter to modify the speed with a custom value from a script.」
- URL：https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.AnimatorState-speed.html ・ https://docs.unity3d.com/6000.0/Documentation/Manual/class-State.html
- ❌ **未能核实（重要）**：官方文档**完全没有**描述负 speed 的**进入行为**——既没说「进入状态时从末帧开始」，也没说它与 `normalizedTimeOffset` / `Cycle Offset` 如何相互作用，更没有非循环状态下的时间钳制规定。「负 speed → 从末尾倒放」是**社区经验，不是文档化语义**。这一条**必须靠 Play 实测**确定。
- 相关（✅ 手册原文；注意它讲的是 **transition 的 Exit Time**，不是 CrossFade 的 offset）：
  - `class-Transition`：「Exit Time — … This is represented in normalized time (for example, an exit time of 0.75 means that on the first frame where 75% of the animation has played, the Exit Time condition is true). On the next frame, the condition is false. **For looped animations, transitions with exit times smaller than 1 are evaluated every loop** … Transitions with an Exit Time greater than 1 are evaluated only once, so they can be used to exit at a specific time after a fixed number of loops. For example, a transition with an exit time of 3.5 are evaluated once, after three and a half loops.」
  - `class-State`：「Cycle Offset — **The offset added to the state time of the motion. This offset doesn't affect the Motion Time.** Enable Parameter to specify the Cycle Offset from a script.」；「Foot IK — This property only applies to states with humanoid animation. Enable to respect Foot IK for this state.」
  - `class-Transition` 的 Interruption：「Interruption Source — Use this to control the circumstances under which this transition might be interrupted.」+「Ordered Interruption — Determines whether the current transition can be interrupted by other transitions independently of their order.」

### 7.6 `Animator.MatchTarget` / `SetTarget`（跨 clip 对齐的官方 API）

- **`MatchTarget` 官方原文（✅ 全文直读，含 4 条硬限制）**：
  - 「Automatically adjust the GameObject position and rotation. Adjust the GameObject position and rotation so that the AvatarTarget reaches the matchPosition when the current state is at the specified progress.」
  - **「Target matching only works on the base layer (index 0).」**
  - 「You can only queue one match target at a time and you must wait for the first one to finish, otherwise your target matching will be discarded.」
  - 「If you call a MatchTarget with a start time lower than the clip's normalized time and the clip can loop, MatchTarget will adjust the time to match the next clip loop. For example, start time= 0.2 normalized time = 0.3, start time will be 1.2.」
  - **「Animator.applyRootMotion must be enabled for MatchTarget to take effect.」**
  - 参数逐字：`startNormalizedTime`「Start time within the animation clip (0 - beginning of clip, 1 - end of clip).」；`targetNormalizedTime`「End time within the animation clip (0 - beginning of clip, 1 - end of clip), **values greater than 1 can be set to trigger a match after a certain number of loops. Ex: 2.3 means at 30% of 2nd loop.**」；`completeMatch`「Allows you to specify what should happen if the MatchTarget function is interrupted…」
  - URL：https://docs.unity3d.com/6000.5/Documentation/ScriptReference/Animator.MatchTarget.html
  - ⚠️ **对本项目的直接后果**：本项目当前口径是 `applyRootMotion = false`（动作库规格 §四·乙），而 MatchTarget 明确要求 **applyRootMotion 必须开启**才生效 → **在本项目现口径下 `MatchTarget` 不可用**（除非临时开启 root motion，而那会与「位移由 CharacterController 承载」的口径冲突）。另：它**不是过渡方案**，是「让指定部位在指定进程到达指定位姿」的自动 root 调整，且只作用于 base layer、同一时刻只能排队一个。
- **`SetTarget` 官方原文**：「Sets an AvatarTarget and a targetNormalizedTime for the current state. Once the frame is evaluated, use **Animator.targetPosition** and **Animator.targetRotation** to query the position and rotation.」
  - URL：https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animator.SetTarget.html
  - → 这是**读**目标姿势的查询接口（不产生过渡、不要求 root motion），用途恰好对应本项目的真实需求：**在指定归一化时间点取某骨位/根位，量出两条 clip 的姿势基准差**（0.338 m / 23–40 mm 这类读数），再用一次性偏移补偿，而不是让引擎替你对齐。

### 7.8 Root Motion 参考系 / 「Bake Into Pose」的官方表述

- 手册「How Root Motion works」逐字：「The Root Transform is a projection on the Y plane of the Body Transform and is computed at runtime. **At every frame, a change in the Root Transform is computed.** This change in transform is then applied to the Game Object to make it move.」；「The Animation Clip Editor settings - Root Transform Rotation, Root Transform Position (Y) and Root Transform Position (XZ) - let you control the Root Transform projection from the Body Transform. … which is known as **Baked into Pose**.」
- **Root Transform Position (Y) → Bake Into Pose 逐字**：「The Y component of the motion will stay on the Body Transform (Pose). The Y component of the Root Transform will be constant and **Delta Root Position Y will be 0**. This means that this clip won't change the Game Object Height. Again you have a Green Light telling you that a clip is a good candidate for baking Y motion into pose. Most of the AnimationClips will enable this setting.」
- `ModelImporterClipAnimation.lockRootHeightY` 逐字：「Enable to make vertical root motion be baked into the movement of the bones. Disable to make vertical root motion be stored as root motion.」
- URL：https://docs.unity3d.com/6000.0/Documentation/Manual/RootMotion.html ・ https://docs.unity3d.com/6000.0/Documentation/ScriptReference/ModelImporterClipAnimation-lockRootHeightY.html
- ❌ **未能核实（重要）**：官方手册**没有**一句「root motion 以各 clip 自身首帧为参考系」。手册只说「每帧计算 Root Transform 的变化量并施加到 GameObject」，以及 Bake Into Pose 时「Delta Root Position Y will be 0」。→ 本项目「各 clip 首帧即参考系 → 两条 clip 姿势基准差 0.337 m / 接缝不连续 0.338 m」这一条**是本项目的实测结论，不是文档陈述**；文档能背书的只是**修法**（Y 烘进姿势可让该 clip 不改变 GameObject 高度）。

### 7.9 Playables API（自己写过渡的官方底座）

- 手册逐字：「The Playables API provides a way to create tools, effects or other gameplay mechanisms by organizing and evaluating data sources in a tree-like structure known as the **PlayableGraph**. The PlayableGraph allows you to **mix, blend, and modify multiple data sources**, and play them through a single output.」；「The animation system already has a graph editing tool, it's a state machine system that is restricted to playing animation. The Playables API is designed to be more flexible and to support other systems.」
- 可核实的相关类型（页面均实测 200）：`AnimatorControllerPlayable.CrossFade`、`AnimationMixerPlayable`、`AnimationScriptPlayable`（后者用于自定义动画 Job——**若真要自己实现 inertialization，入口在这里**）。
- URL：https://docs.unity3d.com/6000.0/Documentation/Manual/Playables.html ・ https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.AnimatorControllerPlayable.CrossFade.html ・ https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.AnimationMixerPlayable.html ・ https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.AnimationScriptPlayable.html

### 7.10 `com.unity.animation.rigging` 是否提供 inertialization？

- **✅ 已核实（官方包文档原文）**：Animation Rigging **1.3.1** 的全部内置约束（原文「The Animation Rigging package includes the following predefined constraints that you can use to define your Animation rigs」）为：Blend Constraint ・ Chain IK Constraint ・ **Damped Transform** ・ Multi-Aim Constraint ・ Multi-Parent Constraint ・ Multi-Position Constraint ・ Multi-Referential Constraint ・ Multi-Rotation Constraint ・ Override Transform ・ Twist Chain Constraint ・ Twist Correction ・ Two Bone IK Constraint。
- 包自述定位（原文）：「Use Animation Rigging to create and organize animation rigs, or sets of constraints for adding procedural motion to animated objects. Examples include: Deformation rigs…; World Interaction rigs (sets of IK and Aim constraints)…」
- → 包内**没有** inertialization 或「过渡/惯性混合」类节点；与「平滑跟随」最接近的是 **Damped Transform**（弹簧阻尼跟随）。包另有「Bidirectional Motion Transfer」工作流。官方正文（主线 6000.x）也**未检索到** inertialization / dead blending 节点（对照 §3.3：团结引擎有）。
- URL：https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/index.html ・ https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/TableOfContents.html ・ https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/ConstraintComponents.html
- ❌ 说明：这是**基于官方文档清单的否定性核验**（清单里没有、检索不到），不等于 Unity 运行时内部不存在任何类似平滑机制。

## 八、判断 A：研究原型 vs 生产可用

> 三条判据：**需要训练数据/GPU 吗？能在 Unity 运行时跑吗？有可用开源实现吗？**

| 技术 | 需要训练数据 / GPU | 能在 Unity 运行时跑 | 有可用开源实现 | 判决 |
|---|---|---|---|---|
| 运动图 + 注册曲线（§一） | 不需要训练；需要**一批**可比的 clip | 可（纯几何/插值算法，C# 可实现） | 无权威官方实现；概念可自实现 | **有生产历史的经典方法**（2002–2003 量产于游戏），但收益随 clip 数量增长——clip 极少时收益趋零 |
| Motion warping / spacetime（§二） | 不需要训练；spacetime 需**离线求解** | 形变函数可运行时求值；完整 spacetime 求解不适合运行时 | 无主流开源 | **离线编辑工具**一类，不是运行时过渡方案 |
| inertialization / dead blending（§三） | 不需要训练数据；不需要 GPU | **可**（纯数学后处理：向量 + 四元数五次曲线 / 指数衰减） | ✅ 有：Unreal 引擎内置节点；**团结引擎 AnimGraph 内置节点**；Unity 主线第三方 2 个（BSD-3 / MIT，均非官方） | **今天就能在生产里用**——**但 Unity 主线需第三方或自写** |
| Motion Matching（§四） | **需要大量连续 mocap**（GDC 原文口径 5–10 分钟起；特征/轨迹/标注要手工或半自动） | 可（C# 实现存在，Unity 6+） | ✅ 有（orangeduck/Motion-Matching：C / MIT；JLPM22/MotionMatching：C# / MIT，活跃） | **生产可用，但前置成本高**；Unity 官方无内置（Kinematica 已退出官方文档） |

## 九、判断 B：比例性——本项目该用什么、明确否掉什么

> 本节的输入是**实测数据**（本项目 ActionLab 探针与其规格记录，见 `design/presentation/动作库规格.md` §二 修正块 / §四·乙 / §七，路径存在、本次已读）：Unity 6000.5.2f1；1.64 m Humanoid；52 个语义骨位（`HumanBodyBones`）、完整 `mixamorig` 骨架 65 骨；动作来源 Mixamo Humanoid，**只有 2–3 条** clip（坐下 / 起身 / 坐姿待机）；架构 = **离散状态机 + 运行时 `CrossFade`（零参数、零 transition）**。

### 9.1 量级对照表（这是判据本体）

| 已知失配 | 量级 | 性质 | 恰当工具箱 |
|---|---|---|---|

| 过渡窗口 | fade **0.06–0.15 s**（规格 §七，**秒制**） | 时间域不连续 | `CrossFadeInFixedTime`（秒制；`CrossFade` 是比例，见上） |

### 9.2 明确否掉（杀鸡用牛刀）

1. **Motion Matching** —— 其数据前置条件是**5–10 分钟连续 mocap**（GDC 2016 官方摘要原文，§4.1），本项目只有 **2–3 条 clip（数十秒量级）**，差 1–2 个数量级；且它解决的是「从数据库里挑下一帧」，而本项目的问题是「两条 clip 的端点静态失配」。**本项目没有「挑哪一帧」的自由度——总共就两三条路可走**；在 3 个候选里做最近邻检索会退化为既有状态机，只是把显式 transition 换成隐式特征匹配。另注：Unity 自家 Kinematica 这条路线已不在 6000.x 官方文档中（§4.2）。
2. **所有学习型方法（PFNN / MANN / NSM / Learned Motion Matching / in-betweening）** —— 四条同时出局：(a) 训练数据量：本项目 clip 数不足以训练任何模型；(b) **许可**：AI4Animation README 明确「not freely available for commercial use or redistribution」，LAFAN1 为 **CC BY-NC-ND 4.0**（禁止商用 + **禁止演绎**），PFNN 复现为「academic and non-commercial」（§5.2）；(c) **控制信号为零**：这些方法的输入是数秒历史帧 + 未来轨迹/转向速度/地形，本项目是 3 个离散状态、零 Animator 参数，没有可喂给网络的连续控制量；(d) 它们的目标是**生成**新动作，而本项目的 149 mm / 17.6° 是**静态构型差**——生成模型只会给出「第三条腿」，不会比足 IK 更对。
3. **spacetime constraints 类离线求解** —— 需要求解器与调参，收益（端点精确对齐）本项目用「Y 烘入 + 一次性 offset」已达成（0.0177 m）。
4. **`Animator.MatchTarget`** —— 工程上不可用（当前口径）：官方原文明确「**Animator.applyRootMotion must be enabled for MatchTarget to take effect**」（§7.6），而本项目口径是 `applyRootMotion = false`。**要用它就得改位移口径，代价大于收益。**

### 9.3 该用的「标准工具箱」（逐件给依据）

1. **对齐（align）：端点/基准偏移补偿 + 用 `Animator.SetTarget` 把偏差变成读数** —— 这是本项目已有成效最大的一步（0.338 → 0.0177 m）。文献依据：注册曲线论文把混合的自动化归结为「时间 + 局部坐标系 + 约束」三类关系的自动确定（Kovar & Gleicher 2003，§1.2）——本项目手工做掉的正是其中的「局部坐标系」这一项；该文同时提醒「输入动作选得不够相似时，混合算法不可靠」，这正是本项目 149 mm / 17.6° 处境。官方 API 依据：`Animator.SetTarget` + `targetPosition` / `targetRotation`（§7.6）**可在不依赖 root motion 的前提下读出指定归一化时间的姿势**，把「基准差」变成读数而不是观感。
2. **短窗混合（blend）：现成的 `Animator.CrossFade`（必要时 `CrossFadeInFixedTime`）** —— 官方语义见 §7.1 / §7.2；本项目 fade 0.06–0.15 s 已在文献口径内（motion matching 的过渡也只是「small blend time」，§4.1）。这一件**不需要新东西**：把残留 7.2 mm 髋高差、17.6° 膝角差中属于「时间不连续」的部分摊进过渡窗即可。⚠️ 时长差一个数量级的 clip 对（坐下 vs 坐姿待机）建议用**秒制**的 `CrossFadeInFixedTime`：`CrossFade` 的时长是「源状态归一化时长的比例」，在短 clip 上会得到极短的过渡。
3. **足部接触修正：足 IK** —— 已落地（`FootGroundingIK.cs`：`Animator.SetIKPosition` + `OnAnimatorIK` + IK Pass）。文献谱系：footskate cleanup（Kovar/Schreiner/Gleicher 2002，§1.3）。官方侧的等价自动化开关：`Animator.stabilizeFeet`（原文即「Automatic stabilization of feet during **transition and blending**」，§7.7）——**值得实测一次**，看它能否替代/补强自写足 IK；Animation Rigging 的 Two Bone IK / Chain IK 属同一工具箱（§7.10）。
4. **inertialization 式过渡（可选，非必需）** —— 适用场景是「想缩短 fade、又不想出现速度不连续」。出处：GDC 2018 David Bollo（§3.1）+ SIGGRAPH 2017 补充材料的五次多项式曲线（初始加速度为零、防过冲）+ 引擎级实现（Unreal 内置；团结引擎 AnimGraph 内置；Unity 主线第三方 2 个）（§3.2–§3.4）。**本项目的判决：优先级最低**——它优化的是「过渡期的双重求值开销」与「速度连续性」，而本项目 2–3 条 clip、fade 0.1 s 量级的开销可忽略（团结引擎官方性能数据也只是 100 个同屏角色频繁切换时过渡阶段约 +4.5%）；只有当你把 fade 压到 ~0（瞬切）并观察到肩/膝的「顿挫」时才值得上。
5. **静态姿势构型差（膝角 17.6°、踝 149 mm）：换 clip 或足 IK 兜底，不要指望任何混合算法** —— 这是本综述最想强调的一条判断：**混合（blending）处理的是「时间轴上的不连续」，不是「空间上的静态失配」。**把两条坐姿按权重平均，得到的是一条「半坐不坐」的腿（且大概率穿地），而正确解已经在项目里：足 IK（已把坐姿足底 −60.0 / −9.1 mm 修到 +2.4 / +1.0 mm，规格 §四·乙 实测），或者去换一条与坐面高匹配的 clip。
6. **工程约束（非文献技术，但最该补的一件）：把过渡质量固化为数值断言** —— 本项目量级下「过渡质量」的全部可观测量就是已实测的三个数：**接缝距离、足底陷入量、站立端高度差**。任何新方案（包括上面第 4 件）必须先证明**不劣化**这三个数，否则不予采纳；这条同时是拒绝 motion matching / 神经方案的可执行依据。
7. **需要倒放回退时，不要用「负 speed + offset」**（§7.5：官方对负 speed 的进入时间与非循环状态的时间钳制**全部未定义**，「负 speed 会从末尾倒放」是社区经验）。改用：(a) 准备一条**真正倒放的 clip**，用正向 `Play` / `CrossFade` 驱动；(b) `Animator.Play(hash, layer, normalizedTime)`（官方限定 `0~1`）显式指定起点（§7.3）；(c) `Animator.SetTarget` 采样后自行插值（§7.6）。**另：判断「状态是否已播完」不可用 `normalizedTime`**——非循环状态下官方从未承诺它封顶在 1（§7.4）。

**一句话结论**：在这个量级（2–3 条 clip、接缝 17.7 mm、静态构型差 149 mm / 17.6°、fade 0.1 s）上，**motion matching 与任何神经网络方案都不合理**——它们的数据前提比本项目的整个动作库大 1–2 个数量级，许可上对商业项目不可用；正确做法是**「对齐 + 短窗 `CrossFade` + 足 IK」三件套**（前两件已有成效，第三件已落地），inertialization 仅作为「把 fade 压到接近零」时的可选补丁。

- **Unity 侧**：直接抓取 `docs.unity3d.com` 页面（6000.0 与 6000.5 双版本；ScriptReference 与 Manual 均有），必要时与 **Unity C# 参考源码**（`Unity-Technologies/UnityCsReference` → `Modules/Animation/ScriptBindings/Animator.bindings.cs`）交叉核对默认值；Animation Rigging 取 1.3.1 包文档；团结引擎取 `docs.unity.cn` 手册页。
- **论文侧**：**Crossref API**（`api.crossref.org/works/{DOI}` 与 `bibliographic` 检索）逐条核验题名/作者/会议或期刊/年份/DOI 一致性；arXiv 侧用 **arXiv API**（`export.arxiv.org/api/query`）核验条目 ID、题名、提交日期；开放 PDF 用 `pdftotext` 提取正文逐句读（注册曲线全文、GoW SIGGRAPH 2017 补充材料）。
- **演讲侧**：GDC Vault 页面元数据（`conferenceName` / `sessionTrack` / `sessionFormat` / Speaker / Company）与官方摘要原文直读。

**❌ 未能核实（不得当结论用）**：

1. **非循环 clip 的 `normalizedTimeOffset` 是否取模** —— 官方文档只写「The time of the state (normalized).」（§7.1）；`Animator.Play` 只写「varies between 0 and 1」；`AnimatorStateInfo.normalizedTime` 只写「整数部分是已循环次数」（§7.4）。**没有任何一句谈非循环情况下的取模/钳制**。只能由 Play 实测确定。
2. **负 `AnimatorState.speed` 的「进入行为」** —— 官方只说「A speed of -1.0 plays the animation backwards」，**未描述从哪一帧进入、与 `Cycle Offset` / `normalizedTimeOffset` 如何交互**（§7.5）。任何「负 speed 自动从末尾倒放」的表述均为社区经验。
3. **「root motion 以各 clip 自身首帧为参考系」** —— 官方手册无此表述；本项目这一结论来自实测（0.338 m / 0.337 m），不是文档（§7.8）。
4. **`Animator.CrossFade` 两个重载默认 offset 不一致的官方解释** —— 事实已核实（string 版 `float.NegativeInfinity`，int 版 `0.0f`，文档与源码一致），但**官方没有说明为什么不同、以及 `NegativeInfinity` 的确切语义**。
5. **Motion graphs 全文** —— ACM 付费墙，作者站点镜像 URL 实测 404（§1.1）；该文的过渡构造细节本综述未直读，只核验了元数据。

7. **Motion warping / Spacetime constraints / Popović & Witkin 1999 的公式细节** —— 仅核验 Crossref 元数据，未读全文（§二）。
8. **PFNN / MANN / NSM / Learned Motion Matching / Robust Motion In-betweening 的正文与网络结构** —— 仅核验元数据与 arXiv 条目，未读全文（§5.1 / §六）。本综述**不**转述其结构细节。
