# 开局「经历 · 疾病接回病历」（阶段 7）

> **一句话**：一局的经历不再是十段散点，而是**一件事**——那件事直接激活它的病，玩家在对话里认下其中一张，医师把「初步诊断」写上纸；那张病反过来驱动他怎么说话与精神检查那三行。
>
> **维度: 呈现 + 数据契约**（口径文档）。**范围仅开局 / Web 演示**，不得引入 C# 引擎或神经模拟系统（[AGENTS.md §二](../../AGENTS.md) 拦截规则）；**战斗相关内容一律不碰**（7 扇 `paused` 的遭遇门原样保留、不渲染）。
>
> **现行 = 哪一份 · 存量 = 哪一份 · 为什么**（提示词 §一 第 10 条要求写明）：
>
> | | 现行（阶段 7 起） | 存量（阶段 5 起断电，**原样保留、键不删**） | 为什么留着 |
> |---|---|---|---|
> | 问诊与病历 | [`data/opening_clinic.json`](../../data/opening_clinic.json) · [开局门诊问诊](开局门诊问诊.md) | — | 阶段 5 起它就是开局问诊的唯一权威 |
> | 那件事 | `data/opening.json` 的 **`event_rule` + `events`** | `interview`（八问）· `interview.pool`（池子与放宽阶梯）· `quota`（认满十段） | 存量契约与 `web/src/character-creation/` 的测试逐条钉着它们（[经历结构](经历结构.md) §十 已就地标 🔧） |
> | 疾病 | `data/diseases.json` 的 `items`（26 张名册 + 1 条固有项）+ **`candidate_rule`** | `pool_rule`（病并集 2–4） | `opening.js` 的 `fillPool` / `poolFloors` 与 `diseases.js` 的结构校验仍在读（[疾病结构](疾病结构.md) §五 已就地标 🔧） |
> | 言语与精神检查 | `opening_clinic.json` 的 `voices`（指纹挂病）+ `compose` | 阶段 6「调子不等于诊断」 | 那句被 owner 第 6、7 条裁定推翻，[开局门诊问诊](开局门诊问诊.md) §14.3 已就地标 🔧、§十五 是现行 |
> | 288 段经历 | **素材库**（`events[].source_experiences` 指回它） | 一局的可选项来源（已退役） | 内容一字不改，是这一轮明确要求的口径（提示词 §7.4） |
>
> **一句话说清「为什么改」**：owner 判定「经历首先需要满足能够激活疾病」且「精神病人的疾病诱因往往是围绕着一件事展开的」——存量口径下，玩家答的话与「哪张病」之间隔着一层**十段并集的运气**（实测：`c·k = 2×10 = 20 < 26`，本局至少 22 张病结构性不可达）。改设计，不改内容。

## 一、一局的链条（五步，每步都可机核）

```
门诊问诊（114 问 · 现行，不动）
  → ① 答案收敛出「那件事」（一局恰一件）
  → ② 那件事激活的病（本批每件 4 张 → 候选 ≤ 4）
  → ③ 玩家在对话里认下其中一张
  → ④ 医师笔迹把「初步诊断」写上纸（诊断栏 fill: blank → derived）
  → ⑤ 那张病驱动言语指纹与精神检查三行 → 病历写完 · 签字
```

| 步 | 判据（一条判据一个 id，报错能指到数据行） | 落在哪个文件 |
|:--:|---|---|
| ① | `one_event_per_run`（任何答案组合下恰一件）· `event_unreachable`（没有死事件）· `event_locate_fallback_missing`（兜底件存在）· `locate_rule_target_missing` / `locate_value_unknown` / `locate_question_unknown` | `opening_clinic.json` 的 `event_wiring.locate` + `opening.json` 的 `events` |
| ② | `event_activates_empty` · `event_activates_range`（1–4）· `event_activates_always_on`（不许是 `dis_0027`）· `event_voice_per_event`（4 张分属 4 套指纹）· `candidate_over_limit` · `candidate_empty` | `opening.json` 的 `event_rule` + `events[].activates` · `diseases.json` 的 `candidate_rule` |
| ③ | `not_in_candidates`（不在候选里认不了）· `voice_disease_conflict`（与调子收敛到的病不一致就拒） | `opening-clinic.js` 的 `confirmDisease` |
| ④ | `diagnosis_pen_not_hospital`（`who` 必须是 `hospital`、`fill` 必须是 `derived`）· `diagnosis_source_unknown` | `opening_clinic.json` 的 `record.columns` |
| ⑤ | `candidate_without_voice`（每张被激活的病都要有指纹代言）· `voice_without_disease` · `expand_not_on_paper`（答了必须上纸） | `opening_clinic.json` 的 `voices` + `compose` |

**一局的经历数 = 恰 1 件事**（owner 待裁 6 的默认 (a)）：不是 0（走不出病历），也不是多件（owner：「不是大海捞针」）。它由**规则表的末条无条件兜底**保证——这是**结构保证**，不是抽样结论；`one_event_per_run` 只是把它再枚举验一遍。

## 二、① 那件事：`events`

### 2.1 schema（`data/opening.json`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `^evt_\d{4}$` | 主键，不透明、不复用 |
| `title` / `summary` / `claim` | string | `title` ≤ 8 字 · `summary` / `claim` ≤ 48 字 · 禁阿拉伯数字 · 禁「从小 / 一直 / 每次 / 总是」· 禁时间 facet 的标签（与经历侧同一套 `text_lint`） |
| `spine` | 对象 | 那件事的**主轴**：`onset` · `context` · `relation` · `duration_span` · `duration_pattern` · `agency` · `event`（多值）。取值**全部来自现有 11 facet 词表**，不新建轴（`event_spine_facet_unknown` / `event_spine_value_unknown`） |
| `expansions` | array ≥ `expansions_min` | **扩展位**：每档 `{ id, facet, value, q, value_id, label, clause, column, basis, exclude? }` |
| `activates` | `string[]` 1–4 | 那件事激活的病 id（`diseases.json` 的 `items[].id`）。这是 owner 第 2 条裁定的落点 |
| `effects.attributes` | `{attr: int}` ≤ 2 项 | **= `source_experiences` 那几段素材属性效果的合计**（`event_effects_not_from_material` 现场比对） |
| `source_experiences` | `string[]` 2–4 | 这件事**扩写自**的存量素材（`exp_####`）。用途两个：① `profileOf().experiences` 直接把它交给下游结算；② 审计素材覆盖。**不是反查键**（方向是 事件 → 素材） |
| `basis` | string | 这件事的临床依据（逐条指到 `psy7.txt` 行号或规范条文） |

### 2.2 `claim` 是「经得起扩展」的第一判据

owner：「这件事给病患的影响之大以至于**打乱了他的整个人生轨迹**」。每件事必须有一句 `claim` 说清**打乱了哪一段**。教材侧最贴近的原文是 `psy7.txt:7416-7417`「所谓『创伤性体验』应该具备两个特点：**第一，对未来的情绪体验具有创伤性影响**」——⚠️ 教材说的是**情绪体验**层面的未来影响，**不是**「人生轨迹」；「人生轨迹」是 owner 口径（见 [诱因事件检索记录 §七 7.1 第 2 条](../spec/material/ref/诱因事件与生活事件-检索记录.md)）。

### 2.3 扩展位：哪一问对应哪一位

owner 第 4 条列了六位（什么时候 / 在哪儿 / 身边有谁 / 那时你能决定多少 / 后来怎样 / 留下了什么）。在现行 114 问里**能对上四位**：

| owner 的位 | facet | 哪几问（现行题库里的原问，**没有新增一问**） |
|---|---|---|
| 在哪儿 | `context` | `q086`（幼年家庭环境 → `context.family`）· `q087`（学习与工作 → `context.school` / `work`）· `q009` 的 `work_p` 档 |
| 身边有谁 | `relation` | `q089`（婚姻 → `relation.partner`）· `q092`（病前性格与人际 → `relation.peers` / `parents`）· `q009` 的 `relation` 档 |
| 后来怎样 | `duration_pattern` | `q007`（既往有无类似发作 → `single` / `intermittent` / `continuous`） |
| 留下了什么 | `consequence` | `q011`（病后功能 → `consequence.ability` / `behavior`）· `q093` 的 `money` 档（→ `consequence.resource`） |
| 什么时候 | `onset` | ⏳ **没有问可问**（q005 问病程长度、q006 问起病缓急，都不是 facet `onset` 的童年/少年/成年）⇒ 由 `spine.onset` 承载 |
| 那时你能决定多少 | `agency` | ⏳ **一问都没有**（侦察实测：114 问全部答案闭集对 11 facet 对照，`agency` 命中 0）⇒ 由 `spine.agency` 承载 |

⇒ 所以 `event_rule.expansions_min = 6`（**档数**下限），并要求每件事的扩展位覆盖那**四位**（`expansion_axes_required`）。两位 ⏳ 的处置：**由 spine 承载，不进 expansions**——这不是绕过，而是承认「那件事的『什么时候』与『他能决定多少』在现行门诊初诊口径里问不出来」。

**扩展位的文案不另写一套拼句引擎**：`clause` 就是该问该档在 `compose` 模板里已经用到的那一段（同一个字符串），`column` 就是那一问答问时落笔的栏目。答一句 → 纸上多一句，由现有的 `composeColumn` 完成。这三样是**重述**，由 `expansion_label_mismatch` / `expansion_clause_mismatch` / `expansion_column_mismatch` 现场比对。

## 三、②③ 候选与认：从 4 张收窄到 1 张

### 3.1 候选为什么恰好是「一件事 4 张、一套指纹一张」

⚠️ **这个 4 不是随手取的上界，是两条既定约束合起来钉死的**：

1. 语言指纹有 **4 套**（owner 阶段 6 亲自选的那四套）；
2. 提示词 §7.3.3 要求：**任意一局里，「玩家认下的病」都必须与「他怎么说话」收敛到的病一致**（判据 `voice_disease_conflict`）。

而「他怎么说话」由玩家在对话里的选择决定，与「那件事」近乎独立 ⇒ 要让这条一致性**在任何答案组合下都成立**，那件事的 `activates` 就必须**每一套指纹各有一张病**；4 套指纹 ⇒ 每件事恰 4 张。

**这不是推论，是实测过的**：本批第一版取 2 张时，45 局里有 **17 局**「调子显出来了、但候选里没有一张对得上」——玩家按不了「认」这个键，那一局是死的。改成一套指纹一张之后，同一组采样 **0 局**无解。

### 3.2 收窄规则（数据在 `event_rule.candidate_and_voice` 与 `event_wiring.candidate`）

```
候选 = 那件事的 activates
       减去 已答扩展位声明排除的病（expansion.exclude；本批没有声明任何一条）
再按这一局说话的调子收窄：调子显出来 ⇒ 只剩该调子代言的那一张；没显出来 ⇒ 4 张全摆出来
上界 = event_rule.candidate_max = 4 = diseases.json 的 candidate_rule.candidate_max
```

所以玩家看到的是：**还没怎么说话时 4 张里挑；一开口就被自己的说法收敛到 1 张**——「怎么说话就是在说哪张病」（owner 第 7 条）。实测（枚举：每分支每题 k 档 + 全部拒答）：**候选 1 张 = 38 局 · 候选 4 张 = 79 局 · 超过 4 张 = 0 局 · 调子与候选冲突 = 0 局**。

「先收窄、后落笔」这件事在数据自洽时让 `voice_disease_conflict` **永远不触发**——它是一道**兜底判据**（数据坏了才响）。反例测试 `opening-clinic-event.test.js` 里用手工改坏的数据把它逼出来了一次。

### 3.3 认落在哪：对话里一枚回应（owner 待裁 4 的默认 (a)）

**不新开屏、不在纸上加「患者意见」栏**：门诊初诊的法定栏目（《病历书写基本规范》第十三条）里**没有**「患者意见」，自造栏目违反「不许自造」（[开局病历填报](开局病历填报.md) §2.1）。玩家只做「**认**」这一个动作。

## 四、④⑤ 诊断栏与言语

### 4.1 诊断栏：医师的笔，不是玩家的

| 项 | 值 | 依据 |
|---|---|---|
| `fill` | `blank` → **`derived`** | owner 第 6 条裁定 |
| `who` | `hospital`（不变） | 《病历书写基本规范》第十三条：初诊病历记录书写内容含「诊断及治疗意见**和医师签名**」 |
| `value_from` | `confirmed_disease`（新增） | 本局认下的那张 |
| 门诊侧的栏名 | 「诊断」（国家规范）/「**初步印象**」（河南细则第二十三条） | [门诊检索记录](../spec/material/ref/精神科门诊病历-书写规范-检索记录.md) §2.4 |
| `treatment` | **仍留白** | owner 待裁 3 的默认 (a)：医嘱尚无口径 |

⚠️ **写上去的是文书上的「初步诊断」，不是给玩家看的标签**；不写医嘱、不写量表分、不写护理等级（owner 第 7 条）。没认病时诊断栏**仍是空白态**（`diagnosis_pen_not_hospital` 在「全拒答」那一局上验过这一点）。

### 4.2 言语挂在病上（`voices.items[].disease` + `covers`）

owner 第 7 条：「语言指纹现在**挂在病上**：怎么说话就是在说哪张病」。§14.3 那句「调子不等于诊断」被推翻，[开局门诊问诊](开局门诊问诊.md) §14.3 已就地标 🔧。

- `disease` = 这一套的**主病**（owner 待裁 5 指定的四张）
- `covers` = 它同时代言的其他病
- 由病反查指纹 = `voiceOfDisease()`；一套代言哪些病 = `diseasesOfVoice()`
- **覆盖判据** `candidate_without_voice`：凡出现在任何事件 `activates` 里的病，必须被**恰好一套**指纹覆盖——否则会出现「候选里有它、但这一局没有台词特征」的病，那条冲突判据就形同虚设

⚠️ **为什么必须有 `covers`**：「四套各对 1 张主病」（owner 待裁 5）与「样板批 ≥6 张病」（owner 待裁 2 的默认 (a)）**两条要并存**，唯一的出路就是「主病 + covers」这个形状。这不是自造概念，是两条既定约束的必然结果。本批实测：4 套指纹覆盖 **26/26** 张名册病（沉下去 7 · 往上冲 6 · 有人在盯 6 · 要数清楚 7）。

### 4.3 精神检查：认了病之后按病落笔

`observationRows()` 在认了病之后优先按**病**取 `derive.table`（`derivedFrom.kind === 'disease'`）；还没认病时回落到按**调子**取——阶段 6 的行为**一字不变**，所以旧的观察行测试全绿。数据形状没改（`derive.from: 'voice'` 仍是那四套指纹的表），改的是**取哪一套的优先级**。

### 4.4 属性结算：一个数，不是两个

`event.effects.attributes` = `source_experiences` 那几段素材属性效果的**合计**（`event_effects_not_from_material` 现场比对）。而 `profileOf().experiences` 带出去的**正是那几段素材 id** ⇒

- 新路径 `settleEventAttributes(odb, eventId)` 与
- 旧路径 `settleAttributes(odb, [...profile.experiences])`（下游 `opening-runtime.js:71` 至今这么调）

**结算出同一个数**——测试里逐件事断言两者 `raw` / `clamped` / `totalRaw` 相等。⇒ 不存在第二份权威。

⚠️ **与存量的差别（要 owner 知道）**：净值 = 素材数 × `effects_rule.net`（2）。本批每件事 **4 段素材 ⇒ 一局的原始总和是 8**，而存量「十段和」是 **20**。序章三条检定阈值（3 / 5 / 7，见 `opening-runtime.js:6`）在总和 8 之下会明显更难通过——见 §八 待裁 4。

**新增判据** `expansion_id_collision_unjustified`：若某扩展位两端的 id **字符串恰好相同**（本批 3 处：`q074.threat` · `q086.loss` · `q089.partner`），必须带 `same_id_note` 说清「**同名是巧合，不是语义相等**，映射理由是这一句判断」——缺了就报错。三处都写了，例如 `q086.loss`：clinic 的「小时候有过亲人去世」是**成长环境里的一件事**（个人史栏），opening 的 `event.loss` 是**这件事在事件轴上的坐标**；映射成立靠的是「亲人去世在事件轴上就是失去」这一判断。

## 十二、三条形态裁定（2026-09-27，owner 在真浏览器里看过成品之后）

> **owner 原话背景**：「owner 刚在真浏览器里看过阶段 7 的成品」。三条都是**呈现层**的裁定，
> 与数据、与 §一 的链条无关：**一个字都没动 `data/**`**，也没动契约层算法。
> 落地位置：`web/src/opening-clinic/index.js` · `opening-clinic.css` ·
> `design/presentation/叙事界面原型.html` 的 `:root`（颜色变量与夜色 / 浅底那批同一处）。

### 12.1 纸不随每次点击滚到底

| 项 | 现行 |
|---|---|
| 左世界那张纸（`.oc-paper-scroll`） | **不再随每次渲染 / 每次点击滚动**。⚠️ 但 `innerHTML` 一换，那个容器本身是**新元素**、`scrollTop` 会归零——所以渲染前记住、渲染后**放回去**（位置要留住，不是每次跳回纸头） |
| **唯一允许的例外** | 「正在填的那一栏」（`activeColumnId`）**发生了变化**时，把它滚进视野一次：按**视口矩形**（`getBoundingClientRect`）算，语义 = `scrollIntoView({ block: 'nearest' })`（上沿在视野之上 → 对齐上沿；下沿在视野之下 → 对齐下沿；**本来就看得见 → 什么都不做**）。⚠️ 不用 `offsetTop`：它相对 `offsetParent`，中间隔一个 `position: relative` 就偏了。拿不到矩形的宿主才回落到 `scrollIntoView({ block: 'nearest' })` |
| **不做平滑动画** | `.oc-paper-scroll` 上没有 `scroll-behavior: smooth`；换栏那一次是直接赋值 |
| 同一栏里连续落笔 | **不滚**（那一栏没变，走「放回去」那条路） |
| 右栏叙事流 | 🔧 **追加裁定取代了原来那条「始终滚到最新」**：改成**让回应整块进视野**，见 §12.2 末的「回应块进视野的规则」 |

**判据**（`render-clinic.mjs --check` ⑨ · `opening-clinic-ui-shape.test.js`）：
同一栏连着渲两次，`scrollTop` 不变且**不等于纸尾**；换栏那一次 `scrollTop` = 「那一栏的下沿对齐视野下沿」
（桩里的数 300 + 200 − 400 = 100）；那一栏本来就看得见时**不动纸**。
⚠️ 无头桩必须照**真浏览器**建模（`innerHTML` 一换就把 `scrollTop` 归零、那一栏的视口矩形随纸滚动上移），
否则这条判据是空的——已验证：把旧的「滚到底」放回去，这条判据**会红**
（`scrollTop 900`，且换栏时算成 `300` 而不是 `100`）。**生产代码走的就是被判据覆盖的那条矩形路**，
`scrollIntoView` 只是拿不到矩形时的退路。

### 12.2 右栏不再分成上下两段：整栏只有一个滚动区

| 项 | 现行 |
|---|---|
| 结构 | `.oc-panel` 的网格从**四行**变**三行**（说话者条 · 调子条 · 唯一的滚动区） |
| 回应 | 从「钉在底部的第二个滚动区」（`.oc-responses`，有自己的 `overflow-y: auto` 与 `max-height`）改成**叙事流末尾的一块**：`.oc-now`，**没有自己的 `overflow` / `max-height`** |
| 一个滚动条 | 右栏只有 `.oc-story` 一个滚动容器（左世界的纸在世界那一侧，不算） |
| 选择之后 | 那一块由「患者说」那条 beat 接替（`dialogueTurns` 里那条本来就是干这个的），**不留两份** |
| 语义不变 | `data-choice-index` 的数字键 1–9 · `data-responses` · `data-candidates` · `data-disease` **一个字没改**（测试与自检都靠它们） |
| 不动的 | 说话者条 · 「他说话的样子」条 · 敏感提示的位置 |

**判据**：HTML 里 `data-responses="1"` 落在 `.oc-story` **之内**；渲染出来的 HTML 不再有 `class="oc-responses"`；
`blocksOf('.oc-now')` / `blocksOf('.oc-responses')` 的规则体里**没有** `overflow` / `max-height`；
CSS 里 `overflow(-y): auto|scroll` 的类只有 `.oc-paper-scroll` 与 `.oc-story`。
⚠️ 结构判据跑在**去掉注释**的 CSS 上（注释里也会出现 `.oc-now` 这类字眼，不剥掉会吃到下一个规则的规则体）。
`.oc-responses-label` 留着——它只是流里的一个标签，没有滚动。

**回应块进视野的规则**（🔧 2026-09-27 追加裁定：**取代原来那条「叙事流永远滚到最底」**。
实现在 `web/src/opening-clinic/index.js` 的 `scrollStoryToNow()`，`GAP = 24`）：

| 档 | 条件 | 滚到哪 |
|:--:|---|---|
| ① | 回应块高度 + **24px** ≤ `clientHeight`（装得下） | `min(最大滚动量, 块底 + 24 − clientHeight)`，**下限 0** = 刚好把整块连同那 24px 带进视野的**最小**位置——**前面医师那一句能留多少留多少** |
| ② | 块比可视高度还高（装不下） | `min(最大滚动量, 块顶 − 24)`，**下限 0** = 让玩家从提示那一行往下读，而不是只看见选项的下半截 |
| ③ | 拿不到 `clientHeight` / `offsetTop` | 回落到原来的「滚到最底」（`scrollTop = scrollHeight`） |

- 最大滚动量 = `scrollHeight − clientHeight`；两端都夹紧（不许滚成负数、也不许越过上限）。
- ⚠️ `offsetTop` 相对的是**定位祖先**——所以 `.oc-story` 在 CSS 里拿到了 `position: relative`
  （否则会以 `.oc-overlay` 那种 `position: fixed` 的祖先为参照，量出来是错的）。**这一条写在 CSS 注释里**。
- **生产代码走的就是被判据覆盖的那条路**：`render-clinic.mjs` 的桩给 `.oc-story` 建了 `clientHeight`、
  给 `.oc-now` 建了 `offsetTop` / `offsetHeight`，**①②两条分支各一条判据**（外加下限/上限与回退各一条）。
  实测：装得下 → **724**（1400/400/900/200）· 装不下 → **676**（1600/400/700/600）· 贴边 → **0** · 拿不到尺寸 → **1200**。
  已验证反证：改回「永远滚到最底」，这三条判据**会红**（1400 / 1600 / 非零退出）。

### 12.3 调子色只画在选项上，且不是唯一线索

**边界（owner 明写）**：`design/conventions/README.md` §二 第 46 行的禁令原文是
「❌ **用颜色表示情绪/态度**（颜色系统已废弃，用 PAD 向量）」——它禁的是**用颜色承载那个已废弃的
情绪 / 态度模型**，**不是**禁止界面用颜色。所以：**这是言语指纹的分组色，不是被否决的
「颜色表示情绪 / 态度」那套体系。**

| 项 | 现行 |
|---|---|
| 定义 | 四个 CSS 变量 `--voice-depressive` / `--voice-manic` / `--voice-paranoid` / `--voice-compulsive`，与夜色 / 浅底那批**同一个 `:root`**（`design/presentation/叙事界面原型.html`） |
| 画在哪 | **只画在选项上**：左侧一条 3px 细边 + 调子名那一小块（`.oc-choice-voice` 的 `border-color` / `color`）。**不铺整块底色**（规则里没有 `background`） |
| 不只是颜色 | `.oc-choice-voice` 里的调子名（沉下去 / 往上冲 / 有人在盯 / 要数清楚）**照旧写着**——颜色是**冗余**信息 |
| 对比度 | 正文与选项文字仍 ≥ 4.5:1（本屏老纪律）。四色在选项底（#171c1a）上：沉下去 **7.08:1** · 往上冲 **9.44:1** · 有人在盯 **5.19:1** · 要数清楚 **11.25:1** |
| 色盲可分辨 | 四色**拉明度差**而不是只靠色相：相对亮度 **0.266 / 0.381 / 0.524 / 0.635**（相邻差 ≥ 0.11） |
| 类名 | 选项上挂 `oc-voice-<指纹 id>`；四套指纹 id 仍是 `depressive` / `manic` / `paranoid` / `compulsive` |

**判据**：本屏带指纹的档都带色类名，且**色块数 = 调子名数**；四个类都在 CSS 里且都走 `var(--voice-*)`；
四个变量都在页面 `:root` 里；调子色的规则体里**没有** `background`。

### 12.4 这一轮**没做**的（诚实清单）

- **仍然没有真实浏览器实测**：只有无头 DOM 桩（这一轮把桩补成会建模滚动位置的那种）+ `--check`。
  滚动位置、`scrollIntoView` 的真实手感、候选块并进流里之后的观感，**都要 owner 自己看一眼**才算验收。
- 数字键那条路在桩里是真按过的（从渲染出来的 html 反读按钮），但**真浏览器的 keydown 绑定**没实测。
- `data/**` 一个字节没动；`opening-clinic.js` 的契约算法没动；`web/src/character-creation/**` 没动。
