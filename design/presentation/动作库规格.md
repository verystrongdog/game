## 一、定位与边界

- **载体**：`ActionLab` 动作演示场（**Mixamo X Bot 真人模型** 🔧 默认，Y Bot 备用 + 词表 controller + 按键触发 + HUD 当前动作名），无回合逻辑。
- **载体上的道具**：面具、武器等**不换模型**，作为**骨骼挂点道具**（attach 到 `Head` / 手骨）实现——载体保持 X Bot/Y Bot 不变（2026-09-12 裁定，理由见 §八 所有权约定的推论）。
- **排除**：数值、UI 规格、特效与声音（留给「反馈动画方向」grilling）；技能动画（P1 技能系统接入时另立）；回合流程扩展动作（沙盘 #122 D1 范围外）。
- **下游消费者**（本规格只备底子，不实现）：DemoSandbox 白盒换真人模型、NPC 行为演示（unity-brain-connect）、反馈动画 grilling。

## 三、词表元规则

### 3.1 分层判定（二维）

- **Q-a 消费端就绪度**：现役消费者在驱动？若无，是否在已排期路线图（设计已闭合/批次已列）？
- **Q-b 动画来源就绪度**：现成资产可引用，还是缺口（采购/制作/程序化）？

| Q-a | Q-b | 层级 | 处理 |
|---|---|---|---|
| 现役 | 现成 | L1-引用 | 本期接 clip |
| 现役 | 缺口 | L1-制作 | 本期补缺口 |
| 已排期（设计闭合） | 现成 | L2-登记 | 锁名 + 资产锚，不制作 |
| 未排期 或 形态未设计 | — | 不入表 | 扩展协议快轨 |

### 3.2 分类枚举（受控）

`category ∈ {locomotion, combat, reaction, social, interaction, status}`——词条必带，可按类检索；新类出现走扩展协议。

### 3.3 扩展协议（元规则，Grilling #123 用户采纳）

1. **命名只增不删**：动作 id 发布后不改名；改名/删除走 `🔧 修正注记`（同决策树闭合后修正机制）+ 全项目一致性清扫。
2. **新增 = 快轨**（不等 grilling，沿 term_registry 即时更新惯例）：提出须满足三条件——(a) 有正典来源或呈现形态定义，(b) 命名符合词表规范，(c) 声明状态（L1/L2）与来源；裁决后入表。仅当触碰命名规范或新资产采购/制作 → 升级 grilling。
3. **状态迁移**：L2→L1 触发 = 消费端就绪（批次/issue 启动）；L1 动画落地单独走实施批次。
4. **防漂移校验**：PlayMode 测试断言 controller 状态覆盖全部 L1 id、每状态有 clip；AI 引用动作只允许词表内 id。

### 3.4 升级触发器（引用契约 A → B/混合）——🔧 已触发

出现任一需求即评估迁移（locomotion 迁参数化/层，一次性动作可留 A）：

| 触发器 | 状态 | 处置 |
|---|---|---|
| ① 连续速度/方向混合（blend tree） | **🔧 已触发**（2026-09-12） | locomotion 迁契约 B（§四·乙） |
| ② 上半身/下半身层分离 | 未触发 | 按需：Probe 与 Play 反馈证实需要时才加 |
| ③ 动作组合复杂度超出 C# 可读范围 | **🔧 已触发**（词表将携带变体与过渡参数） | 机器源迁 `data/action_set.json`（§四·丙） |

**机器源形态裁定**：`data/action_set.json`（`role: generator-input`）+ Editor 侧生成器读它产出 controller 与 C# 静态表。理由与备选见 [分解文档](../engineering/动作系统分解-2026-09-12.md) 决策表 D-a。

## 四、引用契约（形态 A + 形态 B 混合）

**分工原则**：**离散的一次性动作留 A，连续与过渡迁 B**。判定看该动作是否需要「连续参数插值」或「跨动作的姿势对齐」——不需要的不要迁移。

### 甲、契约 A（保留：一次性动作、终态）

- **Controller = 纯状态集**：零参数、零手动 transition；每动作 1 状态，**状态名 = 词表 id = 代码字符串**（三面对一）。
- **切换 = 运行时 `Animator.CrossFade(id, fade)`**（不依赖 transition）；衔接决策在 C#（`ActionPlayer`）：
  - 优先级：`Down > HitReaction > 一次性动作(物攻/精攻) > Defend(持续态) > locomotion`（受击/倒下可打断出招；一次性动作播放期间锁移动切态与物理位移）。
  - 一次性动作播完（计时 `clip.length + 0.05s`）→ CrossFade 回 locomotion 目标态。
  - `Down` 为终态：停留末帧，须显式 `ResetToIdle()`。
- **适用词条**：`PhysicalAttack` · `MentalAttack` · `HitReaction` · `Down` · `Defend`（循环持续态）。
- **手动侧微流程**（每动作恒定 3 步，兼作 Animator 学习）：① Create State ② 挂 clip ③ 命名 = 词表 id。

### 乙、契约 B（新增：locomotion 与过渡）

针对触发器①（连续速度/方向混合），locomotion 由「离散三态 + CrossFade」改为**参数化混合**：

- **1D Blend Tree（速度轴）**：`Idle(0) → Walk(走速) → Run(跑速)` 三点混合，单一混合相位。**取代**原来 Idle/Walk/Run 三态在阈值处硬切——硬切**不做相位对齐**，走跑换挡处会产生步频相位跳。
  - 速度阈值来源：`ActionLabDriver.walkSpeed = 3.0` / `runSpeed = 6.0` m/s（**演示常量，非正典数值**，代码位置 `ActionLabDriver.cs`）；blend tree 的三个采样点即 `0 / walkSpeed / runSpeed`。
- **层与 Avatar Mask**：**本轮不预建**。触发器②未触发——按需在 Play 反馈证实「需要边移动边出招/受击」时才加层。预建层会在没有需求时增加调试面。
- **过渡相位对齐**：B 的混合由参数驱动，不再依赖 CrossFade 的时长插值；一次性动作 ↔ locomotion 之间的切换仍走 A，其 fade 口径见 §七。
- **位移口径（🔧 已裁定：坐/起例外，须开 root motion）**：本规格原为「位移全走 CharacterController + `applyRootMotion = false`」。**实测推翻了它在坐/起上的适用性**（原 Windows 拷贝里的实现，2026-09-07）：
  - **坐下段必须接管 root motion**：临时禁用 CharacterController（默认 root motion 走 `cc.Move` 会被地面碰撞挡住 → 坐姿沉不下去、双脚离地），并由 `OnAnimatorMove` 手动把 `animator.deltaPosition` 施加到 transform。
  - **起身段走了过程性过渡**，因为 `Sit To Stand` clip 与坐下 clip 的坐姿基准不匹配（根位基准差 ≈ 0.31 m），纯姿势混合在接缝处下陷/跳动。
  - **结论**：`applyRootMotion = false` 作为**默认口径仍适用于 locomotion 与一次性上身动作**，但**凡涉及体位改变（坐/站/倒地类）的衔接，纯姿势混合不够**——这正是「姿态切换自然」在本项目里第一个被证据否定的假设。
  - 待 #137 补齐的是**数值读数**（就座落点与锚点的水平/垂直偏差）与**clean 实现**（合并两侧分叉），而不是「纯姿势混合行不行」这个方向性问题。
- **足部贴地**：不在本轮预建。仅在探针或 Play 证实「地面起伏导致脚悬空/陷入」时才引足 IK（试验场可用玫瑰花海那块真实起伏地形，见 [地块数据](地块数据-Konza草原.md)）。

### 丙、机器源与数据契约

- 机器源 = `data/action_set.json`：词条元数据（id / 呈现词 / category / 层级 / 循环性 / 优先级 / fade / clip 路径）+ locomotion 混合参数。
- 消费方式：**Editor 侧生成器**读它，产出 ① controller 资产 ② C# 静态表（运行时消费生成的 C#，**运行时 Unity 不跨边界读 `data/`**）。
- 生成器必须**非破坏**：只补缺失、不覆盖 Editor 侧已手调的值（否则手调成果在下次生成时被吞掉）。
- 依赖边声明见 [ARCHITECTURE.md §二](../../ARCHITECTURE.md)。

**目视清单（用户 Play）**：① 待机→走→跑→停 切换顺滑（🔧 批次 4 后按 B 的混合判）；② 每动作触发后 HUD 显示正确动作名；③ 物攻→受击（打断）→回待机；④ 防御姿态循环不穿模；⑤ 倒下停留不悬浮；⑥ 衔接过渡帧是否可接受。
