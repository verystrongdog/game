## 一、架构边界

**游戏设计文档是 primary artifact；代码是验证与实现工具。**

```
design/     设计文档（正典）         ← 唯一真相源，回答"这个游戏是什么"
reference/  外部参考与已废弃子系统   ← 文献锚点，不参与正典
code/       实现与验证              ← 服务于设计验证，不反向定义设计
data/       结构化数据契约           ← 参数真值源
```

| 边界 | 规则 |
|---|---|
| design ↔ code | 代码里的数值必须与 `design/` 正典一致；不一致时以 `design/` 为准并修代码（例：`CalibrationConfig.NpcHp` 曾长期停留在 15，而权威表为 20-30）。**完整边界声明与已知越界点见 [ARCHITECTURE.md](../../ARCHITECTURE.md)** |
| design ↔ data | `data/canon/` 是引擎消费的契约；参数的权威定义在 `design/`，`data/` 是其机器可读形态 |
| code/unity | Unity 工程是**纯呈现**，不承载逻辑正典。逻辑正典在 `code/src/`（C# 类库） |
| 跨语言 | 设计文档（中文）→ `data/*.json` → 引擎消费。三者的参数必须可机械比对 |

**设计分界**：玩家交互 = 3D 技能树 + 快捷槽，技能直接走数值结算；NPC AI = 脑区链路预烘焙查表（6 性格标签 → 髓鞘化偏移 → 27 情境 × SAN 分段行为概率分布）。

## 二、内容禁令

以下是被**明确否决**的方向，不得重新引入（详见 [决策树 — 被否决的方向](../decisions/01-rejected-directions.md)）：

- ❌ 用颜色表示情绪/态度（颜色系统已废弃，用 PAD 向量）
- ❌ 离散 ±1/0 态度晶体（改用连续空间）
- ❌ 把"态度"当作独立实体或卡牌类型（态度是结算结果的组合，不是实体）
- ❌ 卡牌交互方式（已迁移至 3D 技能树）
- ❌ 把战斗简化为"削血"逻辑
- ❌ 治疗模拟框架（世界观是意识外显效应，不是治疗中心扮演）
- ❌ 在代码中使用与设计文档不一致的公式
- ❌ 凭空添加设计文档中没有的机制

**术语使用禁令**（防止旧模型回流）：

| 术语 | 现状 | 禁止 |
|---|---|---|
| 态度 | ⚠️ 已废弃 | 不要说"态度卡"、不要当作实体 |
| 7 驱动 / 5 模块 | ⚠️ 已废弃 | 技能分类当前口径是 **主导网络（Kroell 14 网络）× 主导角色（8 行为角色）** |
| CPM | ⚠️ 已废弃 | — |
| 意志力 (WP) | ⚠️ 已废弃 | 已替换为**认知负荷模型**（`design/rules/skill-tree/脑功能层级模型.md` §十三） |
| PAD | ✅ 活跃（情绪表示） | 作为**技能定位空间**已废弃（坐标已迁 MNI 解剖坐标） |
| SAN | ✅ 活跃 | 是护盾不是血条；SAN 与 HP 可互相转化但有上限 |

完整术语状态以 [`data/term_registry.json`](../../data/term_registry.json) 的 `status` 字段为准。

## 三、文档格式规范

**文件头部**

```markdown
# 文档标题

> 一两句话摘要——本文档的核心内容和定位。
```

**文件尾部**

```markdown
---
*创建: YYYY-MM-DD | 更新: YYYY-MM-DD*
*关联: [文档名](相对路径), ...*
```

| 规范 | 要求 |
|---|---|
| 目录 | 超过 200 行的文档，在摘要后加 `## 目录`（有序列表链接到各 `##` 小节） |
| 小节编号 | 用 `## 一、标题` 中文数字（便于交叉引用，如"见 §二"） |
| 一个文件一个主题 | 不要在一个文件中放多个 H1 |
| 参数速查表 | 涉及数值参数的文档，文末加表，列名统一为 `\| 参数 \| 符号 \| 默认值 \| 位置 \|` |
| 语言 | 设计文档用中文；代码注释中英皆可 |

**豁免**：`SKILL.md` 与其它**可执行指令文档**的小节标题可用描述性文字，不要求中文数字编号。

## 四、引用与参数规范

完整规范见 [写作与引用规范](writing-and-references.md)。要点：

- **路径**：仓库根相对路径或正确的相对路径；优先段引用（`§八`）而非 URL 锚点（渲染器差异）
- **参数**：所有数值参数必须有**来源注释**（文献出处或设计文档章节）。新增参数标注 `[NEW]` + 来源编号，关闭后下一次编辑该文件时摘除
- **交叉引用**：`[显示文本](相对路径)`，展示文本清晰描述目标（不只是裸文件名）
- **引用即读取**：任何事实性引用（参数、公式、已有决策、文件路径）**必须先读源文件确认**，不得凭记忆引用。这条不因工具或流程变化而豁免

## 五、术语注册表

[`data/term_registry.json`](../../data/term_registry.json) 记录术语的项目内定义、"已否决的默认模型"与偏离原因。

**触发更新**（三者任一）：

1. 引入注册表中没有、且项目内有自定义含义的新术语
2. 已有术语的 `definition` / `old_model` / `deviation_reason` 被实质修改
3. 两个已有术语的边界被重新划分

**覆盖范围**：设计文档的表格列头与参数名中出现的 ≤4 ASCII 字符短标识符，一并入库；**不在注册表中的短标识符默认视为未定义**。

**状态**：注册表是**术语参考**，不是准入门禁。它不阻塞任何改动，只用于核对术语是否已被否决。

**修订流程**（四条短规则，2026-09-14 增；🔧 2026-09-15 增第 4 条）：

1. **改定义**：`definition` / `old_model` / `deviation_reason` 的实质修改属触发更新第 2 条 ⇒ 改字段的同时刷 `updated`、遍历复查 `numerical_locations`，并**全项目 grep 该术语**后跑 [§八 工具链](#八工具链) 的三个校验器（`numerical_locations` 只覆盖"数字出现在哪"，**不覆盖术语被文字引用的地方**）。
2. **废弃**：**保留条目、不删**（删了就没有"这个词曾被用过"的记录）；`status` 改 `deprecated`，并把**替代物写进 `definition`**（先例：「7驱动」写"NPC AI 改用脑区链路模型"）；**并且**补 `enforcement` 字段——**逐术语执法策略**（🔧 2026-09-15 [#159](https://github.com/verystrongdog/game/issues/159) 起由校验器**自动覆盖**，不再靠手工加正则）：

   | `enforcement` | 判定行为 | 该选它的判据 |
   |---|---|---|
   | `扫描` | 活跃文档里出现即判残留（`⚠️ 已废弃` 行 / 整节、以及引用式写法除外） | 该串**除旧模型外无合法用法** |
   | `只登记` | 不判；命中数只计数、不列明细 | 该串在活跃文本里**另有合法用法**（记号 / 缩写 / 日常词）⇒ 逐串匹配分不出新旧义，判了就是假阳性机器 |
   | `关闭` | 不判；**但现存量每次运行都打印**（欠账在明处） | 本可扫，但活跃文档**现存残留未清** ⇒ 先记账，清理后改回 `扫描` |

   **缺字段或取值非法 ⇒ 按 `扫描` 处理**（fail-closed）："只标 `status` 不加门禁"这一形态不得靠不写字段成立。判定实现 = [`validate_trash_isolation.py`](../../code/tools/validate_trash_isolation.py) **检查 4**（设计文档面，判定面 = `design/` + `reference/` 活跃文档）；issue 正文面 = [`validate_issues.py`](../../code/tools/validate_issues.py) **I10**（读同一字段；`只登记` 档在那边也不判——机器分不出新旧义的串，在讨论面同样不可判）。三档实测分布与各档现存量见 `data/term_registry.json` 的 `_maintenance` 与每次运行的门禁输出。**只标 `status` 不加门禁 = 记了一笔没人查的账**——现在这笔账每跑一次门禁就打印一次。
3. **不够格 / 待裁决**：登记进 [`data/term_registry_candidates.md`](../../data/term_registry_candidates.md)；达标后由 **owner 裁决**、结论落 `design/` 正典，再移入主表。
4. **口语判词的归类（🔧 2026-09-15 增，三问）**：现实语言里人人能懂、但**没有可计算定义**的判词（重心 / 审美 / 自然 / 稳…）必须逐词走一遍三问，**不允许停在中间态**（⚠️ 一个词可能**被拆成两半**各归一问——先例：`自然` 已拆为「**结构性自然**（问 1，是承诺）/ **审美与节奏自然**（问 2，仅目视）」，见 `design/presentation/动画处理能力对照实验.md` §六.7）：

   | 问 | 答「是」⇒ 处置 |
   |---|---|
   | **1. 能不能落成可计算量？** | 入库 `active`；`definition` 必须写成**代理量 + 单位 + 取值时刻** |
   | **2. 落不成量，但只出现在 owner 的目视意见里？** | 入库 `active`；`definition` 明写「**仅属 owner 目视语汇；不得出现在判据 / 禁止清单 / 验收线**」，并写明它**如何生效**（[动作描述口径 §二](../presentation/动作描述口径.md)：参考图 / 参考 clip /「像这样」**只能发起讨论，不能结案**，须由 agent 翻成 ① 点约束或 ② 关系判据才结案） |
   | **3. 它现在正被当禁止清单的宾语？** | 必须挂上第 1 或第 2 问的结论：**能成量的写量，落不成量的从禁止清单里删出去**——不可执行的禁令不是禁令 |

   `old_model` 与 `deviation_reason` 必填；**没有 `old_model` 的条目 = 没走完程序**。⚠️ 入库**不产生机器执法**（本节的「状态」段：注册表不阻塞改动）⇒ 结论落 `design/` 正典之后，**被它约束的文档要手工改**（含修正注记），再跑 §八 的三个校验器。

   **首批走完的词（2026-09-15，owner 逐词裁决）**：`重心` · `脚滑` · `穿模`（问 1，三者各有定义；后两者已有现成判据）· `审美` · `自然动作`（问 2，仅目视语汇）；`悬空` 与 8 个语汇（稳定 / 站得稳 / 出戏 / 滑步 / 姿态 / 姿势 / 可读性 / 动作质量）登记为候选清单的「暂不动」档。

## 六、归档与隔离

| 目录 | 语义 | 活跃文档可否引用 |
|---|---|---|
| **垃圾桶**（原 `design/archive/trash/`，现 `.trash/`） | 垃圾箱——确实废弃、不再作为数据源。**2026-09-13 整份移出仓库**（26 个文件 / 848K）：本地保留在仓库根的 `.trash/`（被 `.gitignore` 排除），历史仍可从 git 历史取回 | ❌ **不得引用**（两个位置都不得——指向 `.trash/` 对别人就是死引用） |
| `design/archive/grilling/` | grilling 源记录归档（决策记录 / 任务计划 / 工作稿） | ⚠️ 仅历史叙述，不得当作设计依据 |
| `design/decisions/` | 决策树（跨轮次索引与分叉记录） | ✅ 可引用（历史层） |
| `reference/deprecated/` | 已废弃子系统，**保留为参考数据源** | ✅ 可引用（数据源） |

**隔离原则**：内容移入垃圾箱后，项目中任何活跃文档（含索引、README、规格文档、状态表）不得引用其路径。移动文件时必须 grep 全项目所有引用该路径的地方，一并更新。废弃的数字/术语同理——只允许出现在决策树历史记录与标注了 `⚠️ 已废弃` 的段落中。

> **2026-09-13：垃圾桶移出仓库，隔离由「不在场」保证。** 原先靠校验器守一份「桶里有哪些文件」的枚举清单——2026-09-13 实测该形态会空过：一份**行内代码形式的子路径引用**（不在 7 个硬编码文件名内、也不是 markdown 链接）畅通无阻地写进了活跃文档，校验器仍是绿的。移出后，被检查的对象消失，规则只剩一条、且与桶内容无关：**活跃文档不得指向垃圾桶下的任何内容**（`design/archive/trash/<子路径>` · `.trash/<子路径>` · `垃圾桶/<子路径>`）；只写目录本身（用于定义本规则或记载变迁）不算引用。
>
> **代价（如实记）**：`git rm` **不会**把内容从仓库**历史**里删掉——那 26 个文件仍在历史中，要真正抹除得用 `git filter-repo` 重写全部 commit SHA，本仓所有既有 SHA 引用（README / issue / 证据）都会失效，故**不做**。

机械校验：[`code/tools/validate_trash_isolation.py`](../../code/tools/validate_trash_isolation.py)（§六 第一道检查即上述规则；另含废弃术语残留与链接检查）

## 七、Git 工作流

**提交**

- **小步提交**：完成一个独立文档、一个可运行脚本或一批关联修改即提交，不等"全部做完"
- **按主题分批**：不同子系统的改动分开提交
- **提交信息用中文**，格式 `类型: 描述`：
  - `feat:` 新功能/新系统 · `docs:` 文档 · `sim:` 模拟脚本 · `fix:` 修正 · `refactor:` 结构重组 · `chore:` 杂项

**分支**

- `main` — 唯一真相源，永远可发布
- `feat/<功能名>` — 新子系统或大规模重构
- `exp/<实验名>` — 不确定方向的实验

**危险操作**（`git reset --hard` / `git rebase` / `git push --force`）必须先确认。
