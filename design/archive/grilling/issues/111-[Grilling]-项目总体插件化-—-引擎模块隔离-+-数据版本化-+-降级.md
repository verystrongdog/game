## 正文

## 话题

探讨将当前 DSH harness 的「一切都是插件」哲学应用于项目引擎/知识架构的总体方向：引擎模块隔离（某部分出错不影响其它功能）+ 数据版本化与可换实现（过时设计数据不阻塞进度）。本 issue 为讨论锚点，供新窗口继续。

## 背景与动机

### 触发点 1：issue 讨论内容跟不上项目进展（#35 引出的教训）

#35（战斗输出权重校准）启动时发现，跨 14 个 grilling 推迟聚合的待校准参数清单，其引用链大量过时：

| # | 失效模式 | 实例 |
|---|---------|------|
| 1 | 公式被替换，推迟项悬空 | w_perception/w_execution 依附的 #32 §八 原表已被 2026-08-13 #33 修订淘汰（速度权重移到合成层 w₁/w₂/w₃=1/3），term_registry 条目过期 |
| 2 | 快照引用未随修表更新 | CalibrationConfig.NpcHp=15 注释引旧敌人表（轻度 12-18），F-5 权威表已改 20-30 |
| 3 | 术语漂移，同名异物 | 「情境强度系数」（#75 推迟行）在活跃正典中零命中，实际落地为 #108 Q7 的 strength 双档/s_neg |
| 4 | 引用链内部矛盾 | #88 裁决「#35 是战斗域，记忆数值不推 #35」vs #90 却把 κ/θ_g（记忆勾起）推给 #35 |

**根因**：同一事实被复制到多个存储点（正典参数速查表 / term_registry / CalibrationConfig / 决策树 / issue body，最多 5 处），靠人工同步——多源复制是结构，漂移是必然；任何"事后检查"（validate_params 等）都只是给必然的漂移打补丁，每种新失效模式要新设计一种检查（打地鼠）。

### 触发点 2：用户联想 harness 插件特性

用户观察：当前使用的 harness 声称"一切都是插件"——插件崩溃/热换不影响宿主，插件按版本协商、坏插件可被替换/mock，其它插件不受牵连。这恰好对应两个诉求：

1. **引擎某部分出错，其它功能不受影响**（隔离性 + 契约边界）
2. **过时设计数据不干扰进度**（版本化依赖 + 可换实现）

## 已有讨论摘要（2026-08-31 会话，决策树/文档未写入，待本 issue 讨论定案）

### 方向 1：知识新鲜度治本 = 单一事实源 + 生成视图 + 历史/现状分层

- 每个事实只有一份权威拷贝（data/params.json 或扩展 term_registry）；其余位置（CalibrationConfig 数值区、正典参数速查表、term_registry.numerical_locations）为**生成产物**，禁止手抄
- issue/决策树 = 不可变历史，只溯源、不承担事实职责；现状只从现状层读取
- 项目已有先例：`gen_modulation_ceiling_v2.py` 从同一数据同时生成 JSON + 速查表 md（该表从未漂移）；引擎数据全部走 GameDataLoader 读 JSON——**唯一例外是 CalibrationConfig.cs 手写常量**（#35 暴露漂移的地方）
- 边界：只覆盖可结构化知识（数值/结构/引用/状态）；语义层（设计意图、叙事）仍由正典文档承载

### 方向 2：插件化 = 隔离层（与方向 1 正交互补）

- **可转移**的 harness 特性：隔离性、契约边界、版本化依赖、可换实现/mock
- **不可 1:1 转移**：HMR 运行时热替换（Unity 是编译期装配，对应编辑器迭代，不是运行时机制）
- 项目已有种子：IResponseResolver 等接口缝（#70 F-4）、#103 消费分级（PLACEHOLDER 只读 OK / 正式消费 fail-fast）、#104 结构实现+PLACEHOLDER 分级（当年 m_field 占位全 0 阻塞 P2 数周）、#106/#110 fail-fast、CLAUDE.md 自动发现机制（目录级匹配）
- **契约形态提案**：

```csharp
interface ICombatModule {
    SchemaVersion SupportedDataVersion { get; }   // 声明我消费的数据版本
    ModuleStatus  Status { get; }                  // Ready / Degraded(reason) / Unavailable
    ModuleOutput  Step(ModuleInput input, CombatContext ctx);  // 自有状态，只经契约 IO
}
```

  - 数据版本化：模块声明支持版本 → 加载器协商（拒绝 or 自带兼容层，带标记）
  - 降级协议：模块失败 → Status=Degraded + 输出标 unavailable → 消费方**显式**处理（不消费该输出 → 战斗继续；消费 → 明确诊断）
  - mock/引用实现：未校准数据用 mock（带 PLACEHOLDER 标记），正式数据就绪换真实现——不碰其它模块
  - 敌我同构天然兼容（同一注册表，两种配置）

### 核心张力（必须拍板的哲学决策）

**fail-fast（现状哲学：#103/#106/#110——坏数据即停，防污染正式消费）vs 边界降级（插件化——坏模块标记继续，保进度）**

| 选项 | 语义 | 评价 |
|------|------|------|
| A | 全量 fail-fast（现状） | 保护正式消费，但坏数据全局停、阻塞进度 |
| B | 全量边界降级 | 保进度，但正式消费可能被污染 |
| **C（推荐）** | **分级混合**：模块自声明消费等级——正式数值消费（伤害/SAN 结算）fail-fast；开发期/结构性消费（情境/月光场/数据驱动模块）边界降级带标记 | 坏一个模块开发照跑，正式结算不撒谎；#103 消费分级的推广形态 |

### 风险边界（不吹）

- 确定性契约：插件加载顺序/版本协商必须确定，不破坏「同 seed 同输出」（#71 契约）
- 复杂度成本：建议只做「接口 + 版本声明 + 降级协议」，不做运行时装配
- 与单一事实源是**两个正交轴**：单一事实源消灭漂移（事实层），插件化控制爆炸半径（隔离层）——互补不互斥
