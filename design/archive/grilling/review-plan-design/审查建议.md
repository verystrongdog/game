### Dry-run 小结

方案自身的 7 个核心规则段落中：
- **2 个 ❌**（排序算法未定义、H→9列映射未定义、半径扩张状态追踪依赖持久化体系）
- **5 个 ⚠️**（疾病文件判定、拉入边界、值域叉乘配对、类型闭合判定标准、半径扩张触发）
- **0 个 ✅** 完全闭合

方案提出的方法论是自洽的——trace table 确实暴露了方案自身的规格缺口。但这也说明：方案目前处于"概念模型完整，操作步骤有断层"的状态。

## 二、缺口汇总

按严重度排序：

| # | 位置 | 严重度 | 描述 | 建议 |
|---|------|--------|------|------|
| 1 | §七-2 | ❌ | **排序算法未定义**。"按数据流依赖排序"没有给出判定数据依赖的具体规则。 | 定义最小依赖判定规则集。例如：frontmatter `父类: X` → X 在子文件之前；`[引用](path)` → path 在引用方之前；JSON 数据文件 → 在引用它的 md 之前。无法判定的依赖 → 保留原始顺序，标注"依赖未解析"。 |
| 2 | §七-3 | ❌ | **H1-H6 → 9 列 trace table 的映射方法不完整**。方案定义了发现"值得 trace 的段落"的方法（H1-H6），定义了记录结果的格式（9 列），但中间的关键步骤——"从一段自然语言文本中推导出输入类型、变换逻辑、输出类型、消费者"——没有任何操作指南。 | 补充一个 §三-B "从标注到 Trace" 的段落。为每个 H 给出列填充策略。例如 H3（数据变换）→ "变换"列填 md 原文中的变换描述，"输入·类型"列从变换的上文寻找数据定义，"输出·类型"列从变换的下文寻找产出描述。至少给一个完整的 worked example。 |
| 3 | §六 | ❌ | **半径扩张依赖"状态变更"追踪，但 v1 是一次性 AI skill，没有状态持久化机制**。方案说"判定从 ❌ 变为 ✅ 时触发"，暗示 review-plan 是一个持续运行的审查系统，但实际 v1 是每次调用独立的。 | 两个选择：(a) v1 中半径扩张改为"每次 trace 时，如果一个 ❌/⚠️ 行被修复（设计者改了文档），审查者手动触发 re-trace 该行的所有消费者"；(b) 去掉状态变更条件，改为"任何标记为 ❌ 或 ⚠️ 的行，必须在缺口汇总中列出其输出·消费者，作为待复查清单的一部分"——即半径扩张 = 强制列出消费者，不等状态变更。推荐 (b)，符合 v1 的一次性调用模式。 |
| 4 | §七-1 | ⚠️ | **"涉及疾病文件"的判断标准未定义**。 | 加一条明确规则：文件路径匹配 `design/entities/diseases/**/*.md` → 涉及疾病文件；或文件 frontmatter 含 `疾病:` 字段 → 涉及。 |
| 5 | §七-1 | ⚠️ | **H1 自动拉入被引用文件的边界未定义**。拉入深度（一级？递归？）、循环引用处理、拉入上限（防止拉入整个项目）均未指定。 | 设定深度上限（建议 1 级——只拉入直接引用，不递归）和数量上限（建议最多 5 个额外文件），超出时标注"未拉入"并继续。循环引用通过 visited set 处理。 |
| 6 | §七-3 | ⚠️ | **Trace 粒度未定义**。一份 md 文件应该产生多少行 trace？每段？每条规则？每个数据变换？ | 以"语义上独立的数据变换"为一行。具体：H3 触发的每个变换 = 1 行；H2 触发的每个枚举定义 = 1 行（变换 = "定义值域"）；H4 的每个分支段落 = 1 行；H1 的跨文件引用 = 生成引用连接行（输入=被引用方，变换=引用解析，输出=引用方可用的数据）。 |
| 7 | §四 | ⚠️ | **9 列中的"输入·类型"和"输出·类型"在 md 上下文中没有类型系统支持**。代码有 `int`/`string`/`List<Foo>`，md 中的"类型"是什么？是枚举值列表？是语义描述？ | 为 md 上下文定义简化类型系统。建议用 4 种类型标签：`枚举<T>`（值域列表）、`数值`（含范围）、`引用`（指向其他文件/段落）、`文本`（无约束字符串）。每种标签的"已定义"标准不同（枚举=列出所有值、数值=有上下界、引用=目标存在、文本=有格式/长度约束）。 |
| 8 | §七-3 | ⚠️ | **值域叉乘的组合爆炸没有上限**。N=5 输入 × M=4 分支 = 20 组合，尚可。N=20 × M=10 = 200 组合，AI 会开始遗漏。 | 设定叉乘上限：N×M > 50 → 采样检查（随机 20 组 + 边界组合 + 典型组合），剩余标注"未穷举"。 |

## 四、建议补充的内容

### 4.1 缺失：Worked Example

方案中最关键的一块缺失是**完整的 worked example**。§八的示例 trace table 只有 2 行且全是省略号。建议用方案自身（或一个已有疾病文件）做一次完整 trace，出 15-20 行 trace table，展示：

- H1-H6 各触发一次的真实案例
- 值域叉乘的具体过程
- 一条完整数据链从源到消费者的追踪
- 一个真实的 ❌ 缺口 + 半径扩张 + 复查

### 4.2 缺失：v1 Skill Prompt 的核心指令设计

方案在 §十说 v1 是"纯 AI Skill"，但方案本身是"方法论描述"而非"可执行的 skill prompt"。

建议补充一个附录：`SKILL.md` 的核心指令草稿。至少包含：

- 模式切换指令（见上面 #11）
- 9 列表格的列含义（一行一句，AI 逐列自查用）
- H1-H6 的触发检查——一句话版（如 "H1: 看到 `[xxx](path)` → 标记跨文件引用，拉入 path"）
- 停止条件自检（trace 完成一行后，检查 4 个"不能停的信号"）
- 输出格式模板

### 4.3 缺失：与现有审查产物的关系

项目已有 5 轮 review（v1-v5），产物在 `.scratch/` 下。方案应说明：

- 已有的 review 产物是否用新方法重新审查？
- 新旧审查结果如何对照？（旧结果中的发现是否被新 trace table 覆盖？）

## 五、实现路线修订建议

### 当前问题

§十 v1 的起点是"直接写 SKILL.md"。但方案自身的 7 个核心段落 trace 结果：0 个完全闭合，2 个 ❌，5 个 ⚠️。这意味着**v1 skill 的实现者拿到方案后，会反复遇到方案未定义的判断**（排序怎么做？粒度怎么定？），需要在实现时自行填补——这正是方案自己批评的"修复是点状的，不做半径复查"。

### 建议修订

在 v1 之前插入一个 **v0 阶段**：

```
v0（本方案修订）— 填补操作断层
  - 补 worked example（首选目标：疾病目录中 1 个简单疾病文件做完整 trace）
  - 补排序规则（见缺口 #1）
  - 补 H→9列映射方法（见缺口 #2）
  - 补 md 简化类型系统（见缺口 #7）
  - 补 trace 粒度标准（见缺口 #6）
  - 修订半径扩张触发条件（见缺口 #3）
  - 补 SKILL.md 核心指令草稿（见 §4.2）

v1（不变）— 纯 AI Skill
  - 基于修订后的方案编写 SKILL.md
  - 用 worked example 作为 skill 的 few-shot 示例

v2+（不变）— AI + 脚本混合
```
