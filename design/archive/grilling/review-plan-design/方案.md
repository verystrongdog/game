# /review-plan — 基于符号执行的方案审查机制

> 对 md 方案/规格文档做符号执行审查，追踪数据从定义到消费的完整链路，找语义断层。
> 替代纯 pattern matching 式审查（"读文本→找不一致"）。

## 一、问题诊断

### 1.1 v1→v5 退化模式

五轮审查，每轮发现更深层问题，但审查方法始终是"读文本→找不一致"的 pattern matching：

| 轮次 | 典型发现 | 审查方法 |
|------|---------|---------|
| v1 | 计数错误、表格缺行、文件遗漏 | 表面一致性 |
| v2 | 残留引用、措辞修正 | 交叉文件比对 |
| v3 | YAML 解析升级、代码集成规格 | 代码级语义 |
| v4 | "异常"方向未定义、病理类型矛盾缺失 | 校验语义 |
| v5 | "净 m 方向"计算方法未定义、父类路径双约定矛盾 | 实现级语义 |

### 1.2 两个根因

1. **审查不做实现预演**。P0.3-A 说"比对净 m 方向与父类定性方向"，v4 补上了 ↑/↓/异常/null 四种语义的定义（解决了"异常没定义"），但没有往下追问："好，现在我有四条链路各有三级 m 值，你具体怎么算净方向？"——这一步追问需要假装自己在写 `_compute_net_direction()` 函数，而不只是读文本。

2. **修复是点状的，不做半径复查**。v4 #5 发现"异常方向未定义"→ 补了方向语义表。但没有问："方向语义表补完了，那计算方法呢？矛盾矩阵补完了，那非矛盾类型呢？P0.3 的 step 2 路径写对了没有？"

## 二、核心模型

### 2.1 符号执行（Symbolic Execution）

审查 = 对规格文本做符号执行。读到的不是自然语言，而是类型签名、数据流、控制流。核心动作是**写下每一步的输入类型和输出类型**——不是"读懂了就行"，而是"写出来了才算"。

**与 pattern matching 的区别**：

| Pattern Matching | 符号执行 |
|-----------------|---------|
| "这个字段有四种合法值 ✅" | "这四种值各自的消费者是谁？每种值在消费方的分支里都处理了吗？" |
| "这个函数描述了计算逻辑 ✅" | "输入类型是什么？输出类型是什么？中间每一步的类型变化是什么？" |
| "表格填满了 ✅" | "表格列之间的数据流能贯通吗？null 单元格的下游处理了吗？" |

### 2.2 限界验证（Bounded Verification）

借鉴 Alloy (Jackson 2012) 的方法论：不验证无限情况。对当前步骤涉及的实体（3-4 个文件 × 值域枚举 × 分支条件）做**叉乘完备性检查**。大多数设计错误在有限范围内就会暴露。

### 2.3 概念完整性

借鉴 Brooks《人月神话》：审查流程本身需要一个单一的核心模型来赋予概念完整性。所有检查规则都是"符号执行"这个模型的推论，不是散装的清单。

## 三、启发式规则 H1-H6

从 md 自然语言中识别"含数据流动、值得 trace"的规则段落：

| # | 触发信号 | md 中的形态 | 抓取内容 |
|---|---------|------------|---------|
| **H1** | 跨文件引用 | YAML `父类: xxx`、`[显示名](路径)`、`参考 xxx.md §N` | 消费方文件路径、被引用字段 |
| **H2** | 枚举/类型定义 | 列表 `↑/↓/异常/null`、表格中值域列、YAML 字段的可选值 | 完整值域枚举、是否有 null/其他兜底 |
| **H3** | 数据变换 | 含"计算/求和/取最大值/比对/转换/映射/归一化"的段落 | 变换的输入→输出类型、中间步骤 |
| **H4** | 分支/条件 | "如果…则…"、"当…时…"、表格中不同行有不同处理逻辑 | 分支条件、所有分支是否覆盖完备 |
| **H5** | 管道衔接 | 编号步骤（Step 1→2→3）、"上述结果传入…"、"基于上一步的…" | 步骤间数据类型传递 |
| **H6** | 表格数据列 | ≥3 列的表格，列中含数值/类型字段/文件路径 | 每列类型、值域范围、null 处理 |

### 不触发的情况

- 纯叙述/解释段落（"X 系统负责 Y 功能"——无数据流动）
- 纯设计意图/动机（"为什么选择 A 而不是 B"——无可 trace 结构）
- 已标记 `⚠️ 已废弃` 的段落
- 纯索引/目录列表

## 四、Trace Table 格式

9 列结构化表格，强制填写每一列。空白格 = 未验证 = 视为缺口。

| 列 | 追问的问题 | 空格的后果 |
|---|---|---|
| **#** | 步骤序号 | — |
| **规则** | 在追踪哪条规则？（格式: `文件名 §段落`） | 无法追溯 |
| **输入·来源** | 数据从哪个文件/字段/上一步来的？ | 不知道数据有没有定义 |
| **输入·类型** | 确切类型签名？值域枚举完整吗？ | v4 的"异常未定义"会漏 |
| **变换** | 这一步对数据做什么？（计算/比对/查表/分支） | 净方向计算方法未定义 |
| **输出·类型** | 产出的确切类型？所有可能返回值列出 | 返回值枚举不全 |
| **输出·消费者** | 谁在下一步消费这个输出？列出所有调用方（文件名+步骤号） | 修了这里不知道影响谁 |
| **边界** | 空输入/极端值/类型不匹配时怎么处理？ | null 穿透、除零、空列表 |
| **判定** | ✅完整 / ⚠️有疑点 / ❌有缺口 | 未验证 = 留空 |

### 列间关系

- **"输入·类型" ← "输出·类型"（上一步）**：上一步的输出类型必须等于下一步的输入类型，不匹配 = ❌ 类型断层
- **"输出·消费者" → 半径扩张**：修改了某行的输出类型后，必须去检查所有消费者的输入类型是否仍然匹配
- **"输入·类型"值域 × "变换"分支条件 → 叉乘检查**：N 种输入 × M 种分支 = N×M 种组合，逐一检查是否覆盖

## 五、停止条件

### 正常停止（满足任一）

1. **项目边界停**：数据源是项目外不可变的东西（YAML 规范、Python 标准库、IEEE 754）。但如果项目内调用了**非标准工具**（如自写的 `parse_frontmatter()`），要追进去。
2. **类型闭合停**：输入类型已定义 + 输出类型已定义 + 值域叉乘已覆盖 + 边界条件（null/空/越界）有处理。
3. **重复模式停**：与之前 trace 过的步骤同构（同样的输入→变换→输出模式，只差参数名），引用之前的 trace 结论。

### 不能停的信号（出现任一必须继续）

- 某步的输入类型或输出类型没写全
- 某步的变换逻辑有"计算/求和/映射/比对"但没有具体方法
- 某步的输出没有列出所有消费者
- 某步的边界条件有空白

## 六、半径扩张机制

修复一个缺口后，**必须**检查所有消费者：

1. 从 trace table 的"输出·消费者"列找到所有消费该输出的下游步骤
2. 对每个消费者重新 trace（从该行开始，到类型闭合或项目边界停）
3. 在 trace table 底部追加"待复查清单"

### 待复查清单格式

| 修复点 | 修复内容 | 受影响消费者 | 复查状态 |
|--------|---------|-------------|---------|
| Step N 输出类型新增 X | 值域从 {A,B} 扩为 {A,B,X} | Step M（`文件名`）, Step K（`文件名`） | 待复查 / ✅已复查 |

**触发条件**：任何一行的判定从 ❌ 或 ⚠️ 变为 ✅ 时，自动触发半径扩张。

## 七、执行流程

```
/review-plan <file.md> [file2.md ...]
  │
  ├── 1. 解析阶段
  │   ├── 读取所有目标 md 文件
  │   ├── 如涉及疾病文件 → 前置运行 validate_disease.py，
  │   │   将其 ERROR/WARNING 作为已验证基础层
  │   ├── 对跨文件引用（H1）→ 自动拉入被引用文件
  │   └── 用 H1-H6 标注所有规则候选段落
  │
  ├── 2. 排序阶段
  │   └── 按数据流依赖排序（数据源在前，消费者在后）
  │
  ├── 3. Trace 阶段
  │   ├── 逐条填 9 列 trace table
  │   ├── 每步做值域叉乘（输入值域 × 输出值域 → 所有组合是否覆盖）
  │   ├── 空白格 = 缺口 → 标记 ❌ 或 ⚠️
  │   └── 缺口产生时 → 列出受影响消费者 → 写入"待复查清单"
  │
  ├── 4. 半径扩张阶段
  │   └── 遍历"待复查清单"，逐项重新 trace
  │
  └── 5. 输出阶段
      ├── 写入 .scratch/review-trace-<日期>-<文件名>.md
      └── 终端打印摘要（总行数 / 缺口数 / 待复查数）
```

### 调用示例

```
/review-plan 实体/疾病目录/偏执型精神分裂症.md
/review-plan 实体/疾病目录/_父类/奖赏系统障碍.md 实体/疾病目录/双相障碍I型.md
/review-plan 方案.md
```

## 九、与其他工具的分工

原则：**格式/引用/参数 → 脚本做（确定性）；语义断层 → AI trace（需要理解）**。

| 工具 | 检查内容 | 与 review-plan 的关系 |
|------|---------|---------------------|
| `validate_disease.py` | 链路ID存在性/m范围/CGI-S一致性/域方向/病理类型矛盾 | 前置输入——trace 之前先跑，结果作为已验证基础层 |
| `validate_cross_refs.py`（#16 计划中，阶段 2） | 死链/断引用 | 同上 |
| `validate_params.py`（#16 计划中，阶段 3） | 参数合法范围 | 同上 |
| `/review-plan` | **语义断层**——类型闭合/分支完备/数据流贯通 | 在已验证基础层之上做符号执行 |

脚本不存在时，AI 在 trace 过程中一并检查格式/引用/参数层，并在 trace table 中标注。不推给不存在的工具。

## 十、实现路线

### v1（当前）— 纯 AI Skill

- 实现形式：`.claude/skills/review-plan/SKILL.md`
- 审查能力：AI 按本方案中的 H1-H6 + 9 列 trace table + 停止条件 + 半径扩张执行
- 输入：任意 md 文件
- 输出：`.scratch/review-trace-*.md`
- 前置输入：已有脚本（`validate_disease.py` 等）的输出

### v2+（未来）— AI + 脚本混合

- 跑 3-5 次审查后，统计 AI 反复漏的检查类型 → 固化为脚本
- 脚本输出 JSON 中间表示（借鉴 CommonSpec 的 SpecIR → SQLite 架构）
- 最终分工：脚本做确定性层（parse/格式/引用/参数）+ AI 做语义层（类型闭合/分支完备/数据流）

### 演化触发条件

- 同一类缺口被 AI 漏检 ≥ 2 次 → 为该类检查写确定性脚本
- 每次新增脚本后，AI prompt 中移除对应检查项，引用脚本输出即可
