## 🔴 阻塞级

### B1. 行 84 — 示例引用行号错误（致命）

> 原文：`规则/核心机制.md:205`：SAN ≥ 60 稳定（+1 认知槽），< 30 恐慌，= 0 随机行为

**事实核查**：
- `规则/核心机制.md` 第 205 行 = `### 3.3 响应速度`（NPC 响应时机，与 SAN 无关）
- SAN ≥ 60 稳定 = 第 **314** 行
- SAN < 30 恐慌 = 第 **316** 行
- SAN = 0 随机行为 = 第 **318** 行

**严重性**：这是文档自身的**招牌示例**——"正确的引用格式"。如果招牌示例本身就是错的，整个体系的公信力归零。而且这个错误还出现在 §3.2 Step 3 产物模板中（行 163），属于同一错误的二次传播。

**修正**：替换为正确的行号，或改为段引用格式 `规则/核心机制.md §5.1`（更稳健，行号随编辑漂移）。

**建议写法**：
```
`规则/核心机制.md:314` — SAN ≥ 60 稳定；:316 — SAN < 30 恐慌；:318 — SAN = 0 随机行为
```
或更稳健地：
```
`规则/核心机制.md` §5.1 — SAN ≥ 60 稳定，< 30 恐慌，= 0 随机行为
```

### B3. 行 61, 163, 215 — `memory/` 路径未定义

全文多处使用 `memory/xxx.md` 作为路径：
- 行 61：`memory/numerical-calibration-grilling-2026-07-31.md`
- 行 163：`memory/numerical-calibration-grilling-2026-07-31.md`
- 行 205：`memory/grill-brain-skill-tree-2026-07-27.md`
- 行 215：`memory/numerical-calibration-grilling-2026-07-31.md`
- 行 232：`memory: numerical-calibration-grilling-2026-07-31.md`

**事实核查**：
- 项目根目录下 `/home/dog/game/memory/` **不存在**
- 实际 memory 路径：`~/.claude/projects/-home-dog-game/memory/`
- CLAUDE.md 中用的也是 `memory/` 作为简写（通过 tool 上下文注入）

**问题**：这是写给另一个窗口（可能是另一个 AI 会话）参照执行的文档。那个窗口**不会**有 CLAUDE.md 的上下文注入来解析 `memory/` 这个简写。不加定义直接用，会造成"找不到文件"。

**修正**：在 §4.1 或首次出现处明确定义：
```markdown
> **路径约定**：本文中 `memory/` 是 `~/.claude/projects/-home-dog-game/memory/` 的简写。
> 所有 memory 文件的实际位置在用户 home 目录下的 `.claude/projects/<项目名>/memory/`。
```

### B4. 行 331 — 实施计划未确认目标 skill 文件现状

> 原文：将 §三 "Grilling 流程强化" 的新增步骤写入 Grilling skill 指令（`.claude/skills/grilling/`）

**事实核查**：`.claude/skills/grilling/SKILL.md` 当前内容仅 13 行，是一个极简的通用 grilling 指令。§三提出的强化流程（资料包声明、事实锚定、写入验证表、质量门禁等）远超当前 skill 的结构复杂度。

**问题**：文档只说"写入 skill 指令"，但未讨论：
1. 当前 skill 的 minimal 风格是否应该保留？
2. 强化检查点是否应该作为独立的 agent definition（如 `grilling/agents/qa-checker.md`）而非全部塞进 SKILL.md？
3. Skill 指令的长度限制？（SKILL.md 过长可能导致上下文膨胀）

**建议**：在阶段 1 中增加一行决策——"确认 skill 文件拆分策略（单文件 vs 多 agent）"，或至少加一个 TODO 标记。

### B5. 行 266-269 — 校验脚本与现有工具未整合

> `tools/` 下新增 5 个脚本：`validate_cross_refs.py`、`validate_params.py`、`validate_file_structure.py`、`check_grilling_quality.py`、`validate_json_schema.py`

**事实核查**：`tools/` 下**已有** `validate_cards.py` 和 `validate_disease.py`。这两个脚本没有统一的输出格式，也没有被列入本体系的整合计划。

2. 新老脚本的命名规范是否统一？（现有的用 `validate_` 前缀，但与新建议的 `check_grilling_quality.py` 命名模式不一致——`validate_` vs `check_`）

**建议**：统一命名前缀（全部 `validate_` 或建立命名分类），并增加一节"已有脚本迁移"说明哪些现有脚本需要适配新输出格式。

## 🟡 重要级

### S1. 行 63 — 示例使用已过时的数据

> 原文：`"link_legitimacy_matrix.json 有 228 条链路"`

**事实核查**：根据 git history（commit `2b15b1b`），链路矩阵已从 228 条更新到 **353 条**。

虽然这只是 §2.2 表格中的一个"引用示例"（不是对当前状态的断言），但作为质量保障文档，示例数据应该是真实的。新窗口的人看到这行可能真的去查文件验证，然后发现"228"不对，从而降低对整个文档的信任。

**建议**：改为 `353 条链路` 或改用不会过时的示例（如"约有 350+ 条链路"）。

### S2. 行 242-248 — 交叉引用示例的锚点可移植性问题

> 原文：`[核心机制 §八 可塑性巩固](../../../%E8%A7%84%E5%88%99/%E6%A0%B8%E5%BF%83%E6%9C%BA%E5%88%B6.md#八可塑性巩固)`

**问题**：Markdown 锚点生成规则因渲染器而异。GitHub 会将 `## 八、可塑性巩固` 转为 `#八可塑性巩固`，但其他渲染器（如某些 VS Code 插件、Pandoc）可能生成不同的锚点。这个示例作为"规范"给出，但没有警告锚点的渲染器依赖性。

**建议**：加一句说明——"锚点格式取决于目标渲染器（GitHub：去掉标点符号；其他：需验证）。如不确定，用 `§八` 段引用 + 文件路径，不用锚点。"

### S5. 行 130-148 — "资料包完整性声明"的容量假设未经验证

> Step 0 要求读取所有直接相关的设计文档，并输出"已读清单"+"未读但可能相关的文件"

**问题**：如果话题足够大（如"战斗系统全面重构"），"直接相关的设计文档"可能达到 10-15 个文件。在当前上下文限制下，读取所有这些文件后剩余的对话空间可能不足以完成 Step 3 的追问。

文档 §1.2 自己指出了"上下文窗口有限"——但 §3.1 的强化方案反而增加了上下文消耗。

**建议**：增加一条容量检查规则——"如果相关文件 > 5 个，优先读取索引文件（维度 .md），具体文件在追问到相关问题时按需读取。"或者区分"必须预读"和"按需读取"两个等级。

### S6. 行 258 — 校验脚本放在 `tools/` 但未说明执行环境

> 在 `tools/` 下新增以下脚本

**问题**：校验脚本需要扫描文件系统、解析 markdown、输出 JSON。没有说明：

### C4. 行 184 — 决策深度自检缺少"什么时候可以停"

> 当话题满足以下任一条件时，必须继续追问

**问题**：这是一个"何时不能停"的清单，但没有对应的"何时可以停"的条件。没有终止条件，理论上会无限追问。应该有互补的"满足以下全部条件时可以关闭话题"。

**建议**：增加终止条件——例如"话题的数值参数有来源依据 + 机制交互已检查与所有相关系统的冲突 + 跨维度影响已逐维确认 + 用户给出非单字确认"。

### C5. 行 339 — 阶段划分缺少时间估算

> 阶段 1（立即）→ 阶段 2（下一个工作块）→ 阶段 3（P1）→ 阶段 4（P2）

**问题**：没有估算每个阶段的工时。对于执行者（可能是另一窗口的人类或 AI），无法判断"下一个工作块"是多长时间。

**建议**：加一列预估工时（如"阶段 2：3-5 小时"），即使是粗略估算也比没有好。

## 正面评价

以下方面写得很好，值得保留：

1. **§1.2 根因分析**（行 33-40）："信息基础不可靠"的诊断一针见血。将知识来源分为"项目文件（ground truth）"和"训练数据（半可靠）"两个来源的框架干净、可操作。

2. **§2.1 "引用即读取"铁律**（行 50-52）：一句话清晰定义，没有歧义。适用/不适用的边界在 §2.2 中明确划分。

3. **§2.3 违规信号**（行 73-80）：列出具体触发短语（"根据我们之前的讨论..."）的自我检测方法非常实用。这是给 AI 自己的 rubbergrip——实际操作性强。

4. **§3.2 产物模板**（行 130-177）：资料包完整性声明、事实锚定格式、写入验证表——三个模板的结构清晰，可以直接复制使用。

5. **§5.4 统一输出格式**（行 296-322）：JSON schema 定义具体，blocker/warn/info 三级分类合理，`source_file` + `source_line` + `target` 字段设计完整。

6. **整体架构**：问题诊断 → 原则 → 流程 → 规范 → 自动化 → 路线 —— 逻辑链完整，从诊断到治疗的推进合理。
