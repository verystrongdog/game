## 一、重构目标

### 1.1 要建立的生产链

```text
当前可玩目标
  → 目标实际需要的设计
  → 有明确所有权的数据
  → 确定性的 C# Core
  → Unity 适配与呈现
  → 构建、试玩和反馈
```

重构成功的核心表现不是目录更整齐，而是：

1. 从根入口可以确定当前正在交付什么。
2. 设计声明、代码实现、系统集成和试玩证据不会混为“已完成”。
3. 同一事实只有一个权威来源。
4. 干净检出可以重复构建、校验和运行。
5. Unity 默认路径使用真实规则核，不复制玩法公式。
6. 历史和研究可以追溯，但不会自动进入当前工作上下文。
7. 重构结束后，仓库回到正常游戏开发，而不是长期维护重构体系。

### 1.2 非目标

- 不重新决定所有游戏机制。
- 不一次性搬迁全部中文目录。
- 不自动把最后修改的文档提升为正确设计。
- 不立即拆分为多个 Git 仓库。
- 不立即把 Core 拆成大量程序集。
- 不在锁定依赖时顺便升级 Unity、.NET、Python 或软件包。
- 不在普通重构提交中重写 Git 历史。
- 不以“文档已写完”替代可运行和可试玩证据。
- 不要求与当前切片无关的历史问题先全部解决。

### 1.3 约束重构范围的产品锚点

以下切片仅作为本方案的**候选范围锚点**，不是已获授权的玩法正典：

**CP-01 候选：住院楼 1F**

```text
夜间病房醒来
  → 进入短走廊
  → 遭遇一个同时具有 HP/SAN 的敌对实体
  → 使用真实 Core 完成物理攻击、防御、精神攻击
  → 到达护士站并结束切片
```

建议 must-prove：

- Unity 能通过适配层使用真实 Core 完成一次战斗闭环。
- 玩家能从 HUD 和反馈中区分 HP/SAN 与三种基础行动的后果。
- 探索、接敌、回合战斗和结束条件能形成一个连续体验。

明确排除完整技能树、完整 NPC AI、Boss、月相全系统、完整叙事、多角色和美术精修。

P3 必须由 owner 正式准入 CP-01 或用另一 Slice 替换它。准入前，它只能限制基础设施范围，不能授权新增玩家行为。

## 三、执行与状态模型

### 3.1 单线程约束

- 同一时刻只有一个 current playable。
- 同一时刻只推进一个主要成果或变更集。
- 若使用 Issue，同一时刻只有一个主要叶子 Issue 处于 `status:in-progress`。
- 一个阻塞当前成果的 Bug、Experiment 或 RFC 可以抢占；原工作必须先标记 blocked。
- 非阻塞发现进入候选队列，不在当前变更中顺手解决。
- 上一阶段未达到退出门禁，下一阶段不得开始。

Issue 是记录和准入载体，不是本地重构工作的目的。外部标签同步、Issue 编辑和自动化不属于本方案的隐式权限。

### 3.2 能力成熟度与健康状态

每项被当前切片消费的能力分别记录：

| 轴 | 合法状态 | 证据 |
|---|---|---|
| Design | `UNRESOLVED / CANDIDATE / ACCEPTED / SUPERSEDED` | 当前设计或短决策记录 |
| Implementation | `NONE / FAKE / PARTIAL / DONE_FOR_SLICE` | 源码和单元测试 |
| Integration | `ISOLATED / CONNECTED / E2E` | 集成测试、场景 trace 或构建 |
| Health | `UNKNOWN / PASS / REGRESSED` | 当前版本回归结果 |

试玩状态不对整项能力给总分，而对每条 must-prove 分别记录：

`UNTESTED / OBSERVED / SUPPORTED / REFUTED / INCONCLUSIVE`

所有状态必须绑定 Slice、build/commit 和证据。`DONE_FOR_SLICE` 只表示满足当前切片范围，不表示永久完成。

### 3.3 Issue 类型的最小用途

| 情况 | 类型 |
|---|---|
| 当前可玩目标 | Slice |
| 已接受玩家行为的实现 | Implementation |
| 明确且不决定新玩法的交付 | Task |
| 可复现行为违背已接受预期 | Bug |
| 玩家体验或技术可行性未知 | Experiment |
| 跨系统、难回滚的决定 | RFC |

实质修改 Issue 的范围、行为、证据标准或依赖后，必须返回 triage 重新准入。

### 3.4 阶段的两次闭合

1. **门禁闭合**：本阶段验收通过，可以进入下一阶段。
2. **消费闭合**：下一阶段成功使用本阶段产物，且没有暴露结构性错误。

门禁通过只说明当前证据支持继续前进。下游无法消费时，应回到产生错误假设的阶段修订，不能只在下游添加兼容补丁。

## 四、阶段通用处置流程

每个阶段执行以下最小循环：

1. 记录 base commit、工作树和前序门禁。
2. 在开始前列出允许变化和预期差分。
3. 建立改前复现、trace、hash、依赖图或体验假设。
4. 一个提交只做一种变化。
5. 每个提交运行快速相关检查；阶段退出运行全部适用回归。
6. 比较改前、改后问题集合和非预期 diff。
7. 在临时 worktree 或临时分支验证普通 `git revert` 能恢复上一状态。
8. 保存精简证据摘要并签出阶段。

问题差分采用：

```text
new_finding = after - mapped(before) - expected_delta
```

- `before` 必须能在 base commit 稳定复现。
- `expected_delta` 必须在阶段开始前登记。
- 本阶段产生的新问题不得事后倒填为“已知债务”。
- 阶段退出要求 `new_finding` 为空。
- 未运行、超时、工具异常和零测试不是通过；它们只阻塞实际依赖该能力的阶段或子门禁。

问题指纹使用：

```text
validator_id + rule_id + stable_subject_id + semantic_fingerprint
```

路径、行号和自然语言消息只作展示。发生搬迁时，P6 必须先建立旧、新 subject 映射。

完整机器报告放 CI artifact 或被忽略的本地 artifact 目录；仓库只提交 `docs/engineering/evidence/` 下的精简结论。证据摘要至少包含 base/head SHA、工具版本、命令与退出码、问题差分、测试报告定位和回滚演练结论。

## 五、P0——冻结基线

### 5.1 实际工作

- 从准确的 `origin/main` commit 建立重构分支。
- 记录 tracked、untracked、ignored 和用户已有修改。
- 记录仓库文件、大二进制、依赖、构建入口和运行入口。
- 分别记录 .NET、Python、Unity 和校验工具的真实状态。
- 给现有问题建立稳定指纹。
- 建立可恢复的基线 commit 或 tag。

### 5.2 可能遇到的问题

- 本地分支落后远端或远端引用过期。
- 用户已有修改被混入重构。
- 检查命令本身写入状态文件或生成物。
- 当前机器缺少 `dotnet`、Unity Editor 或 Blender。
- 现有检查已经失败，无法获得全绿基线。
- Unicode、大小写和路径行为跨平台不同。

### 5.3 固定流程能解决什么

- Git 状态、commit、文件 hash、工具版本和失败输出可以机械记录。
- 工具缺失记录为 `NOT_AVAILABLE`，不得写成 PASS。
- 已有失败通过稳定 subject 和语义指纹登记。
- 会写工作树的命令先在临时 worktree 审计。

### 5.4 新种类问题怎么办

P0 不修业务问题。无法安全建立基线时停止：工具缺口进入 bootstrap Task；所有权不明的文件进入待分类清单；数据丢失、许可证或历史损坏风险按 K3 处理。

### 5.5 如何确定解决

- 能准确指出重构 base commit。
- 所有检查都有真实状态。
- 相同基线重复执行得到相同问题指纹。
- 用户原有修改保持不变。

### 5.6 如何确定没有新增问题

- 基线前后 `git status` 和 tracked-file hash 一致。
- 业务文件没有语义 diff。
- 临时回滚演练能恢复相同问题集合与 hash。

### 5.7 阶段输出

基线证据摘要、已知问题集合、工具可用性清单和回滚点。

## 六、P1——治理复位与目标骨架

### 6.1 实际工作

- 新建精简 `AGENTS.md`，作为唯一通用 Agent 约束。
- 将 `CLAUDE.md` 退役为兼容指针，不再拥有独立规则。
- 建立 `WORKFLOW.md` 和 `PLAYABLE.md` 空骨架。
- 建立第二节所列目标目录的最小空骨架或 README；不移动旧业务内容。
- 将人类协作和提交约定保留在 `CONTRIBUTING.md`。
- 仓库内 Issue 模板仅链接工作流，不复制解释。

远端标签、Issue 内容和自动化同步是独立外部操作，需要显式授权，不作为 P1 本地门禁。

### 6.2 可能遇到的问题

- 删除旧规则时丢失仍有效的安全边界。
- `AGENTS.md` 成为新的巨型总纲。
- 多个入口继续复制同一规则。
- 不同 Agent 工具无法加载同一入口。
- 治理文件继续包含玩法参数或历史设计。
- 为了让当前任务合规而临时修改流程。

### 6.3 固定流程能解决什么

- 为旧 `CLAUDE.md` 建立逐项处置表：保留、迁移、过时、删除理由。
- Agent 入口只允许仓库目的、安全边界、权威入口和标准命令。
- 对已知个人绝对路径、自指规则、玩法参数表和自动外部写操作做模式扫描，再人工复核命中。
- 用 Bug、Experiment、Implementation 和小型 Task 四类场景检查本地路由。

### 6.4 新种类问题怎么办

新 Agent 加载方式不兼容时先做最小实验，不复制整套规则。现有工作类型无法表达时阻塞当前工作，通过 RFC 判断是否需要修改流程。流程本身有缺陷时，与当前业务修改分开处理。

### 6.5 如何确定解决

- 旧规则处置表没有去向未知项。
- Agent 入口不含玩法参数、自指规则和自动外部写操作。
- 工作流只有一个解释来源。
- 代表性工作可以被一致路由。
- 治理入口链接有效。

### 6.6 如何确定没有新增问题

- P0 的玩法代码、数据和运行结果不变。
- 治理变更独立提交并可独立回滚。
- 两个不同任务场景可以只读找到相同权威入口。

### 6.7 阶段输出

精简 Agent 入口、本地工作流骨架、目标目录骨架和旧规则处置表。

## 七、P2——建立最小可信校验

### 7.1 实际工作

- 先修复统一检查入口的假绿、漏跑、零测试和写工作树问题。
- 为 runner 建立 pass、fail、error、timeout、skip 和 zero-tests 夹具。
- 建立 validator 机器注册表，核对磁盘发现集合。
- 让根入口和声明为 current 的文档进入链接检查。
- 本阶段只建立后续重构需要的可信检测，不要求修复所有历史内容。

依赖锁、完整 CI 和 Unity 资产身份不在本阶段一次完成；它们在 P4 对应子门禁按实际依赖建立。

### 7.2 可能遇到的问题

- Validator 崩溃但 runner 返回成功。
- 新 validator 没有登记。
- 局部数学符号被误判为全局参数冲突。
- 检查器写 `.scratch`、缓存或输出。
- 没有发现测试却被视为通过。
- 历史红项淹没 current 内容。

### 7.3 固定流程能解决什么

- 磁盘发现的 active validator 必须与注册表一致。
- 运行前后比较工作树和 tracked-file hash。
- 假绿、假红、异常和零测试使用合成夹具验证。
- 参数校验使用域限定 ID；局部显示符号不承担全局唯一性。
- Current 与 historical 扫描范围分开报告。

### 7.4 新种类问题怎么办

现有门禁检测不到但问题可复现时按 K1：先增加失败夹具，再修复。Validator 无法判断设计语义时停止自动裁决，按 K2 交给当前权威或 owner。

### 7.5 如何确定解决

- fail、error、timeout、required skip 和 zero-tests 稳定返回非零。
- 所有登记为 active 的 validator 恰好运行一次。
- 连续执行两次结果一致且工作树不变。
- 历史债务不会被错误报告为本阶段新增问题。

### 7.6 如何确定没有新增问题

- 故障注入证明已知错误可被捕获。
- `new_finding` 为空。
- P0–P1 回归通过。
- P3 可以依靠该入口验证权威地图和 Slice 文档，完成消费闭合。

### 7.7 阶段输出

可信的只读检查入口、runner 自测矩阵和 current/historical 分层报告。

## 八、P3——确定当前权威与可玩目标

### 8.1 实际工作

- 建立 `docs/canon/README.md` 权威地图，只保存路径、角色和状态。
- 明确产品承诺和少量跨域术语的权威位置。
- 识别仓库是否已经存在 owner 授权的 current playable。
- 若不存在，在 `PLAYABLE.md` 明确记录 `NO_AUTHORIZED_PLAYABLE`。
- 由 owner 准入 CP-01 候选或用另一 Slice 替换。
- 在 Slice 中记录成熟度、健康状态和 must-prove 试玩状态。
- 冻结六维完成百分比、追加式大决策树和 `.scratch` 的当前正典角色。

在没有已准入 Slice 时，可以继续明确的仓库维护和 bootstrap 工作，但不得新增正式玩家行为。

### 8.2 可能遇到的问题

- 把最后修改的文档误当作正确设计。
- 把旧方案、替代方向和部分实现压成一个当前答案。
- 为建立权威地图而试图审查全部历史。
- Slice 不断吸入完整技能树、NPC、月相、Boss 和叙事。
- 临时测试捷径被误写成正式正典。
- 用无法验证的“有趣”“自然”“合理”闭合设计。

### 8.3 固定流程能解决什么

- 只审查 Slice 实际消费的设计。
- 每条能力分别记录成熟度、健康状态和证据。
- Slice 固定 entry、loop、exit、must-prove、non-goals、cut-first、允许占位和创作判断者。
- 六维只检查遗漏，允许 N/A。
- 状态索引只链接，不复制参数和结论。

### 8.4 新种类问题怎么办

玩家是否理解或是否有趣进入 Experiment；Schema、存档、跨系统规则或不可逆内容生产决定进入 RFC；不阻塞关键路径的问题进入 future。历史和替代方案权威无法判断时保持 `UNRESOLVED`，由 owner 决定。

### 8.5 如何确定解决

- current playable 明确为一个已准入 Slice，或诚实记录不存在。
- 已准入 Slice 的起点、循环、终点、必须证明和裁剪线明确。
- 关键路径上没有 `Design=UNRESOLVED`。
- 未被 Slice 消费的系统不进入本轮实现。

### 8.6 如何确定没有新增问题

- 权威图没有循环或两个并列规范来源。
- Slice 外设计没有被无意修改。
- Scope 实质变化后返回 triage。
- P4 能只凭权威地图和 Slice 找到所需上下文。

### 8.7 阶段输出

权威地图、`PLAYABLE.md`、已准入 Slice 或明确的无 Slice 状态，以及绑定证据的状态表。

## 九、P4——打通最短可信运行链

P4 由四个串行子门禁组成。每个子门禁独立提交、独立验收和独立回滚；前一个未闭合，后一个不开始。

### 9.1 P4a——锁定当前切片所需环境

**实际工作**：锁定当前 .NET、Python 和 Unity 版本及直接依赖；建立只覆盖当前切片关键路径的最小 CI。不在锁定提交中升级。

**常见问题**：锁文件只在开发机有效；缓存掩盖漏声明依赖；Unity job 因许可证跳过；Blender 依赖污染普通 Python 环境。

**固定处理**：各生态分提交；空缓存和干净检出验证；required aggregate 检查 job 真实结论；Blender 环境独立。

**新问题**：`NOT_AVAILABLE` 只阻塞依赖该工具的子门禁。Unity 不可用不阻塞数据 ownership，但会阻塞 P4b、P4d 和 P5。

**解决判据**：当前切片需要的环境可以按锁文件恢复；未声明依赖显式失败；应运行的 CI job 没有被静默跳过。

**无新增问题证据**：锁定前后行为测试一致；cache-on/cache-off 结果一致；P0–P3 回归通过。

### 9.2 P4b——建立 Unity 资产身份

**实际工作**：用锁定 Unity 版本生成并提交必要文件和目录的 `.meta`、`packages-lock.json` 与 ProjectSettings；锁定 Visible Meta Files 和 Force Text。

**常见问题**：GUID 重建；场景引用表面编译成功但实际断裂；不同 Editor 版本批量重写资产；二进制继续无治理增长。

**固定处理**：建立 meta 配对和 GUID 清单；版本不一致时停止；资产与 `.meta` 同提交；文本资产和大二进制使用不同 Git 策略。

**新问题**：GUID 冲突或引用来源不明时整批回滚；许可证和不可恢复资产按 K3 处理。

**解决判据**：meta 配对完整；GUID 稳定；ProjectSettings 和包锁与实际 Editor 一致；干净检出后 Unity 能识别相同资产身份。

**无新增问题证据**：建立前后资产清单、GUID 集合和场景引用 smoke 一致。

在 P4b 完成前，不继续提交新的 Unity 场景、Prefab、Animator Controller 或其他序列化资产。

### 9.3 P4c——建立数据契约

**实际工作**：以当前 Slice 实际数据闭包为范围建立 runtime allowlist、ownership manifest、Schema、跨文件语义检查和单一生成 pipeline。

数据属性必须正交记录：

| 字段 | 值 |
|---|---|
| origin | `authored / generated / external` |
| lifecycle | `active / deprecated / archived` |
| role | `runtime / generator-input / reference / evidence` |
| shipping | `true / false` |

另记录 logical ID、schema version、owner、inputs、generator、runtime consumers 和 provenance/license。

**常见问题**：手工语义被生成器覆盖；同一输出多个写入者；Schema 只验形状；时间、路径和随机顺序进入生成物；Python/C# 接受规则不同；legacy 被 glob 纳入运行时。

**固定处理**：先 inventory 后移动；runtime 只用 allowlist；Schema 与语义检查分工；临时目录双生成；Python/C# 共用合法与非法 fixture。

**新问题**：所有权不明时阻塞对应文件；跨系统语义冲突进入 RFC；不得靠默认值掩盖未知。

**解决判据**：当前 Slice 数据闭包中每个文件属性和 owner 明确；生成两次结果一致；跨语言接受/拒绝集合一致；runtime 不含 reference 或 archived 数据。

**无新增问题证据**：比较旧、新 loader 产生的数据对象；`generate --check` 零 diff 且不写工作树；P0–P4b 回归通过。

### 9.4 P4d——建立 Core→Unity 接缝

**实际工作**：定义 command、snapshot、domain event 和错误语义；保留 `IDemoSolver` seam，用真实 Core adapter 一次桥接一个 use case；正式 Runtime 与 Prototypes 分开。

**常见问题**：Unity 复制 Core；RNG、浮点、排序、序列化或事件顺序分叉；Core 使用 Unity 不支持的 API；帧生命周期进入确定性规则核；Core 缺失时静默回退白盒。

**固定处理**：共享 scenario fixture 和 seed；建立 characterization test；adapter 只转换输入输出；字段级定义精确比较或容差；先做编译 spike 再决定同源包或 DLL。

**新问题**：兼容路线未知时先 Experiment 后 RFC；玩法语义需要改变时退出 Task，另行决策；禁止在 adapter 中暗中裁决。

**解决判据**：Core 不引用 Unity、Console 或具体文件路径；Unity 默认调用真实 Core；相同数据、请求和 seed 产生相同事件顺序与结果；版本缺失或不符时显式失败。

**无新增问题证据**：跨运行时 golden trace、Core 依赖扫描、Unity 编译及 EditMode/PlayMode 结果、P0–P4c 回归全部通过。

### 9.5 P4 阶段输出

可恢复环境、稳定 Unity 资产身份、当前 Slice 数据契约和使用真实 Core 的最短 Unity 运行链。

## 十、P5——实现并试玩当前切片

### 10.1 实际工作

- 按玩家路径实现已准入 Slice，而不是按目录或系统完整度实施。
- 提交可直接启动的入口场景，不要求作者先运行编辑器菜单临时生成。
- 打通探索、接敌、真实回合、HUD 和结束条件。
- 将假实现、临时捷径、允许缺陷和替换条件集中记录在 Slice。
- 对 must-prove 执行无引导试玩，观察事实与设计解释分开记录。

### 10.2 可能遇到的问题

- 各组件单独完成但没有端到端游戏。
- 调试场景、假 HUD 或简单 AI 成为默认实现。
- 精确参数再次散落到文档、Core 和 Unity。
- 作者现场解释污染试玩。
- 单个玩家意见被直接改写为正典。
- 技术缺陷、可用性摩擦、信息误解和设计无效混在一起。

### 10.3 固定流程能解决什么

- 每项变更反向追踪到 Slice requirement。
- 精确值只进入既定机器权威。
- 固定输入序列产生可比较事件 trace。
- 先测无引导可完成性，再测预先写好的体验假设。
- 观察、玩家陈述和 owner 判断分别记录。

### 10.4 新种类问题怎么办

阻塞完成路径的缺陷进入 Bug 并抢占。重复体验误解进入单个 Experiment 回路。改变规则、Schema 或边界的修正进入 RFC。切片未闭合前不得开始下一切片。

### 10.5 如何确定解决

- 干净检出后可通过一个文档化入口直接启动。
- 玩家能从 Slice 入口到达出口，无阻塞缺陷。
- 关键能力达到 `Design=ACCEPTED`、`Implementation=DONE_FOR_SLICE`、`Integration=E2E`、`Health=PASS`。
- 每条 must-prove 有绑定具体 build 的 `SUPPORTED / REFUTED / INCONCLUSIVE` 结论。
- 默认玩家路径不使用 Whitebox 或未声明 fake。
- Owner 明确选择接受、继续迭代或放弃，而不是因“代码完成”自动晋升。

建议初始试玩标准：三名不了解设计的试玩者中至少两名能够无作者口头指导完成入口到出口，并在一次遭遇后区分 M1/Broca 与 HP/SAN，说明一次选择的后果。该标准须由 Slice Issue 正式确认后生效。

### 10.6 如何确定没有新增问题

- Core 单元、数据契约、Unity 集成和场景 smoke 全部通过。
- 修复前后使用同一试玩任务复测。
- 无法追踪到 Slice 的改动不进入本阶段。
- 试玩引发的规则变化回写唯一权威并增加相应验证。
- P0–P4 回归通过。

### 10.7 阶段输出

绑定 build 的 playable、试玩记录、owner 判断、已知缺陷和下一轮决策。

新 playable 晋升后，旧 playable 转为 regression slice，保留端到端 smoke。只有相关依赖、规则或玩家路径变化时才重做对应试玩。

## 十一、P6——按消费迁移仓库内容

### 11.1 实际工作

- 只迁移已被 P5 切片消费的设计、数据、工具和实验。
- 每次移动一个依赖闭包。
- 当前设计逐步迁入第二节定义的目标结构。
- Python 生产工具与数值实验分离。
- 纯路径移动与设计、代码、公式语义修改分开提交。

### 11.2 可能遇到的问题

- Markdown 链接、Python import、C# 路径和 CI path filter 断裂。
- Unicode、空格、URL 编码和大小写只在部分平台失败。
- Unity 资产移动时 GUID 改变。
- 相对链接更新导致 byte hash 变化，被误判为语义修改。
- Git 将移动识别为删除和新增。
- 脚本依赖当前工作目录。
- Archive 或旧路径继续成为第二正典。

### 11.3 固定流程能解决什么

- 移动前生成 `old_path → stable_subject_id → consumers` 清单。
- 二进制和未修改源码要求 byte hash 相等。
- 因路径变化而修改的文本使用机械变更白名单或规范化结构比较。
- Unity 单独比较 `.meta` GUID，不用文件 hash 代替。
- `git mv` 后从仓库根、子目录和绝对路径入口验证工具。
- 索引只保存路径、状态和 owner，不复制正文。

### 11.4 新种类问题怎么办

发现未登记消费者时整批停止，补全依赖闭包后重来。路径背后存在语义冲突时保持原位，另开 Experiment/RFC。GUID 无法保持时整批回滚。外部工具要求固定路径时先增加配置或适配入口。

### 11.5 如何确定解决

- 未修改文件搬迁前后 byte hash 一致。
- 路径修订文本只有白名单内的结构变化。
- 已登记消费者全部改用新路径。
- 文档链接、Python import、C# build、数据加载和 Unity 编译通过。
- Unity GUID 集合保持不变。
- 旧位置不再被 current 规格或运行时依赖。

### 11.6 如何确定没有新增问题

- 每个提交运行快速相关检查，阶段退出运行所有适用前序门禁。
- 比较移动前后行为 trace、数据 hash 和 playable smoke。
- 在临时 worktree 回滚该批提交后恢复上一状态。
- 下一次真实修改只使用新路径，完成消费闭合。

### 11.7 阶段输出

小批量、可回滚的迁移提交，旧新 subject 映射，以及无规范性重复的 current 结构。

## 十二、P7——归档、瘦身与退出重构

### 12.1 实际工作

- 将 `.scratch` 内容分为正式资产、证据和历史。
- 冻结追加式大决策树，建立轻量主题索引和 supersedes 关系。
- 通用 Agent skills 移出默认项目上下文，只保留真正项目专用能力。
- 研究资料补充来源、许可、用途和支持的决定。
- 废弃内容进入 archive，不再被运行时或 current 规格消费。
- 为大二进制建立 Git LFS 或外部存储策略。
- 用一个普通设计工作和一个普通工程工作试运行新结构。

### 12.2 可能遇到的问题

- `.scratch` 或决策树包含唯一有效规格。
- 运行时仍读取准备归档的数据。
- Archive 改名后继续承担第二正典。
- 研究材料无法从 Git 或外部来源恢复。
- 许可证不清的资产进入发布路径。
- LFS pointer 存在但远端对象缺失。
- 历史重写破坏所有 commit SHA。
- 新流程只适合重构任务，正常开发仍依赖口头知识。

### 12.3 固定流程能解决什么

- 每项执行“提升为正式资产 / 保留为证据 / 归入历史”三分流。
- 归档前扫描 current 引用、运行时依赖和工具输入。
- 先移动和验证恢复，再考虑删除工作树副本。
- 外部资产记录 checksum、来源和许可证。
- LFS 初期只约束新增资产；历史迁移另立 K3 维护事件。
- 用两类正常工作验证新结构，而不是继续写治理文档。

### 12.4 新种类问题怎么办

无法确认资料是否唯一时保持原位。许可证、所有权、远端 LFS 或备份不确定时按 K3 停止。正常任务仍需历史文件，说明 P3 或 P6 未闭合，应回到对应阶段修复。

### 12.5 如何确定解决

- 默认开发无需读取 decision tree、research、archive 或 `.scratch`。
- Current 代码、数据和规格不依赖 archive。
- 抽样历史材料可以恢复，且不会被误认成当前规则。
- 干净 clone 能取得必要资产、构建并运行 current playable。
- 普通设计工作和普通工程工作都不需要特殊口头解释。

### 12.6 如何确定没有新增问题

- Current playable 全套自动验证与 smoke 通过。
- Active→archive 移动保留 subject 映射和 hash。
- 执行抽样恢复演练。
- 若采用 LFS，验证远端对象、干净 clone 和资产导入。
- 所有适用前序门禁通过，后续正常开发成功消费新结构。

### 12.7 阶段输出

可追溯但不污染默认上下文的历史和研究区、大文件策略、正常工作试运行报告、明确债务，以及正式关闭的重构主线。

## 十三、新种类问题升级机制

| 等级 | 定义 | 处置 |
|---|---|---|
| K0 已知机械问题 | 已有检测器和处理方式 | 当前阶段修复并运行相关与阶段回归 |
| K1 新检测缺口 | 可复现、局部、可逆，但当前门禁检测不到 | 先增加失败夹具或 detector，再修复 |
| K2 权威或语义冲突 | 无法判断哪个文件、设计或行为正确 | 阻塞当前阶段；建立事实表，通过 Experiment/RFC 和 owner 决定 |
| K3 不可逆或外部风险 | 删除、历史重写、许可证、资产丢失、远端不可恢复 | 硬停止；先验证备份和恢复，再取得明确授权 |

固定升级顺序：

```text
发现
  → 停止扩大当前修改
  → 保存最小复现和现场证据
  → 判断边界与 K0–K3
  → 必要时增加失败测试
  → 必要时进入 Experiment/RFC
  → 实施最小修复
  → 新测试转绿
  → 重跑适用前序门禁
```

首次特例不直接成为全局规则。只有在另一个独立任务中再次出现，或首次出现就暴露高影响安全边界时，才考虑修订工作流。工作流修订必须与触发它的业务修复分开。

## 十四、问题解决与无回归判据

### 14.1 按问题类型判定解决

| 类型 | 解决证据 |
|---|---|
| Bug | 修复前稳定失败；修复后通过；有回归测试和受影响范围检查 |
| Experiment | 得到支持、否定或证据不足的结论；原型去向明确 |
| RFC | 真实选项、代价、回滚和 owner 决策完成；必要实施工作已建立 |
| Task | 交付物存在、接入目标位置、直接验证和阶段回归通过 |
| Implementation | 玩家可观察行为符合已接受设计，并进入指定 build/场景 |
| Slice | 玩家能从入口到出口；must-prove 有试玩证据；owner 决定接受、迭代或放弃 |

代码写完、文档写完、测试文件存在、CI 表面绿色或 Agent 汇报完成，都不能单独作为关闭证据。

### 14.2 阶段如何证明没有新增问题

绝对无缺陷无法证明。阶段退出必须提供：

1. 实际 diff 与预先登记的允许范围一致。
2. `new_finding` 为空。
3. 当前专项门禁和所有适用前序门禁通过。
4. 检查后工作树无非预期变化。
5. 干净检出可以复现结果。
6. 临时环境中的回滚演练恢复上一稳定状态。
7. 下一阶段或下一项正常工作成功消费本阶段产物。

玩家体验相关变化还必须增加绑定 build、场景、Slice 和 must-prove 的试玩证据。

### 14.3 已知问题的携带规则

只有能在 base commit 稳定复现的问题才可登记为 preexisting。它必须有稳定指纹、影响边界、不阻塞当前目标的理由和对应候选工作。由当前变更产生的新问题不得通过“接受为债务”进入下一阶段。

## 十五、全局成功标准

只有同时满足以下条件，重构才可关闭：

1. 根入口能指出唯一 current playable、权威地图、构建命令和本地工作流。
2. Agent 入口不保存玩法参数、历史禁令或重复流程。
3. 当前能力分别记录设计、实现、集成、健康和试玩证据。
4. 当前 Slice 数据闭包有明确 allowlist、owner、Schema、版本和消费者。
5. 生成物可重复，检查默认只读并 fail closed。
6. Core 是玩法规则的唯一运行时实现，Unity 通过 adapter 消费。
7. 干净检出可以构建、验证并启动 current playable。
8. Current 源码、数据和规格不规范性依赖 `.scratch`、archive 或大决策树。
9. 历史和研究可以恢复，但不会自动进入默认上下文。
10. 一个普通设计工作和一个普通工程工作已使用新结构完成。
11. 所有适用阶段门禁通过，剩余 preexisting 债务已明确建档。

验收主线：

> 新加入者或 Agent 能从仓库入口找到当前目标，在干净环境构建并运行一个使用真实 Core 的 Unity 可玩切片，而不需要先阅读历史决策和临时资料。

## 十六、待确认决策

- CP-01 是否成为第一个正式 current playable；如果不是，由哪个 Slice 替代。
- 首个 Slice 的 must-prove、试玩样本和晋升阈值。
- Core 供 Unity 消费时采用同源本地包、多目标构建还是受版本校验的 DLL。
- 当前 Slice 运行时数据闭包的精确范围。
- 研究 PDF、原始科学数据和美术源文件采用 Git LFS 还是外部存储。
- 是否以及何时执行 Git LFS 历史迁移；如执行，必须是独立 K3 维护事件。
- 远端 GitHub 标签、Issue Forms 和自动化何时同步；任何同步都需要显式授权。
