## 你的任务

为《子非鱼》的**开局**（角色创建）设计「人生经历」的**数据结构**与**接口调用方式**。

**不是**产出分类学讨论，**不是**产出设计哲学，**不要**写文献综述。

## 一、硬约束（违反即作废）

1. **只在开局 / Web 演示侧工作。** 禁止引用或依赖 C# 引擎与**神经模拟系统**：脑区 · 连接组与链路 · 主导网络 × 主导角色 · W 矩阵 · 意识结构 · 情境原语 · 认知评价（`AppraisalProfile`）· α 模式 · 环境基调 · 数值化阈值与 β/k/g 参数——**一律不得作为先例、字段、接口或依赖出现**。
   理由：该系统**过于复杂，不能立刻实现**。当前目标是**先把开局跑通**。
2. **不要读任何旧文档来推导结构。** 旧的 48 段经历是**过渡期产物**：可整体作废，不需要兼容，不需要逐条保留。不要去翻旧文件。
3. **禁止层级归属。** 记录中不得存在"类别 / 主题 / 父类 / 归属"这类**单值归属键**；不得有"一种经历是另一种经历的子类"的结构。每段经历必须能**独立存在、独立被引用**。
4. **组合 + 接口**：数据结构 = 扁平记录（字段即 facet）+ 受控词表（字段取值是指向词表的引用）+ 查询式接口。调用方**按字段查询**，不按路径寻址，不靠字符串匹配。
5. **立刻可实现**：纯 JSON + 浏览器 JS。无后端、无数据库、无外部依赖、无构建期代码生成。
6. **一份权威数据**：数据只有一份，设计文档与 Web 都从它派生。**禁止同一批记录出现两份手写副本。**
7. 同一事实只有一个权威来源；数据里的每个数值必须可追溯到它的来源字段。

## 二、起点：owner 给的 facet 草案

```
Experience
│
├── Context       发生在哪里
│   ├── 家庭 · 学校 · 工作 · 社会 · 生存环境
│
├── Relation      与谁发生关系
│   ├── 父母 · 伴侣 · 同伴 · 陌生人 · 群体
│
├── Role          自己处于什么位置
│   ├── 被照顾者 · 照顾者 · 执行者 · 被管理者 · 管理者 · 局外人
│
├── Event         发生了什么
│   ├── 获得 · 失去 · 冲突 · 威胁 · 失败 · 成功 · 暴露 · 改变
│
├── Duration      持续多久
│   ├── 瞬时 · 短期 · 长期 · 反复
│
├── Agency        自己有多少控制权
│   ├── 主动 · 部分主动 · 被迫 · 完全无法控制
│
└── Consequence   造成什么后果
    ├── 能力 · 关系 · 资源 · 信念 · 行为模式 · 情绪反应
```

这不是最终结构——它是**起点**。你可以增、删、拆、合并 facet，但必须逐条说明理由。

## 三、已定结论（直接采用，不要重新论证）

- **Duration 与 Agency 必须是一等字段。** 现在"长期 / 反复 / 从小 / 被迫"这类语义只活在人类可读的字符串里，机器读不到——这是必须修掉的核心缺陷。
- **Consequence 是输出槽，不是与 Context 平级的分类器。** 它必须**多值**（一段经历可有多个后果出口）。
- **Role 草案混了三种东西**：照护位（被照顾者 / 照顾者）· 权位（执行者 / 被管理者 / 管理者）· 归属状态（局外人）。必须拆开或归位，不能留在一张表里互相污染。
- **facet 是求值向量，不是笛卡尔积枚举。** 每条经历给每个 facet 一个值即可。**不要**生成组合空间，**不要**枚举所有可能单元。
- **浏览分组 = 视图（selector）**，不是身份。一条经历可以同时命中多个视图；视图增删不需要改经历数据。
- **词表必须闭集**：每个取值有稳定 id + 玩家可读标签。
- **非法 facet 组合必须显式登记**（例：学校 × 伴侣）。不要寄望数据结构自动排除语义上荒谬的组合。
- 不要为了"完整"而增加 facet。**每个 facet 必须能回答"调用方拿它查什么"**；答不上来就删。

## 四、必须服务的开局交付物（本次不改这些，但你的结构要能喂它们）

- **属性五项**：体格 / 巧手 / 观察 / 沟通 / 意志。最终限制 **0–10**，映射五档（笨拙 / 协调 / 精通 / 娴熟 / 本能）。
- **每段经历的原始属性变化净值固定为 +2**（可写 `+2`、`+1/+1` 或 `+3/−1`）。
- 玩家**限额选 10 段**；**同类最多 2 段**（"类"按哪个 facet 计由你定义，见输出要求）。
- 经历 → **疾病候选**：玩家只能在候选里选病。
- **互斥**：某些经历不可同时选，互斥项在界面上灰掉。
- **流程五屏**：选经历 → 属性结算 → 疾病候选 → 选疾病 → 镜子。

> 若上述任何一条与 owner 最新口径冲突，以 owner 为准，并在产出里标出你改了哪条。

## 五、你要交付的

### 1. 受控词表
每个 facet 给出：**id · 名称 · 取值列表（id + 玩家可读标签）· 单值还是多值 · 空单元/禁止组合登记**。
另需说明：通配或缺失取值（如 `none` / `unknown`）的使用规则。

### 2. 经历记录 schema
给出 JSON 级字段描述 + **至少 3 条完整示例记录**（跨不同 facet 组合）。
硬要求：**主键是稳定 id**；**没有类别字段**；**所有语义在字段里，不在文本里**。

### 3. 接口
- **查询函数签名**：按 facet 过滤 · 视图 selector 求值 · 互斥判定 · 配额计数 · 疾病候选并集 …
- **视图定义格式** + 至少 3 个真实视图。
- **调用点清单**：开局每一屏分别调哪个接口、拿什么参数、得到什么。
- **增删改口径**：加一条新经历需要改几个文件——**答案必须是 1**；若你的设计不是 1，说明为什么不可避免。

### 4. 校验与不变量
列出可机械检查的不变量：词表收口（无未登记取值）· 取值可达性 · 互斥对称性 · 文本与字段一致性 · id 唯一 · 视图非空 …
并对每条给出**没有工具强制时人肉怎么核**的办法。

### 5. 反例清单
明确写出什么算**失败**：父类/类别归属键 · 语义藏在字符串里 · 同一批记录两份手写副本 · 字段不可查询 · 新增记录前必须先决定它"属于哪一类" · 依赖模拟层概念。

### 6. 自检
逐条回答：
- 删掉任意一个视图，经历数据需要改动吗？（应为否）
- 加一条经历，改几个文件？（应为 1）
- 每个词表取值都有 ≥1 条记录用到吗？列出**死值**。
- 有没有哪个字段只存在于人类可读文本里？
- 有没有哪个 facet 无法回答"调用方拿它查什么"？
