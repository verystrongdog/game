## 回滚演练（WORKFLOW §六.6 · P4a 遗留未实测）

在临时 worktree 中执行（不触碰工作区）：

```bash
git worktree add .evtmp_fixture_verdicts/rollback-drill HEAD
cd .evtmp_fixture_verdicts/rollback-drill
git revert --no-commit dec52ef 849ab27 e059999 6ad1a8d 7420295 e338fc8
```

**结论：可以整体撤销，且撤销后逐项恢复到 P4c 之前的稳定状态。**

| 复验项 | 撤销后实测 | 与 base 一致？ |
|---|---|---|
| 与 `dec070a` 的 diff | 空 | ✅ |
| `data/runtime-fixtures/` | 不存在 | ✅ |
| `data/manifest.json` 文件数 | 47 | ✅ |
| 校验器数量 | 10（`validate_runtime_fixtures.py` 消失） | ✅ |
| 11 → 10 个校验器 | 全部 exit 0 | ✅ |
| `dotnet test` | **353 passed / 0 failed** | ✅ |

> ⚠️ **一处必须记录的坑**：**逐个** `git revert <sha1> <sha2> …` 会在
> `data/manifest.json` 上冲突——因为 manifest 被后续提交反复改过。
> **一次调用按逆序列出全部 6 个** SHA 则干净通过。
> 这不是脚本缺陷，而是"生成物被多次提交"的必然结果：
> 整体撤销与逐条撤销的语义不同。回滚本阶段请用后者。

临时 worktree 已移除（`git worktree list` 只剩主工作树）。

## ★ 本轮抓到 6 个真实缺陷

| # | 缺陷 | 性质 | 发现方式 |
|---|---|---|---|
| 1 | 5 个 ENIGMA 矩阵被标 `archived`，实为活跃生成链输入 | **误分类** | 追未闭合项 3 时对照生成器源码 |
| 2 | `doc_refs` 扫**工作区**，`.refactor-backup/` 与 `.scratch/` 副本抬高计数 | 判据污染 | 同上 |
| 3 | `doc_refs` 排除整个 `data/`，`data/README.md` 的引用被忽略 | 判据过窄 | 同上（误伤 `enigma_all_connections.csv`） |
| 4 | `git ls-files ''` 不报错但**返回 0 个文件** → `doc_refs` 静默全返零引用 | **静默型** | 加规则后分类全变成"零引用"，读数可疑 |
| 5 | 必需嵌套键判 `is null` 无效——record 的 init 默认值是 `new()` | **C# 静默接受** | fixture `BR-required-nested-1` |
| 6 | `situation_primitives` 的 `primary_networks` 指向未注册网络，加载期完全不可见 | **契约空洞** | 写 SP-network-registry 规则时 |

**#4 与 #5 尤其值得记**：两者都不会让任何校验器变红。
#4 靠"读数不合理"发现（13 个文件突然全变成零引用）；
#5 靠 fixture 的**构造性**发现——它把"删掉一个必需字段"变成一次真实加载调用，
而"看一眼代码觉得判了 null"不会暴露这件事。

## ★ 「共用 fixture」不是判据，「逐条判定相同」才是

owner 方案 §9.3 的原文判据是「跨语言接受/拒绝集合一致」。前四个提交只做到
「两侧读同一批输入」——**共用输入 ≠ 同一判定**。第 5 个提交把它变成可执行比对：

```
Python 判定 53 条 · C# 判定 53 条 · 交集 53 条 → 差异 0
```

**零豁免这一事实本身值得记录**：C# 走真实加载器，额外覆盖跨文件语义
（moonlight 的 supp ⊆ W_active 端点集）与反序列化层契约（`[JsonRequired]`、
枚举 converter），本可正当地被"已声明差异集"豁免。实测这些用例两侧判定
**也相同**，说明两侧规则确实重叠，而不是靠豁免掩盖分叉。

## 未闭合项（不得当作通过）

1. **`hansen2024/` 的 5 个数据文件零受控消费者**（`brainstemfc_Schaefer400.npy` 等）。
   `gen_modulation_ceiling.py` 的 `load_hansen_brainstem()` 自述
   「没有原始 FC 矩阵，使用基于 Hansen 社区分类的**估计值**」——
   数据在仓库里，生成器却不读它。后果是「Hansen 2024」作为参数来源的标注
   与代码实际行为不一致。
   **处置需 owner 裁定**（改读真数据 or 标注为估计值），两项都改设计/代码行为，
   超出「只动结构与引用」的 P4c 范围。已登记于 [external-sources.md §二](../../../data/connectivity/external-sources.md)。
2. **三项外部数据许可未登记**（`hansen2024` / `cab-np` / `kroell14_networks`）。
   当前无发布行为故不阻塞；进入发布路径前必须补齐（owner 方案 §12.3）。
3. **`role=generator-input` 仅 1 个实例**（`domain_role_map.json`）。这不是缺口而是
   判据收紧的结果：被生成器读取**且有活跃文档背书**的文件优先归 `reference`
   （`privileged_pathways` / `region_name_map` 等属此类）。四轴中该角色合法且可用，
   只是当前数据里满足其严格定义的只有一个。
4. **Unity 阻塞消费闭合**（不变）：P4c 产物的消费者是 P4d（Core→Unity 接缝），
   仍受阻于 Unity `NOT_AVAILABLE`。
