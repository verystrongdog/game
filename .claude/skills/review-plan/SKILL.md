# /review-plan — 符号执行审查

对 md 方案/规格文档做符号执行审查（Symbolic Execution），追踪每一步的输入和输出类型，找语义断层。审查只报告缺口，不做设计决策。

## 核心动作

读完一段规则后，问三个问题：
1. 这段话定义了什么数据？
2. 这个数据的类型是什么？
3. 谁消费它？

三个答不上来 → **有缺口**。报告缺口，不替用户做设计。

## 执行流程

```
0. Layer 1 强制执行 → 1. 解析 → 2. 排序 → 3. Trace → [3.5 交叉比对] → [4. L1.5抽查] → 5. 输出
```

### Step 0 — Layer 1 强制预检查（不可跳过）

**每次 `/review-plan` 被调用时，AI 必须首先自动运行 Layer 1 脚本。** 不传 `--pre-check` 不再允许——AI 自己跑脚本、自己消费输出。

执行方式：
```
python3 tools/run_all_checks.py --format json
```

AI 必须：
- [ ] 运行 `run_all_checks.py`，收集 JSON 输出
- [ ] 如有 FAIL（blocker > 0）→ 打印死链/参数冲突清单，询问用户"是否忽略这些错误继续审查？"
- [ ] 如有 WARN → 在 trace 输出中标注"Layer 1 发现 N 个警告，详见预检查报告"
- [ ] 将 JSON 输出中的 `blocker` 和 `warn` 数组作为 `--pre-check` 等效输入传给 Step 3.5
- [ ] 如果脚本无法运行（exit code = -1 或 ModuleNotFoundError）→ 报告用户并降级为纯 AI 模式，标注"⚠️ Layer 1 不可用，审查结果可能遗漏基础错误"

### Step 1 — 解析

- 读取所有目标 md 文件
- 用 H1-H6 标注所有规则候选段落（见 §启发式规则）
- 如有 --pre-check → 解析预处理输入（见 §--pre-check）
- H1 自动拉入被引用文件：深度 1 级，上限 5 文件，visited set 去重

### Step 2 — 排序

按数据流依赖排序：父类→子类 > 被引用→引用方 > 数据文件→消费方 > 方案→实现。循环引用保留原序。

### Step 3 — Trace

逐条填 9 列 trace table。每步做值域叉乘（N×M>50 → 抽样）。空白格 → 标记 ❌ 或 ⚠️。产生缺口时 → 填写"输出·消费者"→ 写入待复查清单。

### Step 3.5 — 交叉比对（--pre-check 时）

Layer 2 trace 出的 ❌/⚠️ 与 Layer 1 覆盖声明取交集：
- 缺口落在 Layer 1 覆盖区域内 → `⚠️ Layer 1 可能漏检（非抽查发现）`
- 缺口落在覆盖范围外 → 正常标记

### Step 4 — Layer 1.5 抽查（--pre-check 时）

- 覆盖声明 = pre-check 输入的"检查范围"段
- 随机抽 3 项独立验证
- 不一致 → `⚠️ 前置脚本可能漏检`
- 输入无检查范围段 → `⚠️ 无法确定覆盖范围，跳过抽查`

### Step 5 — 输出

写入 `.scratch/review-trace-YYYY-MM-DD-HHMM-<文件名>.md`，终端打印摘要。

## 启发式规则 H1-H6

| # | 触发信号 | md 中的形态 | 抓取内容 |
|---|---------|------------|---------|
| H1 | 跨文件引用 | `父类: xxx`、`[显示名](路径)`、`参考 xxx.md §N` | 消费方路径、被引用字段 |
| H2 | 枚举/类型定义 | 列表 `↑/↓/异常/null`、表格值域列、YAML 可选值 | 完整值域枚举、null 处理 |
| H3 | 数据变换 | "计算/求和/取最大值/比对/转换/映射/归一化" | 输入→输出类型、中间步骤 |
| H4 | 分支/条件 | "如果…则…"、"当…时…"、表格不同行不同逻辑 | 分支条件、覆盖完备性 |
| H5 | 管道衔接 | 编号步骤（Step 1→2→3）、"上述结果传入…" | 步骤间类型传递 |
| H6 | 表格数据列 | ≥3 列表格，含数值/类型/路径 | 每列类型、值域、null 处理 |

**不触发**：纯叙述段落、设计意图/动机、已标记 `⚠️ 已废弃` 的段落、索引/目录。

## H→9列映射方法

| 触发 | 核心动作 | 填列顺序 |
|------|---------|---------|
| H1 | 生成"引用连接行" | 输入·来源（被引用文件+字段）→ 变换=引用解析 → 输出·类型 → 输出·消费者 |
| H2 | 生成"类型定义行" | 输出·类型（完整值域）→ 变换=定义值域 → 输入·来源 → 输出·消费者 |
| H3 | 生成"变换行"（核心行类型） | 变换 → 输入·类型 → 输出·类型 → 边界 |
| H4 | 有前置 H3 → 扩展 H3 行。无前置 H3 → 独立生成 trace 行（变换="条件分支"）。前置范围 = 同一 `###` 小节 | 分支条件 → 分支数×值域 → 逐组合检查覆盖 |
| H5 | 合并多步为行序列。管道内同时 H4 → 先 H4 扩展再 H5 衔接。顺序：H3→H4→H5 | 严格检查输出·类型 = 下一行输入·类型 |
| H6 | 每列 1 类型定义行（H2）+ 行间关系生成变换行（H3） | 同 H2 + H3 |

### 推导策略

- **输入·类型**：从原文找"从 X 中取"/"基于 X"/"X 包含"——X 即输入。已在前序 trace 行定义过 → 复用。未定义 → ❌ 缺口
- **输出·消费者**：全文搜索引用该输出的段落（字段名/变量名/步骤编号）。搜不到 → ⚠️ 未被消费
- **边界**：枚举所有异常输入（null/空/越界/类型不匹配），逐条检查是否有处理逻辑

### 叉乘上限

N×M>50 → 抽样。全边界：数值型 min+max+null，枚举型全部值+null，混合型笛卡尔积。随机补 10-15 组，总计 ≤30。标注 `⚠️ 抽样检查`。

## Trace Table 9列

| 列 | 追问 |
|----|------|
| # | 步骤序号 |
| 规则 | 在追踪哪条规则？（格式: `文件名 §段落`） |
| 输入·来源 | 数据从哪个文件/字段/上一步来？ |
| 输入·类型 | 确切类型签名？值域完整吗？（使用类型标签） |
| 变换 | 这一步对数据做什么？ |
| 输出·类型 | 产出的确切类型？所有可能返回值 |
| 输出·消费者 | 谁在下一步消费这个输出？列出所有调用方 |
| 边界 | 空输入/极端值/类型不匹配时怎么处理？ |
| 判定 | ✅完整 / ⚠️有疑点 / ❌有缺口。AI 代劳无脚本时标注覆盖深度：`✅(浅)` = 浅层，`⚠️(AI)` = 不完整 |

## 简化类型系统

| 标签 | 含义 | "已定义"标准 |
|------|------|------------|
| `枚举<T>` | 有限值域 | 所有合法值已列出 + null 处理明确 |
| `数值` | 连续值 | 有下界 + 上界 + 单位 |
| `引用<T>` | 指向其他文件/段落 | 目标存在 + 类型已知。段引用（`§N`）→ 段必须存在。字段引用（YAML）→ 字段必须存在 |
| `文本` | 无约束字符串 | 有格式约束则注明，否则"无约束" |

复合：`List<T>` `Dict<K,V>` `Optional<T>`。任意基础类型组合均合法。
`枚举<是|否>` 等价布尔，不单独建标签。

### 判定规则

- `枚举<T>` 值域没列全 → ❌
- `数值` 缺上界或下界 → ⚠️
- `引用<T>` 目标不存在 → ❌
- `文本` 一般不做缺口判定（除非显式格式约束）

## 停止条件

### 正常停止
1. **项目边界停**：数据源是项目外不可变物。`tools/` 目录下脚本默认为"非标准工具，需 trace"
2. **类型闭合停**：输入类型已定义 + 输出类型已定义 + 叉乘覆盖 + 边界已处理
3. **重复模式停**：与之前 trace 步骤同构，引用之前结论

### 不能停的信号
- 输入/输出类型没写全
- 变换有"计算/求和/映射/比对"但无具体方法
- 输出没有列出所有消费者
- 边界条件有空白

## 半径扩张

任何 ❌/⚠️ 行 → "输出·消费者"列必须填写 → 自动进入待复查清单。修复后重新运行 `/review-plan`，对比两次输出。

上次 trace 发现：glob `.scratch/review-trace-*-<文件名>.md`，按时间戳取最新非本次文件。`--diff-against <file>` 可覆盖。

## --pre-check 预处理输入

```
/review-plan <file> [--pre-check <text_or_file>]
```

通用机制，不绑定特定领域。传入脚本输出 → 标记为"已验证基础层"，trace 时跳过。

### 推荐格式

```
# <脚本名> — <一句话描述>
## 检查范围
- <检查类别1>：<覆盖说明>
- <检查类别2>：<覆盖说明>

## 结果
PASS  <check_id>  <描述>  [位置]
FAIL  <check_id>  <描述>  [位置]
WARN  <check_id>  <描述>  [位置]

## 汇总
N checks: X passed, Y failed, Z warnings
```

非此格式 → AI 语义解析，标注 `⚠️ 前置输入格式非标准，解析可能不完整`。

## 审查范围策略

| 文件数 | 策略 |
|--------|------|
| 1-2 | 全 trace：每个 H3 触发完整 9 列 |
| 3-5 | 聚焦跨文件：H1 + H5 优先，单文件快速扫描 |
| 6+ | 仅 H1 引用链：保证引用完整性 |

文件数 = 用户显式传入的文件数。H1 拉入文件不参与策略判定。总行数 > 5000 → 降级为聚焦跨文件。`--full` 可覆盖。

## 自检信号

Skill 运行中监控，触发时提示用户：

| 信号 | 触发条件 | 提示 |
|------|---------|------|
| 类型分类退化 | ≥5 行类型无法判定，且 AI 确认"文档清楚但无法归类"（v1 AI 元认知判断；v2+ 替换为客观启发式） | "类型标签体系可能覆盖不足，建议补充 Worked Example" |
| 叉乘频繁抽样 | ≥3 次触发抽样上限 | "文件分支复杂度较高，建议拆分规则段落" |
| Layer 1.5 不一致 | 抽查发现 Layer 1 "通过"结论与独立验证不符 | "前置脚本可能漏检，建议审查脚本逻辑" |
| 拉入超限 | H1 拉入连续超限（>5） | "该文档跨文件依赖较多，建议缩小审查范围" |

## Worked Example 参考

目标文件: `实体/疾病目录/双相障碍I型.md`（继承 `奖赏系统障碍` 父类，含完整功能域配置表和非线性跳变）。

展示 H1-H6 全部触发类型的 15-20 行 trace。仅在"类型分类退化"信号触发时考虑补充第二个。

## 与 grilling 的分工

- `/review-plan` = 发现断层，产出缺口列表（批处理，不中断提问）
- `/grilling` = 对缺口做设计决策（交互式追问）
- trace table 中标注"建议 grilling"的缺口 → 创建 grilling issue
